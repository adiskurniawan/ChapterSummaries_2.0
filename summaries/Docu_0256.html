Document purpose and scope

This document describes the DeckGenerator taxonomy system as a data-driven, auditable classification and slide-type resolution engine. It covers the canonical taxonomy categories, slide-type catalog, YAML lexicon, registry construction, normalization behavior, conflict-resolution policy, validation workflow, migration status, and operational maintenance rules. It is intended for engineers modifying taxonomy data, matcher behavior, slide-type resolution, or audit tooling. The document favors predictable behavior, backward compatibility, and validation over ad hoc vocabulary expansion.
High-level system architecture

The taxonomy stack flows from YAML data into a loader, then into an immutable registry, then into matcher and resolver components:

1. deckgen/taxonomy/data contains canonical YAML catalogs and lexicon files.
2. deckgen/taxonomy/core/loader.py loads and validates YAML into a TaxonomyCatalog.
3. deckgen/taxonomy/core/registry.py builds a TaxonomyRegistry from base categories, optional legacy Python modules, YAML slide-type data, and YAML lexicon terms.
4. deckgen/taxonomy/core/matcher.py scores categories using registry evidence.
5. deckgen/taxonomy/core/rules.py and resolvers.py map matched categories and intents to final slide types.
6. deckgen/taxonomy/core/audit.py and scripts/check_taxonomy.py validate structural health and conflicts.

The design separates data, engine, and presentation. The registry is the single read-only source of truth for matching evidence.

Canonical taxonomy categories

A taxonomy category is a stable content classification, not a slide layout. Examples include executive_summary, comparison, process, risk_assessment, roadmap, dashboard, and checklist. Each category is represented by a CategorySpec with fields such as canonical, display, kind, parent, intents, priority, aliases, phrases, keywords, exclusions, bridges, fallback_slide_type, deprecated, replacement, and description.

The canonical key is the machine-readable identity. The display name is for humans. The priority is used for deterministic conflict resolution. The fallback slide type is used when rules need a default renderable slide type. Deprecated categories must include a replacement when possible.
Category kinds and structural semantics

The registry uses five category kinds:

• meta — high-level routing families such as executive, analysis, planning, governance, reference, collaboration, and delivery.
• domain — broad topical domains such as financial, risk, process, strategy, technical, people, and visual.
• subdomain — specific operational categories such as forecasting, risk_assessment, roadmap, metrics, checklist, and dashboard.
• bridge — categories that combine two domains, such as financial_scenario, risk_governance, and technical_data_platform.
• intent — intent-derived categories used for intent-level routing.

At the last validated count the registry contained 164 categories: 8 meta, 37 domain, 98 subdomain, 9 bridge, and 12 intent categories.
Intent model

Intents describe why content exists, while slide types describe how content should be rendered. Supported intents include collaborate, compare, decide, diagnose, explain, forecast, govern, persuade, plan, reference, report, summarize, and train.

Intents are used in two ways:

1. Categories declare one or more intents, allowing rules to infer slide types from intent.
2. The registry maintains intent-term groups, giving the matcher additional evidence for intent classification.

The reference intent is special: it is supported as an intent but is not always materialized as a separate intent category when the meta category reference already covers the routing need.
Slide-type catalog

Slide types are renderable structural types. The canonical slide-type IDs currently defined are: title, title_only, section, end, summary, comparison, decision_tree, process_flow, timeline, checklist, table, matrix, quote, infographic, diagram, accounting_cycle, content, and custom.

Each slide type has a priority, category, description, aliases, phrases, layout hints, and optional notes. Slide-type aliases are normalized before lookup. Slide-type phrases are also normalized and may be used as additive evidence. The canonical slide-type ID should match the corresponding SlideType enum value when the enum is available.
Slide-type categories versus taxonomy categories

categories.yaml defines slide-type categories such as meta, narrative, executive, decision, action, data, visual, process, planning, domain, and custom. These organize slide types for catalog reporting and documentation.

They are not the same as taxonomy matching categories. For example, the slide-type category executive groups slide types such as summary, while the taxonomy category executive_summary classifies content and maps to a slide type. Documentation and tooling should avoid conflating these two category systems.
Variant model

Variants are specialized expressions of base slide types. Examples include end_thank_you, end_q_and_a, comparison_pro_con, comparison_scenario, decision_tree_logic, decision_tree_option, checklist_actions, checklist_readiness, content_faq, and content_overview.

Each variant must reference a valid base_slide_type. Variants may contribute aliases and phrases. Variant aliases are additive and must not override authoritative slide-type aliases. Variants are useful for precise slide selection, template selection, and future layout hints, but they should not fragment the canonical slide-type enum.
Deprecation data model

deprecations.yaml records deprecated aliases, phrases, terms, categories, or slide-type values. Each deprecation may include kind, value, normalized value, replacement, reason, date, and status. At the last validated count the file contained 22 deprecation entries across kinds alias, phrase, and term.

The loader reads deprecations and the audit tool confirms availability. The matcher does not yet fully enforce deprecations. Future work may suppress deprecated terms, remap them to replacements, or emit deprecation warnings during matching and reporting.
YAML lexicon tree

The lexicon lives under deckgen/taxonomy/data/lexicon. It includes shared, group, common, and domain-specific vocabulary files. Domain files include process.yaml, explanation.yaml, technical.yaml, financial.yaml, risk.yaml, scenario.yaml, comparison.yaml, legal.yaml, people.yaml, visual.yaml, and many others.

At the last validated count the lexicon contained 59 loaded files, 2660 terms, and 29 domains. Current lexicon terms are classified as phrases. The loader supports alias, phrase, keyword, group, and generic term types, but alias and keyword populations are not yet fully migrated into YAML.
Loader behavior and caching

loader.py loads YAML using safe parsing and caches loaded YAML mappings by path. It tolerates missing optional files, collects validation warnings, and can run in strict mode. It produces a TaxonomyCatalog containing slide types, slide-type categories, variants, deprecations, lexicon data, warnings, and raw metadata.

Loader responsibilities include duplicate normalized alias detection, duplicate normalized phrase detection, variant base validation, category coverage warnings, deprecation parsing, and lexicon term normalization. The loader does not import legacy Python alias or phrase modules. This keeps YAML loading isolated from legacy runtime side effects.
Registry construction sequence

registry.py builds the registry in a deterministic order:

1. Initialize built-in base taxonomy categories.
2. Load shared data modules when available: shared terms, shared phrases, shared keywords, intent terms, modifiers, and stopwords.
3. Load legacy alias modules when available.
4. Load legacy phrase modules when available.
5. Load legacy keyword modules when available.
6. Load the YAML taxonomy catalog through the loader.
7. Merge YAML slide-type aliases additively.
8. Merge YAML lexicon terms additively.
9. Validate parents, build children, finalize category alias, phrase, and keyword sets.
10. Build immutable phrase and keyword owner maps.

Missing optional legacy packages are ignored silently in non-strict mode. Real import errors are recorded as warnings. Strict mode raises for unrecoverable structural problems.
Normalization semantics

Normalization is central to deterministic matching. Taxonomy terms are lowercased, trimmed, whitespace-collapsed, and treated with hyphen and underscore as separators. Punctuation edges may be stripped depending on the helper used.

Equivalent examples:

• decision_tree, decision-tree, and decision tree normalize to decision tree.
• process_flow, process-flow, and process flow normalize to process flow.
• title_only, title-only, and title only normalize to title only.

Because normalization collapses these variants, YAML files should not list multiple forms of the same term in the same alias or phrase list. One representative term is enough; matching still covers the normalized equivalents.
Alias ownership and conflict policy

Alias ownership is single-owner. A normalized alias maps to one canonical category. Conflict resolution is deterministic:

1. Explicit alias-owner overrides are applied first.
2. Explicit or base categories beat auto-created auxiliary categories.
3. Auto-created auxiliary conflicts are resolved silently.
4. Explicit versus explicit conflicts are reported as warnings.
5. Remaining conflicts are resolved by higher category priority, then alphabetically earlier canonical key.

Lexicon aliases are additive and do not override existing Python alias owners. This preserves legacy authority during migration while allowing YAML to fill gaps.
Phrase ownership and multi-owner semantics

Phrase ownership is multi-owner. A normalized phrase may belong to multiple canonical categories. The phrase map stores normalized phrase -> tuple of canonical categories. Owner order is deterministic: higher priority first, then alphabetical canonical key.

Multi-owner phrases are not necessarily errors. They allow broad phrases to contribute evidence to several plausible categories. However, highly generic phrases should be audited because they can reduce match precision. Lexicon phrases are additive and currently provide the majority of registry phrase coverage.
Keyword ownership and tuning risk

Keyword ownership is also multi-owner. The keyword map stores normalized keyword -> tuple of canonical categories. Keywords are weaker evidence than aliases and phrases, but they can still influence scoring.

The current validated state reports 310 multi-owner keywords. Examples include accountability, owner, board, committee, compliance, dashboard, policy, and progress. These are not errors, but they should be reviewed during matcher tuning. If a keyword activates too many unrelated categories, it should be moved to stopwords, narrowed, or replaced by more specific phrases.
Slide-type alias precedence

Slide-type alias resolution has a separate precedence model from taxonomy category aliases:

1. Legacy aliases/slide_type.py is authoritative when present and non-empty.
2. Other legacy alias modules may contribute slide-type aliases only when the authoritative source is unavailable.
3. YAML slide_types.yaml aliases fill gaps additively.
4. YAML variant aliases fill gaps additively.
5. Lexicon slide-type terms fill gaps additively.

Additive sources use setdefault semantics. They do not override existing slide-type alias targets. This prevents late-loading YAML or lexicon data from silently changing established slide-type resolution.
Canonical remapping and auxiliary categories

Data modules and lexicon files often reference auxiliary keys such as summary, recap, closing summary, forecast table, risk register, or process flow. Some of these are useful as aliases or phrase owners but should not become standalone taxonomy categories.

The registry remaps many auxiliary keys to stable base categories. Examples include summary -> summarize, overview -> concept_overview, risk register -> risk_assessment, forecast table -> forecasting, timeline -> roadmap, and process flow -> process. If a key cannot be remapped and is needed for ownership, the registry may create a low-priority auxiliary category. Auxiliary categories do not steal alias ownership from explicit categories and should be promoted only when intentional.
Matcher evidence model

The matcher scores categories using evidence from the registry:

• alias_map — strong single-owner evidence.
• phrase_map — strong or moderate multi-owner evidence.
• keyword_map — weaker multi-owner evidence.
• intent_terms — intent-level evidence.
• modifiers — emphasis or qualification signals.
• stopwords — terms that should be ignored or downweighted.

The matcher returns primary and secondary matches with confidence scores, matched evidence, and reasons. The resolver then applies bridge logic, exclusions, priority, and slide-type mapping. Matcher tuning should be documented in docs/tuning.md.
Rules and slide-type mapping

rules.py maps taxonomy categories and intents to slide types. It prefers category-level fallback slide types when available, then intent-level fallback slide types, then a conservative default such as content.

The current validated fallback distribution is heavily weighted toward content, with smaller counts for comparison, diagram, timeline, checklist, process_flow, and summary. This is expected because many subdomains are explanatory and default to content. Specialized categories should declare more specific fallback slide types when their renderable intent is stable.
Audit report contract

audit.py produces a JSON-friendly report with stable buckets:

• errors — structural or loading problems that should fail validation.
• warnings — non-fatal issues that should be reviewed.
• info — successful checks and summary observations.

The report also includes summary.errors, summary.warnings, summary.info, and summary.total. The ok flag is true when errors are zero. In strict mode, ok requires zero errors and zero warnings. The previous accidental infos bucket has been removed. Tooling should rely on errors, warnings, and info only.
Validation workflow

Primary validation command:

python scripts/check_taxonomy.py --print-human

Useful variations:

• python scripts/check_taxonomy.py --json — machine-readable report.
• python scripts/check_taxonomy.py --fail-on-warnings — fail if warnings exist.
• python scripts/check_taxonomy.py --allow-conflicts — do not fail on alias conflicts.
• python scripts/check_taxonomy.py --limit 0 — unlimited list output.
• python scripts/check_taxonomy.py --output - — write Markdown to stdout.

Direct audit commands:

• python -m deckgen.taxonomy.core.audit
• python -m deckgen.taxonomy.core.audit --json
• python -m deckgen.taxonomy.core.audit --strict

The default Markdown report is written to reports/taxonomy_report.md when a reports directory exists.

Why registry aliases are currently zero

The registry reports zero aliases because the loaded YAML lexicon terms are currently classified as phrases, not aliases. This is expected and does not indicate a loader or registry failure. The registry supports lexicon aliases, but the lexicon data has not yet populated alias-type terms at scale.

To add aliases:

1. Add aliases sections to lexicon files.
2. Migrate selected legacy Python aliases into YAML lexicon alias terms.
3. Reclassify selected high-confidence phrases as aliases.
4. Re-run validation to ensure no normalized alias conflicts appear.

Aliases should be reserved for strong, canonical labels. Phrases should remain the broader evidence layer.
Coverage gaps and their interpretation

The coverage report shows categories without direct aliases, phrases, or keywords. At the last validated count, 164 categories had no aliases, 152 had no phrases, 94 had no keywords, and 92 had no aliases, phrases, or keywords.

This does not mean those categories are unreachable. Matching can still occur through parent categories, domain categories, intent terms, keyword evidence, bridge categories, and resolver logic. However, important categories should eventually receive direct vocabulary. Prioritize categories that are frequently requested, frequently misclassified, or critical to deck generation quality.
Multi-owner keyword audit guidance

Multi-owner keywords should be reviewed periodically. For each high-conflict keyword, ask:

1. Does the keyword strongly indicate one category?
2. Does it appear in multiple categories only because of legacy grouping?
3. Should it be a phrase instead of a keyword?
4. Should it be moved to stopwords?
5. Should it be replaced by more specific terms?

Examples:

• dashboard may belong to metrics, data_analytics, and deliverables.
• policy may belong to policy, legal, and governance.
• owner may belong to lists, actions, owners, and stakeholders.

Do not remove multi-owner keywords blindly. Validate with sample matches before changing ownership.
Legacy Python migration compatibility

Legacy packages under aliases, phrases, keywords, and shared are optional during migration. The registry must build successfully when they are missing. This allows YAML lexicon files to replace hardcoded vocabulary incrementally.

Migration rule:

1. Keep legacy modules until their vocabulary is migrated to YAML.
2. Add YAML lexicon terms additively.
3. Validate that phrase and keyword coverage does not regress.
4. Remove legacy Python vocabulary files only after validation and matcher review.

Legacy modules may still be authoritative for slide-type aliases when present. YAML and lexicon sources fill gaps rather than overriding authoritative legacy behavior.
Data editing rules

For ordinary vocabulary changes, prefer YAML lexicon files over Python modules. Use domain-specific files under deckgen/taxonomy/data/lexicon/domains when possible.

Do not add duplicate normalized terms. For example, avoid listing process_flow, process-flow, and process flow as separate aliases in the same slide-type entry. Use one representative term, usually the human-readable spaced form.

Use deprecations when removing or renaming terms. Do not silently delete vocabulary that may still appear in existing content or fixtures. Add a replacement whenever possible.
Schema guidance for slide_types.yaml

Each slide-type entry should include:

• enum_value matching the canonical slide-type ID.
• name for human display.
• category matching a slide-type category.
• priority for deterministic alias and variant precedence.
• description explaining intended use.
• aliases as normalized strong labels.
• phrases as normalized longer expressions.
• layout_hints for renderers.
• notes for exclusions or special behavior.

Avoid duplicate normalized aliases and phrases. Avoid generic aliases that could plausibly belong to many slide types unless explicitly governed by conflict rules.
Schema guidance for lexicon files

Lexicon files should declare domain, value type, status, and description. Terms may be provided as simple strings or structured mappings with target, priority, tags, status, and legacy metadata.

Supported term types include alias, phrase, keyword, group, and generic term. For category vocabulary, phrase terms should include a target category or domain. For slide-type vocabulary, value type should be slide_type and target should be a canonical slide-type ID.

Lexicon terms with no valid owner are skipped. Terms whose target is unknown may be skipped unless they can be safely remapped to an existing category. This prevents uncontrolled creation of auxiliary categories from loosely targeted lexicon entries.
Determinism and reproducibility

The taxonomy system is designed to be deterministic. Given the same data files and legacy modules, registry construction should produce the same alias map, phrase map, keyword map, slide-type alias map, and category specs.

Determinism is enforced through stable sorting, priority-based conflict resolution, alphabetical tie-breakers, and additive setdefault semantics for late-loading sources. Avoid introducing randomness, filesystem-order dependence, or time-dependent behavior into registry construction. Dynamic discovery may enumerate modules, but the resulting names are sorted before use.
Operational failure modes and recovery

Common failure signals and remediation:

• Missing legacy alias package: not an error if YAML lexicon is active. The registry should build with zero import warnings after the optional-missing-module fix.
• Duplicate normalized aliases in YAML: remove duplicate variants and re-run validation.
• Audit unavailable with key errors: ensure audit report uses errors, warnings, and info buckets.
• Lexicon terms not appearing in registry: verify term type, target, domain, and owner remapping.
• Sudden alias conflicts: inspect reports/taxonomy_report.md and use alias-owner overrides only when the correct owner is stable.

Always regenerate the taxonomy report after remediation.
Performance characteristics

Registry construction cost is dominated by module discovery, YAML loading, normalization, and map finalization. The YAML loader caches loaded files by path, reducing repeated load cost within a process. The registry is cached after first construction, with separate caches for strict and non-strict instances.

Matcher cost depends on input length and the number of normalized terms compared against alias, phrase, keyword, and intent maps. Large phrase maps increase precision but also scoring cost. For batch deck generation, reuse a long-running process to amortize registry construction and module import costs.

Evidence layers and relative strength

The matcher uses several evidence layers from the registry:

1. Alias map — strongest evidence. A normalized alias maps to one canonical category.
2. Phrase map — strong evidence. A normalized phrase may map to one or more canonical categories.
3. Keyword map — weaker evidence. A normalized keyword may map to one or more canonical categories.
4. Intent terms — intent-level evidence used to support category intents.
5. Modifiers — emphasis or qualification signals.
6. Stopwords — ignored or downweighted terms.

Because the current registry has zero aliases, the phrase layer is currently the primary taxonomy evidence source. Alias tuning is the highest-leverage next improvement.
Alias tuning policy

Aliases should be reserved for strong, canonical labels that almost always indicate one category. Good alias candidates are explicit, low-ambiguity terms such as executive summary, decision tree, process flow, risk register, roadmap, dashboard, or checklist.

Rules for aliases:

• Add aliases only when confidence is high.
• Prefer single-owner aliases.
• Do not add generic words as aliases unless governed by an explicit override.
• Do not add multiple normalized variants of the same alias.
• Use aliases for labels that should strongly route content.
• Use phrases for longer or less certain expressions.

Because aliases are single-owner, a bad alias can cause confident misclassification. Alias changes require fixture validation.
Phrase tuning policy

Phrases are the main scalable evidence layer. They can be multi-owner, which allows a phrase to support several plausible categories. Good phrase candidates are longer, descriptive expressions such as root cause analysis, executive summary and key takeaways, decision needed on budget, risk register and mitigation plan, or process workflow and swimlane overview.

Rules for phrases:

• Prefer phrases over keywords when the expression is stable and meaningful.
• Allow multi-owner phrases when the phrase is genuinely cross-cutting.
• Avoid very short phrases unless they are highly specific.
• Avoid phrases that are merely generic deck language, such as next slide, overview slide, or important points.
• Add phrases to YAML lexicon domain files whenever possible.
• Validate phrase additions with sample inputs and explain-match output.

Phrase tuning should improve recall without creating excessive multi-owner noise.
Keyword tuning policy

Keywords are weak evidence. They are useful for topical signals but dangerous when overly generic. The current registry contains 5566 keywords and 310 multi-owner keywords. This is the highest-risk tuning area.

Rules for keywords:

• Use keywords only when the term is topically meaningful.
• Prefer multi-word keywords over single-word keywords.
• Demote or remove generic keywords that appear across many unrelated categories.
• Move generic connectors to stopwords.
• Convert stable keyword patterns into phrases when they reliably indicate a category.
• Promote highly reliable keywords to aliases only when they are single-owner and explicit.

Keyword changes should be reviewed in the multi-owner keyword report before and after editing.
Multi-owner keyword policy

Multi-owner keywords are not errors. They indicate that a keyword contributes evidence to more than one category. Examples from the current report include accountability, owner, board, committee, compliance, dashboard, policy, and progress.

For each multi-owner keyword, decide one of:

1. Keep it if it is genuinely cross-cutting.
2. Narrow it by replacing it with more specific phrases.
3. Demote its weight if matcher weights are configurable.
4. Move it to stopwords if it is too generic.
5. Assign it to a single category if it strongly indicates one category.

Do not remove multi-owner keywords blindly. Validate with real content because keywords may be the only evidence for some categories.
Intent-term tuning

Intent terms describe communicative purpose, such as summarize, explain, diagnose, forecast, govern, decide, plan, compare, report, collaborate, persuade, train, and reference.

Intent tuning rules:

• Add intent terms that clearly signal purpose.
• Avoid intent terms that are also generic nouns.
• Keep intent terms separate from category-specific phrases when possible.
• Use intent terms to support slide-type mapping when category evidence is weak.
• Validate that intent terms do not overpower category evidence.

Example: what should we do next may support decide or plan, but should not override explicit category evidence such as risk register.
Modifiers and stopwords

Modifiers change emphasis, urgency, negation, or scope. Stopwords are terms that should be ignored or downweighted during matching.

Modifier rules:

• Add modifiers that reliably change intent or urgency.
• Avoid modifiers that are common filler words.
• Document any modifier that changes scoring materially.

Stopword rules:

• Add stopwords for generic deck vocabulary that does not indicate category.
• Avoid adding domain terms to stopwords unless they are truly non-discriminative.
• Review stopwords before adding new keywords.
• Do not use stopwords to hide bad taxonomy design.

Examples of likely stopwords: slide, page, section, content, details, information, overview when used generically. However, overview may still be meaningful in phrase form, such as process overview.
Slide-type match defaults

The slide-type catalog defines conservative default matching behavior in slide_types.yaml:

• min_score: 0.35
• prefer_exact_alias: true
• prefer_longer_phrase: true
• use_priority_on_conflict: true

Interpretation:

• Matches below the minimum score should be treated as weak or unresolved.
• Exact alias matches should outrank partial or phrase-based matches.
• Longer phrases should generally outrank shorter fragments when both match.
• Priority should be used when multiple slide-type candidates remain tied.

These defaults are intentionally conservative. They favor stable slide selection over aggressive inference.
Confidence thresholds and rejection policy

Matcher output should be interpreted in bands. Recommended bands:

• High confidence: strong alias or long phrase match with clear category ownership.
• Medium confidence: phrase or keyword evidence with some ambiguity.
• Low confidence: weak keyword-only evidence or many competing owners.
• Unresolved: score below threshold or no meaningful evidence.

Policy:

1. High-confidence matches may drive slide-type selection directly.
2. Medium-confidence matches should be combined with intent, title, bullets, and resolver logic.
3. Low-confidence matches should fall back to category defaults or generic content.
4. Unresolved input should use a safe default slide type, usually content.

Do not force a specific slide type when evidence is weak. Prefer a conservative fallback.
Priority and conflict resolution

When multiple categories or slide types compete, resolution should be deterministic:

1. Explicit alias evidence beats phrase evidence.
2. Longer phrase evidence beats shorter fragment evidence.
3. Higher category priority beats lower category priority.
4. Alphabetical canonical key is the final tie-breaker.
5. Explicit slide-type aliases beat additive YAML or lexicon slide-type aliases.

Do not introduce nondeterministic tie-breakers. If a conflict is important, resolve it with an explicit alias-owner override, a phrase ownership change, an exclusion, or a documented tuning rule.
Exclusions and negative evidence

Exclusions reduce confidence when competing signals are present. For example, a strategy category may exclude terms associated with legal, compliance, audit, tax, or accounting when those terms indicate governance rather than strategy.

Exclusion rules:

• Use exclusions only when two categories are commonly confused.
• Prefer narrow exclusions over broad exclusions.
• Document why each exclusion exists.
• Validate exclusions with before-and-after match examples.
• Avoid exclusions that suppress legitimate cross-domain content.

Exclusions are a precision tool. Overusing them can create false negatives.
Bridge category tuning

Bridge categories combine two domains, such as financial_scenario, risk_governance, technical_data_platform, customer_research, and change_communication. They are useful when content genuinely belongs to two domains at once.

Bridge tuning rules:

• Use bridge categories only when both bridged domains are present.
• Do not use bridge categories as catch-all categories.
• Add phrases that explicitly combine the domains.
• Ensure bridge categories have clear fallback slide types.
• Validate that bridge categories do not steal matches from stronger base categories.

Example: financial scenario sensitivity analysis may justify financial_scenario, but plain financial analysis should remain financial_analysis.
Deprecated terms and tuning

Deprecated terms are recorded in deprecations.yaml. The taxonomy currently loads and audits deprecations but does not fully enforce them during matching.

Until enforcement is implemented:

• Do not add deprecated terms as new aliases.
• Avoid adding deprecated terms as phrases unless needed for backward compatibility.
• Prefer replacement terms in new vocabulary.
• Use deprecation entries to document retired terms.
• Plan matcher support for remapping deprecated terms to replacements.

Deprecation tuning should be coordinated with documentation and regression fixtures.
Coverage gap remediation

The current coverage report shows categories without direct aliases, phrases, or keywords. Coverage gaps should be fixed in priority order:

1. Categories that are frequently requested in real decks.
2. Categories that are frequently misclassified.
3. Categories that are important for slide-type selection.
4. Categories that currently rely only on parent or intent evidence.
5. Long-tail categories with low usage.

For each gap, add:

• One or two strong aliases if appropriate.
• Several descriptive phrases.
• A small set of specific keywords.
• Optional exclusions if the category is easily confused.

Avoid adding large keyword lists without reviewing multi-owner effects.
Tuning workflow

Use this workflow for every tuning change:

1. Identify the misclassification or coverage gap.
2. Inspect the current registry report and explain-match output.
3. Decide whether the fix belongs in aliases, phrases, keywords, stopwords, exclusions, intent terms, or resolver logic.
4. Make the smallest possible YAML change.
5. Run taxonomy validation.
6. Run sample matches.
7. Add or update fixture cases.
8. Review multi-owner keyword and phrase counts.
9. Document the change if it affects behavior materially.

Do not make large bulk vocabulary changes without validation. Small incremental changes are easier to diagnose and revert.

Variant model

Variants are specialized expressions of base slide types, defined in variants.yaml. The catalog currently contains 54 variants. Each variant has:

• id — variant key, conventionally base_qualifier, such as end_thank_you.
• name — human-readable label.
• base_slide_type — required; must reference an existing slide type.
• category — slide-type category, inherited from the base when omitted.
• variant_type — for example layout, emphasis, or content.
• description — intended use.
• priority_offset — adjustment applied to the base priority.
• aliases and phrases — additive slide-type vocabulary.
• notes — special behavior.

Variant aliases contribute to the slide-type alias map additively and never override authoritative base aliases.

Priority model

Priorities drive deterministic slide-type selection:

1. Higher slide-type priority wins when aliases conflict across slide types.
2. Alphabetical slide-type ID is the tie-breaker.
3. Variant priority_offset adjusts the base priority for variant-level ordering.
4. use_priority_on_conflict: true is the catalog default.

The current priority ladder runs from title (1000) down to custom (830). Meta slides sit at the top because structural signals are usually explicit. content and custom sit at the bottom because they are fallback-oriented types. Do not raise a priority to fix a vocabulary problem; fix the vocabulary instead.
Global conflict rules

slide_types.yaml defines explicit global conflict rules for ambiguous terms:

• decision -> comparison (generic decision slides are comparison/option slides).
• decision tree -> decision_tree (more specific than generic decision).
• logic tree -> decision_tree.
• option tree -> decision_tree.
• grid -> table.
• cluster -> table.
• matrix -> matrix (explicit matrix content, not generic table).
• flowchart -> process_flow.
• executive conclusion -> summary (legacy resolver behavior).
• final ask -> summary (legacy resolver behavior).
• minimal title -> title_only (title-only/emphasis slide).
• evidence -> table (generic evidence lists).
• evidence summary -> summary (summary, not table).

When adding a new ambiguous term, prefer adding a global conflict rule over silently assigning it to one slide type.
Excluded terms policy

Some terms are intentionally excluded because suffix normalization may collapse them toward the wrong target:

• decision panel and decision panel slide — use decision tree panel and decision tree panel slide for decision_tree.
• decision stack and decision stack slide — use decision tree stack and decision tree stack slide for decision_tree.
• minimal title page — use minimal title for title_only.
• evidence stack and evidence stack slide — use evidence summary and evidence summary slide for summary.

Each excluded term records a reason, a preferred term, and a preferred target. When a term is excluded, document the preferred replacement in the same entry.

Match defaults and thresholds

Slide-type matching defaults from slide_types.yaml:

• min_score: 0.35 — matches below this score are weak or unresolved.
• prefer_exact_alias: true — exact alias matches outrank partial phrase matches.
• prefer_longer_phrase: true — longer phrases outrank shorter fragments.
• use_priority_on_conflict: true — priority resolves remaining ties.

Category-level defaults from categories.yaml:

• min_score: 0.30
• use_slide_type_priority_on_conflict: true
• prefer_specific_slide_type_over_category: true

These defaults are intentionally conservative. They favor stable slide selection over aggressive inference. Threshold changes must be documented in docs/tuning.md and backed by fixture tests.
Normalization rules for aliases and phrases

Slide-type aliases and phrases are normalized before matching:

• lowercase
• collapse whitespace
• strip punctuation edges
• treat hyphen as separator
• treat underscore as separator

Consequences:

• decision_tree, decision-tree, and decision tree are equivalent.
• process_flow, process-flow, and process flow are equivalent.
• title_only, title-only, and title only are equivalent.

Because of this, the catalog keeps one representative form per term and omits duplicate normalized variants. The loader detects duplicate normalized aliases and phrases within a slide type and reports them as warnings. The catalog is currently clean: zero duplicate-normalization warnings.

Slide-type categories versus taxonomy categories

Do not conflate the two category systems:

• Slide-type categories (meta, narrative, executive, decision, action, data, visual, process, planning, domain, custom) group slide types in categories.yaml for catalog organization and reporting.
• Taxonomy categories (executive_summary, risk_assessment, roadmap, and so on) classify content in the registry and drive matching.

A taxonomy category maps to a slide type through fallback rules and resolver logic. A slide-type category never participates in content matching directly.
Validation rules

slide_types.yaml validation settings:

• require_enum_match: true — enum_value must match the entry key and the SlideType enum.
• forbid_conflicting_aliases: true — conflicting slide-type aliases are reported.
• warn_on_duplicate_phrases: true — duplicate normalized phrases produce warnings.
• allow_legacy_python_sources: true — legacy Python vocabularies remain valid during migration.

categories.yaml validation settings:

• require_all_slide_types_covered: true — every slide type must belong to a category.
• allow_duplicate_slide_types: false — a slide type may not belong to two categories.

The loader also validates variants: every variant must reference a known base_slide_type, and unknown variant categories produce warnings.
How to add a new slide type

Steps:

1. Confirm the type is renderable and not expressible as a variant of an existing type.
2. Add a SlideType enum value in deckgen/taxonomy/core/types.py.
3. Add the entry to slide_types.yaml with enum_value, name, category, priority, description, layout_hints, aliases, and phrases.
4. Assign it to a category in categories.yaml.
5. Add variants only if the type has stable specialized forms.
6. Add global conflict rules for any ambiguous aliases.
7. Update renderer support in deckgen/render.py.
8. Run python scripts/check_taxonomy.py --print-human and python -m deckgen.taxonomy.core.audit.
9. Add fixture cases covering the new type.
10. Update this document.
How to add a new variant

Steps:

1. Choose a variant ID using the base_qualifier convention, such as timeline_gantt.
2. Set base_slide_type to an existing slide type.
3. Set category explicitly or inherit from the base.
4. Add a clear description and variant_type.
5. Add aliases and phrases that are specific to the variant and do not conflict with the base.
6. Use priority_offset only when the variant should outrank or under-rank the base in tied situations.
7. Run validation and confirm no new alias conflicts appear.
8. Update this document if the variant changes documented behavior.
Anti-patterns to avoid

1. Adding a new slide type when a variant is sufficient.
2. Adding duplicate normalized alias variants such as process_flow, process-flow, and process flow in the same list.
3. Assigning an ambiguous generic term to one slide type without a global conflict rule.
4. Raising priority to win a conflict instead of fixing vocabulary.
5. Letting variant aliases override base slide-type aliases.
6. Adding technical diagrams to diagram instead of custom.
7. Adding chart vocabulary to a new type before the chart_type taxonomy is reconciled.
8. Editing slide-type aliases in Python while the YAML catalog is active.
9. Removing an excluded term's documentation without a preferred replacement.
10. Changing min_score or conflict defaults without fixture-backed validation.
