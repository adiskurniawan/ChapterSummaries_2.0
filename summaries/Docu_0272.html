1. Introduction: Understanding AI Agents and Their Purpose

Artificial intelligence, usually called AI, is technology that enables computers to perform tasks normally associated with human intelligence. These tasks include understanding language, summarising documents, finding patterns, answering questions, writing content, analysing information, generating code, and helping people make decisions. An AI agent is a software system that uses AI to work towards a particular goal. Instead of simply answering one question and stopping, an agent can plan a series of steps, gather information, use connected tools, carry out permitted actions, check the results, and decide what to do next. This shift from generating a single response to coordinating a process is an important development in modern computer science and enterprise software. In the classical AI literature, including Stuart Russell and Peter Norvig's Artificial Intelligence: A Modern Approach, an agent is understood through its interaction with an environment: it receives information about the environment and takes actions intended to achieve an objective. In the context of modern software, the environment may consist of databases, files, APIs, web interfaces, communication systems, financial applications, and other digital services. Its information inputs and available actions depend on the connections provided by the surrounding application.

Imagine asking an ordinary chatbot to help prepare a monthly financial report. The chatbot might explain how to prepare the report, suggest formulas, or write a narrative if the figures are supplied. An AI agent could potentially go further. If it has the necessary permissions and tools, it could locate the relevant files, read the data, compare actual expenditure with the budget, identify missing information, calculate differences, draft the report, test the calculations, and prepare the results for review. The distinction is that an agent is designed to work towards an outcome rather than merely produce an isolated answer. However, its ability to perform these steps depends on the tools available, the instructions provided, the quality of the information, and the permissions granted. An agent cannot legitimately claim to have performed an action merely because it can describe how the action would be performed. It must obtain evidence that the action actually succeeded.

The concept of an intelligent agent predates modern generative AI. Classical AI research examined systems that perceive environments, choose actions, evaluate results, and pursue goals. Russell and Norvig's textbook presents agent architectures and environmental characteristics that remain useful for understanding today's systems. Michael Wooldridge's work on multi-agent systems adds another important perspective: software agents can be designed to operate autonomously within defined boundaries and cooperate with other agents or people. Modern language-model-based agents combine these established ideas with natural-language understanding, probabilistic generation, retrieval systems, and tool integrations. They can interpret instructions that would be cumbersome to encode as a fixed list of rules, yet they still require ordinary software engineering to make their actions reliable and controlled.

Modern agentic design commonly draws on four practical patterns: reflection, tool use, planning, and collaboration. Reflection means evaluating an initial result against specified requirements and improving it when evidence indicates a problem. Tool use means calling external functions, services, or execution environments rather than attempting every task through text generation alone. Planning means decomposing a broad objective into smaller activities and organising them according to their dependencies. Collaboration means dividing a complex task among specialised components or coordinating the work of multiple agents. These patterns can make a language model more useful, but they do not guarantee correctness or safe autonomy. The system still needs reliable data, controlled permissions, validation, and a clear stopping condition.

A practical definition is therefore straightforward: an AI agent is a goal-oriented software system that uses an AI model and a controlled operating environment to select and coordinate actions towards a requested outcome. Some agents perform one or two tool calls. Others carry out longer workflows involving multiple systems, repeated validation, and human approvals. Neither intelligence nor autonomy should be assumed from the word agent alone. The architecture, operational permissions, measurable capabilities, and demonstrated reliability determine what the system can safely accomplish. Google Cloud and Microsoft's developer documentation describe agent systems in terms of goals, models, tools, context, action, and evaluation, providing useful foundations for distinguishing agent behaviour from ordinary text generation. References: Google Cloud — What Are AI Agents? and Microsoft — Understand AI Agents.

2. The Definition and Concept of an Agent in Software

In everyday language, an agent acts on behalf of another person or organisation. A travel agent helps arrange a journey, a purchasing agent helps obtain goods or services, and a financial agent may carry out specified duties under delegated authority. An AI agent follows a similar principle in software. A user establishes an objective, the developer defines the available operations and restrictions, and the system attempts to complete the permitted work. For example, a user might request, "Review these supplier invoices, identify possible duplicates, and prepare an exception report." The agent could inspect the records, compare invoice identifiers and amounts, group likely matches, calculate discrepancies, and present the findings. If permitted, it could also create a draft investigation request. If it has no authority to approve payments or modify accounting records, it must not perform those actions.

Michael Wooldridge's treatment of autonomous agents helps distinguish agent-oriented software from conventional programs. An agent can operate with some independence, react to environmental changes, pursue objectives, and interact with other agents or people. These characteristics do not mean that a software system possesses human consciousness, emotions, or moral responsibility. They describe capabilities and patterns of operation. In modern language-model systems, autonomy may be limited to selecting between several available tools, or it may extend to coordinating a sequence of actions until a task reaches a defined completion state. The level of autonomy depends on the implementation, not on whether the system appears conversational or humanlike.

Agent research also uses concepts such as beliefs, desires, and intentions to describe decision-making architectures. In a simplified Belief-Desire-Intention model, a system maintains information about the environment, represents objectives, and commits to plans for achieving those objectives. This provides a useful conceptual comparison for modern agents. Their working context contains current evidence; their task instructions define the requested outcome; and their plan specifies the proposed steps. The analogy should not be taken literally. An LLM's internal processing is not automatically equivalent to the mental states of a human being, and a conversational explanation does not establish that the system maintains an accurate, persistent representation of its own reasoning.

Consider an agent responsible for preparing an expense-monitoring report. Its relevant information might include the approved budget, actual transaction data, cost-centre mappings, reporting dates, and organisational policy. Its objective might be to produce a reconciled report with explanations for significant variances. Its planned actions could include importing the transaction data, validating the schema, calculating totals, comparing actual expenditure with the budget, and generating a draft. The application should separately enforce the user's access rights, numerical tolerances, and approval requirements. That separation allows the agent to make useful decisions about the sequence of tasks without giving it unrestricted authority over the financial system.

An AI agent is best understood as a software worker with a defined job, instructions, information, permitted tools, and a method for checking its work. This definition also clarifies why the label can be misleading. A product marketed as an agent might be a conversational assistant with a small collection of tools, a workflow engine that delegates decisions to an LLM, or a sophisticated system that coordinates multiple independent processes. Its actual capabilities should be assessed by examining what it can observe, what it can change, what it can verify, and when it must stop. Clear definitions help teams decide whether a task needs agentic behaviour at all or could be handled more reliably by ordinary software.

3. The Difference Between AI, Generative AI, Chatbots, Automation, and AI Agents

These terms are related, but they describe different things. Artificial intelligence is the broad field of developing systems that perform tasks associated with perception, learning, reasoning, language, planning, and decision-making. Generative AI refers to systems that produce content, including text, images, audio, video, and code. A language model that drafts a paragraph or summarises a document is an example of generative AI. A chatbot is a conversational interface through which a person communicates with software. Depending on the implementation, a chatbot may use fixed rules, a search system, a language model, or a combination of these technologies. Traditional automation, meanwhile, follows predefined rules and sequences. For example, a spreadsheet macro might copy data from one sheet to another when a button is pressed. It usually follows a programmed procedure rather than independently planning how to achieve a broad objective.

An AI agent combines AI with a process for selecting and coordinating actions towards a goal. It may use generative AI to interpret an instruction, conventional software to perform calculations, and connected services to access information or make changes. Consider a monthly expense report. A chatbot can explain the reporting process, a generative AI system can draft a narrative, a spreadsheet formula can calculate the totals, and a script can transfer figures into a template. An agent can potentially coordinate the entire process: find the approved source files, identify the period, invoke the calculation script, check for missing data, assemble the report, and request approval. These categories can overlap. A chatbot can include agent capabilities, and an agent can rely extensively on conventional automation. The important distinction is the function each component performs.

The distinction also affects reliability and maintenance. Traditional Robotic Process Automation (RPA) is effective when a process follows stable rules and consistent interfaces. A scripted process may break when an application changes a field identifier or a document layout. An AI-supported process may be able to interpret a differently formatted document or identify a field by its meaning. That adaptability can reduce maintenance, but it introduces a different risk: the AI may interpret the interface incorrectly. A probabilistic model may select the wrong field even when the correct field is available. Therefore, semantic flexibility should not replace deterministic checks for important operations.

A hybrid architecture often works best. Conventional automation can handle repeatable extraction, filtering, calculations, and database operations. A language model can interpret unstructured descriptions, classify documents for review, or draft explanations. An orchestration layer coordinates the components and checks the results. For example, a finance workflow might use a document parser to extract invoice data, a rules engine to verify required fields, a calculation module to reconcile the totals, and an AI component to identify unusual descriptions. The system can then send exceptions to a human reviewer rather than deciding that every unusual case is automatically acceptable.

This hybrid approach is sometimes described as agentic automation. Its purpose is not to replace every process with an autonomous model. It is to apply flexible interpretation where it is useful while preserving deterministic behaviour wherever accuracy, repeatability, and auditability are essential. The appropriate design depends on task variability, consequences of failure, data quality, and the cost of maintaining the system. A fixed formula may be the better tool for a recurring sum, while an agent may be useful for coordinating the investigation of a discrepancy that requires several documents and multiple possible explanations.

4. The Main Parts of an AI Agent

Most practical AI agents contain several interacting components. The first is the AI model, which interprets instructions, analyses information, generates potential actions, and produces language or structured outputs. Many modern agents use large language models (LLMs). The second is the instruction set, which defines the agent's purpose, boundaries, required outputs, and operating rules. A finance agent might be instructed to use approved source files, preserve original transactions, flag missing exchange rates, and never approve its own financial adjustments. The third component is context: the information available for the current task, including the user's request, relevant instructions, documents, previous tool results, and the current workflow state. The fourth is the toolset, which enables the agent to interact with external resources rather than relying exclusively on generated text.

Tools may provide read access to files, database queries, web research, code execution, spreadsheet manipulation, document creation, or communication functions. Each tool should have a clearly defined purpose, input schema, output format, permission boundary, and error-handling behaviour. A search function might return documents, for example, while a file-writing function saves a report to a specified location. The system should verify that the tool result matches expectations before using it as a basis for further action. If a tool returns an error or partial result, the agent should distinguish that failure from a successful operation and avoid presenting incomplete work as complete.

The fifth component is the workflow controller, often called the orchestration layer or agent runtime. It coordinates the steps, stores task state, validates tool requests, enforces execution limits, and determines whether the agent should continue, retry, pause, or request human assistance. The sixth component is memory or state management. During a task, the system may need to remember which files have been inspected, which calculations have been completed, which evidence has been found, and which questions remain unresolved. Longer-term memory may be supported for selected preferences or recurring instructions, but it should be governed by explicit retention and access policies.

The seventh component is the validation and approval layer. It checks calculations, verifies the presence of required information, enforces thresholds, and determines which actions require human approval. The eighth component is security and monitoring. Authentication, access control, logging, input validation, and runtime limits help prevent the agent from exceeding its authority or creating uncontrolled side effects. Guardrail frameworks can add screening and policy enforcement, but they should supplement rather than replace the security controls enforced by the application and the connected services.

These components are interdependent. A capable model without tools may explain what should be done but lack the means to do it. A tool-connected model without suitable instructions may act inconsistently. A model with good instructions and tools can still fail if the data is incorrect or the application accepts unsafe actions. An agent is therefore an engineered system rather than a model with a prompt attached. Reliability emerges from the interaction of the model, data, tools, orchestration, validation, and governance. Google Cloud's agent concepts provide an overview of these architectural elements: Google Cloud — Core Concepts of AI Agents.

5. How an AI Agent Works, Step by Step

An agent typically follows a repeating cycle of interpretation, planning, action, observation, and adjustment. First, it receives a goal. The user specifies the desired outcome, relevant dates, source material, constraints, and required output. Second, the agent interprets the request and identifies the evidence and operations needed. If the request is ambiguous, it may ask a targeted question, or it may proceed using a clearly documented assumption when the ambiguity is minor and the action is reversible. Third, it creates a plan by breaking the larger goal into smaller tasks and determining their dependencies. Preparing a financial report might require obtaining the trial balance before calculating balances, mapping accounts before aggregating them, and completing reconciliations before publishing the results.

Fourth, the agent retrieves information from approved sources. It may search a directory, query a database, inspect a spreadsheet, or read a policy document. It should check whether the records correspond to the correct entity, period, currency, and version. Fifth, it selects an action using the available evidence and permitted tools. Sixth, it executes the action and observes the returned result. Seventh, it evaluates the result against explicit acceptance criteria. A calculation may need to reconcile to a control total; a generated document may need to contain all required sections; a database operation may need confirmation that the requested record was updated successfully.

If validation fails, the agent may investigate the cause, correct a processing problem, and try again within a safe retry limit. For example, a spreadsheet import may fail because a column name changed. The agent might inspect the headers and map an equivalent column, provided the alternative is clear and the mapping is authorised. If the discrepancy could materially change the result, the system should stop and request clarification rather than guess. An agent should also distinguish between a recoverable technical failure and a business exception that requires a human decision.

The ReAct research framework explores an approach that interleaves reasoning and action, allowing a language model to use observations from external tools while working through a task. Tree of Thoughts explores deliberate problem-solving by considering alternative reasoning paths and evaluating them before proceeding. Reflexion investigates how language agents can use feedback about previous attempts to improve subsequent decisions. These research approaches help explain why agentic systems often operate in loops rather than following a simple sequence of fixed responses. They do not guarantee that an agent will reason correctly or that repeated attempts will converge on a valid result.

A complete workflow needs a defined stopping condition. The agent should stop when the requested acceptance criteria are satisfied, when an approval is required, when the available evidence is insufficient, when a safety limit is reached, or when continued attempts are unlikely to be productive. It should then report what was completed, what was verified, what remains unresolved, and which assumptions were used. A successful workflow is not merely one that reaches an output. It is one that reaches an output whose relationship to the original goal can be demonstrated. Research references: ReAct, Tree of Thoughts, and Reflexion.

6. An Everyday Example of an AI Agent

Imagine asking an agent to organise a business trip. It first identifies the destination, dates, travel preferences, budget, and required approvals. It searches authorised travel sources, compares available options, checks whether the proposed itinerary fits the dates and budget, and prepares a shortlist explaining the differences. If booking is permitted, the agent may proceed to the booking step. If payment or final confirmation requires approval, it must pause and obtain that approval. If the preferred flight becomes unavailable, the agent can search for an alternative, but it should not silently change important preferences or exceed the approved budget. Searching and comparing options are different from purchasing a ticket because a purchase creates a financial commitment.

The agent can also coordinate related tasks. It might compare the proposed itinerary with the user's calendar, identify meetings that conflict with travel, check whether the destination requires supporting travel documents, and prepare an expense-report template linked to a trip reference. These steps illustrate how an agent can combine information from several sources while maintaining a single objective. However, each source must be appropriate for the question. Flight information should come from a dependable booking source, meeting details should come from the authorised calendar, and travel requirements should be verified against relevant official guidance rather than inferred from an old itinerary.

Edge cases demonstrate why a clear plan is not enough. A booking service may return a timeout after receiving a request, leaving the agent uncertain whether the booking succeeded. Repeating the booking blindly could create a duplicate reservation. A safer workflow checks the booking status or uses an idempotency mechanism where supported before retrying. Similarly, an apparent fare change could mean that a flight is unavailable, a price has changed, or a search result is incomplete. The agent should identify which explanation is supported by evidence instead of selecting the most convenient interpretation.

The same approach applies to purchasing, scheduling, and administrative work. The system needs to understand the objective and constraints, gather current information, compare alternatives, execute permitted actions, verify outcomes, and obtain approval when necessary. The more consequential an action becomes, the stronger the required safeguards should be. A useful agent is not one that performs every possible task without interruption. It is one that knows which tasks can be completed independently and which require human judgment or explicit authorisation.

7. An Example Using a Finance Team

Consider a finance team that needs a monthly budget-versus-actual report. The agent receives a request specifying the reporting month, entity, currency, and expected output. It locates the approved budget, general ledger export, exchange-rate table, account mapping, cost-centre list, and reporting instructions. Before calculating anything, it checks that the reporting periods are consistent, the source files are readable, expected columns exist, identifiers are present, currencies are recognised, and required mappings are available. It then uses an approved calculation script or spreadsheet formulas to calculate budget, actual expenditure, remaining budget, variances, and variance percentages. It compares detailed totals with source control totals and identifies unusual movements, missing mappings, duplicate identifiers, and unexpected changes in classification.

Suppose the report indicates that a department has spent 18% more than its monthly budget. The agent can establish the amount of the variance, identify the transactions contributing to it, and compare the expenditure with prior periods. If a documented purchase order explains the increase, the agent can reference it. If the transactions show an increase in travel expenditure but no explanation is available, the agent should state that the increase is observed and the cause remains unconfirmed. It should not invent a narrative simply because a polished report is expected. The distinction between a numerical finding and an explanation supported by evidence is fundamental to reliable financial reporting.

For an Excel-based workflow, transaction data can be loaded into a structured table called Actuals, while the approved budget can be stored in a separate Budget table. A formula such as =SUMIFS(Actuals[Amount],Actuals[Department],A2,Actuals[Month],B2) can calculate actual expenditure for a selected department and month, provided the column names and data model match the formula. A corresponding budget formula can use the same keys against the budget table. The variance is then actual expenditure minus budget, while the variance percentage is calculated against the budget using an explicitly defined zero-budget rule. The agent should preserve any established formulas in the user's workbook and test new formulas against known examples before applying them across the report.

After the calculations, the agent prepares a report containing the key results, supporting tables, exceptions, assumptions, and unresolved questions. It validates the totals, records the source files used, and presents the draft to a finance officer. The reviewer investigates material exceptions and approves the report before distribution. A more advanced implementation may integrate with an enterprise resource planning system through authorised APIs or database views, but the data access should remain controlled and the accounting rules should remain independently testable. This workflow reduces repetitive effort without transferring accountability for published financial information away from authorised personnel.

8. An Example Using a Suspense-Account Tracker

A suspense-account tracker records financial items that have not yet been fully identified, allocated, corrected, or cleared. These items require investigation because the organisation needs to understand what they represent and how they should be resolved. An AI agent supporting this process could inspect the register, identify open items, calculate ageing, detect missing owners, and prepare a list of items requiring attention. Relevant fields might include transaction date, identification date, amount, currency, suspense account, source reference, investigation status, due date, owner, evidence status, correction status, posting status, and remaining balance. It could flag a transaction that has remained unresolved for more than 90 days, an item without supporting evidence, a missing correction reference, or a positive remaining balance that conflicts with a proposed closed status.

The agent could compare the suspense register with the general ledger, report unexplained differences, and group unresolved items by account, owner, currency, entity, root cause, and ageing category. In Excel, a structured table called Suspense could use a formula such as =TODAY()-[@[Transaction Date]] to calculate the age of an item, provided the source date is valid and the workbook's date calculation is appropriate. A status formula could then classify items into defined ageing bands, while conditional formatting highlights records exceeding the relevant threshold. A COUNTIFS formula can identify records that remain open after the review deadline. These rules should be documented because a transaction's age is not, by itself, proof that the transaction is wrong or should be written off.

The agent can prepare an investigation note, recommend the evidence needed, and draft a corrective-action request. It should distinguish between a confirmed error and a possible exception. A missing reference may require investigation, but it does not automatically prove that a transaction is incorrect. The agent should not fabricate a transaction explanation, post a journal, approve a write-off, or close an item without the required evidence and authority. A well-designed workflow preserves the original record, appends changes with timestamps, retains supporting-document references, and requires approval for material corrections or write-offs.

Relationships among records can make the investigation more complex. A single supplier payment might be split across several suspense lines because of partial clearing, currency differences, or different posting dates. The agent should examine shared transaction identifiers, bank references, invoices, and journal numbers before treating each line as independent. Graph-based retrieval methods may help discover relationships among documents and entities when a large collection of records is involved, but any proposed relationship must remain verifiable. Techniques such as GraphRAG combine entity and relationship extraction with retrieval and summarisation to assist with complex information discovery; they do not turn inferred links into accounting evidence automatically.

The agent handles searching, analysis, calculations, and drafting. Deterministic software enforces the applicable financial rules. Authorised staff make decisions that require professional judgment. This division produces a useful investigative workflow while preserving an audit trail. It also allows the organisation to analyse recurring root causes, such as inconsistent reference formats, a recurring rounding difference, or a process that repeatedly leaves transactions unallocated. Fixing a systemic cause is more effective than clearing the same exceptions every month.

9. AI Agents and Ordinary Automation

Traditional automation is especially useful when a process is predictable and the rules are stable. If the same data must be copied into the same template every month, a conventional script may be cheaper, faster, and easier to test than an AI agent. Agents become more useful when work involves changing layouts, ambiguous documents, multiple information sources, or decisions about which permitted action should come next. For example, a fixed script can calculate ageing from transaction dates, while an AI agent may help investigate why a group of items remains unresolved by reading descriptions, locating supporting evidence, and organising possible explanations. The strongest design often combines both approaches: conventional software performs calculations and repeatable transformations, while AI assists with interpretation and coordination.

This hybrid approach can reduce the brittleness of some traditional automation. A fixed script may fail when an invoice layout changes or a column is renamed. A document-understanding model may be able to recognise a field by its meaning and location within the document instead of relying on a fixed position. However, this flexibility can introduce mistakes. The model may confuse an invoice date with a due date, mistake a subtotal for a total, or assign a value to the wrong vendor. Important extracted fields should therefore be validated against expected data types, business rules, and control totals before the process continues.

In an event-driven architecture, conventional automation may respond to a webhook, scheduled job, or message in a queue. An AI agent can interpret the event and select an appropriate workflow. An incoming support ticket, for example, could be routed to a standard password-reset process, a troubleshooting workflow, or a human support specialist depending on its content and risk. The agent should not invent new permissions while routing the task; its choices must come from an authorised set of destinations and operations.

Tool choice should be determined by the task rather than by a preference for AI. Deterministic rules are generally better for simple numerical logic, exact field validation, and predictable transformations. An agent may be useful when context must be interpreted or when several possible next steps depend on the results of previous actions. Combining these approaches creates a more robust system than forcing a language model to carry out every operation. It also makes the system easier to test because the components with exact outputs can be evaluated independently from the components that perform probabilistic interpretation.

10. What Makes an Agent Different from a Script?

A script usually follows a defined sequence of instructions. If an input is missing, it may stop or produce an error according to its programmed rules. An agent can potentially interpret the situation, select between several permitted tools, and adjust its plan in response to observations. It might discover that a source file is missing, search an authorised alternative location, and report that a replacement source requires approval. The important difference is the flexibility of the decision process. A conventional script generally requires an explicit branch for each anticipated condition, whereas an agent can use its model to interpret conditions that were not described as exact rules in advance.

That flexibility also creates risk. A script may be predictable even if its design is limited. An agent may select an unsuitable tool, misunderstand a tool response, or produce a convincing but incorrect explanation. For this reason, important business rules should not depend solely on a language model's judgment. A rule such as "a journal above the approved threshold requires authorisation" should be enforced by the application or financial system, not merely written in the agent's prompt. The model may recommend the next action, but the execution layer should independently verify that the action is permitted.

Sandboxing is another important difference in operational design. If the agent can generate or execute code, the execution environment should restrict file-system access, network access, resource consumption, and available credentials according to the task. Container isolation or specialised execution services can help reduce the risk that an erroneous command affects the host environment. Static analysis, dependency scanning, and tests can provide further safeguards, although none eliminates all possible defects. Access to an execution environment should be granted only when needed and should not automatically imply permission to alter production systems.

Agents also need explicit task state. They may maintain a record of completed steps, evidence found, decisions pending, and operations that failed. This helps them resume a task and avoids repeating completed actions unnecessarily. However, a state record must distinguish confirmed events from proposed actions. A plan saying "send report" does not mean the report was sent. A note saying "reconciliation complete" should be supported by a successful check. Clear state transitions make agents more reliable and easier to audit.

The practical design principle is to use the agent for interpretation and coordination while using conventional software to enforce critical rules. A system may allow the agent to prepare a journal and validate its supporting evidence, but the posting service independently checks access and approval. This preserves the benefits of flexible decision-making without assuming that the model will always comply with every instruction or recognise every edge case.

11. Types of AI Agents

AI agents can be grouped in several ways, and different researchers and vendors use different classification schemes. Classical AI textbooks often distinguish simple reflex agents, model-based reflex agents, goal-based agents, utility-based agents, and learning agents. A simple reflex agent responds to current observations through relatively direct rules. A model-based agent keeps track of relevant aspects of the environment that are not immediately visible. A goal-based agent chooses actions in pursuit of a specified outcome. A utility-based agent evaluates alternatives according to a measure of desirability. A learning agent uses feedback or experience to improve some aspect of its performance over time. These categories are theoretical descriptions of capabilities and decision structures; a deployed system may combine several of them.

Modern applications can also be classified by their operational roles. A tool-using agent interacts with external functions or services. A research agent searches, compares, and synthesises information. A workflow agent coordinates a repeatable process. A coding agent inspects software, proposes changes, executes tests, and reports outcomes. A monitoring agent checks defined information sources for specified conditions and raises exceptions. A conversational agent communicates with a user to clarify requirements, present findings, and request decisions. These categories are not mutually exclusive. One application may use tools, conduct research, coordinate a workflow, and communicate conversationally within the same task.

Learning behaviour requires careful definition. An agent that adjusts its plan based on the current tool response is not necessarily retraining its underlying model. It may simply be responding to new evidence within the task. Longer-term improvement may require a separate mechanism for collecting feedback, evaluating performance, changing prompts or routing policies, or training a model. Such changes should not happen invisibly where they might alter a controlled business process. A dependable system records the version of its instructions, tools, configuration, and model so the organisation can investigate changes in performance over time.

Another useful distinction is between interactive and background agents. An interactive agent works with a user who can provide new instructions, correct misunderstandings, or approve actions. A background agent may be triggered by a schedule or system event and work with limited direct interaction. Background operation requires particularly clear stopping rules, logging, permissions, and exception handling because the user may not be watching each step. If a background agent encounters missing data or a high-impact decision, it should pause the affected workflow and notify the appropriate person rather than improvising beyond its authority.

Choosing an agent type is therefore a design decision. The organisation should begin by defining the task, required autonomy, available information, acceptable error rate, and impact of failure. It can then decide whether a reactive rules-based component, a goal-directed agent, a specialised research agent, or a multi-agent workflow is appropriate. The most sophisticated architecture is not always the best choice. A simpler system with clearly controlled behaviour may deliver better business results than a complex system whose decisions are difficult to predict or review.

12. What Is a Multi-Agent System?

A multi-agent system is a collection of agents that interact to complete a shared task or pursue related objectives. Imagine preparing a donor financial report. One specialised component gathers approved grant records, another checks expenditure classifications, and another prepares variance explanations using available evidence. A coordinating component assembles the report and checks whether required sections are present. Each component has a defined responsibility and receives only the information necessary for its role. This can reduce the complexity of an individual agent's task and make it easier to assign different verification responsibilities.

Dividing a task into multiple agents does not automatically improve reliability. Two agents may rely on the same incorrect source, repeat the same assumption, or fail in similar ways. Their agreement therefore does not prove that a conclusion is correct. A better approach combines specialised work with independent verification. For example, a calculation component can return totals and control checks, while a review component checks whether the required categories and reconciliations are present. Where accuracy is important, the review should use evidence independent of the claim being reviewed rather than simply asking another model to restate the first model's answer.

Frameworks such as AutoGen, CrewAI, and LangGraph provide different ways to coordinate agent interactions, messages, state, and workflows. Their use does not remove the need for sound application design. A multi-agent specification should define each agent's inputs and outputs, permitted tools, error behaviour, timeout conditions, and responsibility for verification. It should also explain how conflicts are resolved. If one component identifies a transaction as a duplicate and another classifies it as a legitimate partial payment, the system needs a defined escalation rule rather than a majority vote that ignores the evidence.

Multi-agent systems can be useful when work separates naturally into independent activities or when competing perspectives are genuinely valuable. A research component can gather primary sources, a critic can check whether the evidence supports the claims, and a synthesis component can prepare a concise explanation. In software engineering, one component can generate code while another runs tests and reports failures. In finance, one can prepare a reconciliation and another can test the calculation against a control total. These are practical applications of task decomposition rather than proof that independent AI personas have humanlike expertise.

Multi-agent coordination introduces additional costs. Agents may duplicate retrieval, consume unnecessary tokens, disagree over terminology, create circular requests, or pass incomplete information to one another. Large agent networks also enlarge the security boundary because each connected tool and shared memory location becomes another potential route for error or misuse. For this reason, the number of agents should be justified by measurable improvements in task performance, speed, coverage, or verification. A single agent with strong deterministic tools and a reliable review process may be simpler and safer than a large group of loosely coordinated agents.

13. What Is an AI Model?

An AI model is a computational system trained to recognise patterns and produce outputs from inputs. A large language model is designed to process and generate language, making it useful for interpreting instructions, summarising information, drafting explanations, generating code, and working with structured representations of tasks. However, an AI model is not the same thing as a complete agent. The model may propose a tool call, but the surrounding application determines which tools are available, whether the proposed action is authorised, how the result is processed, and whether the task should continue. A model's textual statement that an operation succeeded is not equivalent to a confirmation from the system that performed the operation.

Many modern language models use Transformer architectures, which rely on attention mechanisms to process relationships among tokens in an input sequence. Such models can identify patterns across long passages, but they still have context limits and may fail to recall relevant details consistently. Retrieval, context organisation, structured outputs, and validation can improve the reliability of applications built around them. The available context window should not be treated as a guarantee that every important fact will be used correctly. When a task includes a large collection of documents, the system should retrieve information according to relevance and preserve source identifiers so a result can be checked against the original material.

Some models use Mixture of Experts (MoE) architectures, in which different subsets of model parameters are activated for different inputs. This is one approach to balancing model capacity and computational requirements. Other systems use model routing, selecting a more suitable model for a given task according to cost, latency, complexity, or policy. These design choices affect the performance and operating cost of agent systems, especially when an agent calls a model repeatedly over a long workflow. However, a more expensive or larger model does not automatically produce a more reliable result. The model must still be evaluated on the relevant task, languages, data types, and risk conditions.

Structured output modes can make agent applications more robust. A model may be asked to return a validated JSON object with fields such as status, source_reference, variance_amount, evidence, and requires_approval. The application can then validate the structure and reject missing or invalid fields before using the result. This is safer than attempting to extract important values from an unstructured paragraph. Yet valid JSON proves only that the output matches the required format. It does not prove that the values are correct, that the evidence supports the conclusion, or that the requested action is safe.

Model selection should therefore consider the whole application. Relevant questions include whether the model handles the required languages, whether it can call tools reliably, whether it supports the necessary structured outputs, how it behaves when information is missing, and whether its cost is reasonable for the task. The developer should also consider model updates and configuration changes. A change in model version can affect how instructions are interpreted or which actions are proposed. Version tracking, regression testing, and monitoring help detect these differences before they cause serious problems in production.

14. What Is a Prompt?

A prompt is an instruction or set of instructions given to an AI system. A simple prompt might ask for a short summary, while a complex prompt might specify the purpose, input files, required calculations, output structure, validation rules, approval conditions, and reporting format for an entire workflow. A good prompt defines the requested outcome and clarifies the task's scope, source of truth, constraints, and acceptance criteria. For example, "Analyse the finance data" is vague. A more useful instruction would identify the reporting period, source files, reporting currency, required calculations, reconciliation rules, exception categories, and expected output.

Prompts should also define how the system handles uncertainty. The instructions can require the agent to distinguish verified facts from assumptions, cite the source of key figures, flag missing information, and stop when an ambiguity could materially affect the outcome. For example, if a budget file contains a different fiscal-year label from the actuals file, the agent should not silently assume that the periods match. It should verify the period definitions or request clarification. Clear instructions reduce ambiguity, but they cannot ensure that a model will follow every rule under every condition.

Prompt engineering methods include providing examples, defining roles, breaking a task into stages, specifying structured outputs, and including explicit acceptance criteria. Research methods such as ReAct explore combining model reasoning with tool use, while Tree of Thoughts explores evaluating alternative problem-solving paths. These are approaches for structuring certain kinds of tasks, not universal guarantees of accuracy. A more elaborate prompt can even make a system harder to maintain if it contains conflicting rules, unnecessary detail, or unclear priorities. A reusable prompt should therefore be tested on representative cases, including ambiguous inputs, missing information, and deliberately challenging examples.

Prompts should not be treated as a replacement for enforceable application controls. A prompt may tell an agent never to approve a journal, but the accounting system should also withhold approval permission. An instruction may require a variance explanation, but the reporting pipeline should detect when that field is empty. A prompt can request that sensitive information not be disclosed, but access controls should prevent the agent from retrieving or exporting records it is not permitted to use. Critical requirements should be implemented through multiple layers rather than relying entirely on natural-language instructions.

For recurring workflows, the prompt should be maintained as a versioned specification. Any change to its requirements should be documented, tested, and reviewed against the same set of representative inputs. For example, if an organisation changes the definition of a material budget variance from 10% to 5%, the update should be made consistently in the applicable rules, calculations, and reporting instructions. The change should not depend on a preparer remembering to alter one paragraph in an informal prompt. Treating prompts as part of the governed software configuration makes the agent easier to reproduce and audit.

15. What Is Context?

Context is the information available to an AI system while it performs a task. It can include the user's request, relevant instructions, previous tool results, source files, business policies, reference tables, and current workflow state. Good context helps the agent interpret the task correctly, while poor context can cause it to overlook an important restriction or confuse information from different reporting periods. For example, a financial report might contain an approved budget for one year and actual expenditure for another. If the agent fails to distinguish the periods, it may calculate a meaningless variance even though the arithmetic is correct.

Context should be relevant, clearly labelled, and sufficiently complete. Documents should include source identifiers, dates, versions, and other metadata needed for interpretation. When multiple sources disagree, the agent should not simply select the statement that seems most plausible. It should identify the conflict and apply the organisation's approved source hierarchy. A signed contract, an approved accounting policy, and an informal email may have different authority for different questions. The hierarchy should be defined according to the task rather than left entirely to the model's intuition.

Retrieval-Augmented Generation (RAG) is a common way to supply relevant context without inserting an entire document library into every model request. In a RAG workflow, documents are indexed, relevant passages are retrieved for a particular query, and those passages are supplied to the model alongside the task instructions. Embeddings and vector search can help identify semantically related text, while metadata filtering can restrict retrieval to the appropriate entity, date range, confidentiality category, or document type. The quality of the result depends on how the documents are parsed, segmented, indexed, retrieved, and interpreted. RAG is not a guarantee that the retrieved passage is correct or that the model will use it properly.

Standard vector retrieval may be less effective for questions that require relationships across many documents. Graph-based methods can represent entities and relationships that help with multi-hop questions, while GraphRAG combines knowledge-graph construction with retrieval and summarisation methods for discovery across large text collections. For example, an organisation may want to trace how a particular policy change affected several departments and contracts. A graph can help identify connections, but those connections remain hypotheses that should be checked against the supporting documents. Neither vector similarity nor a knowledge graph should be treated as authoritative evidence without source-level verification.

Context management also helps protect against information leakage and mistaken assumptions. Confidential documents should be retrieved only for users and tasks that are authorised to access them. Data from different clients, entities, or projects should not be mixed without a legitimate reason. Old instructions should be distinguished from current ones, and untrusted instructions embedded in source material should remain data rather than become controlling commands. The goal is to supply enough relevant information for the task while preserving source integrity, confidentiality, and a clear understanding of which facts are current.

16. What Is Memory in an AI Agent?

Memory allows an agent to retain useful information about a task or previous interactions when the application explicitly supports that capability. Short-term memory refers to information maintained during the current task or conversation, such as files examined, calculations completed, evidence found, and questions still unresolved. Longer-term memory may contain stable preferences, recurring instructions, reference information, or records of previous work. For example, a reporting agent might retain an approved report-naming convention or preferred date format so that the user does not need to restate those details each time. The system should nevertheless confirm that the stored preference remains applicable and has not been superseded by a newer instruction.

Memory does not necessarily mean the model has permanently learned new information. An application may simply store previous messages, summaries, or structured records and retrieve them when needed. It may also maintain a database of successful procedures or task outcomes. These mechanisms differ from retraining the underlying model, and they should be described accurately. An agent that refers to a stored rule is using retained information; it is not necessarily modifying its model weights or independently developing new knowledge.

Several useful memory categories can be distinguished. Episodic memory records specific events or past interactions. Semantic memory represents more general information, definitions, and relationships. Procedural memory stores instructions or sequences for carrying out tasks. Working memory holds the current task state and the information needed for immediate decisions. These categories are conceptual tools rather than mandatory implementation choices. A real application may use database tables, document repositories, search indexes, or structured workflow state instead of four separate memory systems.

Memory must be controlled carefully. An agent should not retain confidential information unnecessarily or assume that an old preference remains valid forever. A previous statement might describe an exception that applied only to one reporting period. A stored summary may omit an important qualification from the original document. The system should preserve provenance, timestamps, source references, and appropriate retention rules so users can determine where an item came from and whether it is still reliable. Sensitive data should not be placed into long-term memory merely because it may be useful someday.

Suppose a reporting agent has processed many supplier disputes and appears to notice a recurring classification issue. It may record a candidate observation that a specific supplier often labels freight charges inconsistently. That observation should be treated as a hypothesis until supported by verified records and, where necessary, confirmed by a responsible finance specialist. A memory entry should never silently turn repeated correlation into a new accounting rule. The agent may use its observations to prioritise future review, but consequential classifications should remain subject to authorised policies and evidence.

17. What Are Tools and Integrations?

A tool is a function or service that an agent can use to obtain information or perform an action. Examples include searching files, reading a spreadsheet, running Python code, querying a database, checking a business system, creating a document, or sending a message. An integration connects the agent to another application or data source. An application programming interface (API) allows software systems to communicate through defined operations. Tools extend what an agent can do, but they also establish operational boundaries. An agent that can read a file but cannot write to the storage location may analyse the file without changing it. An agent with access to a payment system may have greater potential impact and therefore needs stronger restrictions and validation.

Function calling allows a model to request a defined software operation using a structured description of the tool and its inputs. For example, a model might propose calling a function named read_budget with a reporting period and entity identifier. The orchestration layer should validate those arguments, check access permissions, invoke the function, and return the result to the model. The model should not be allowed to bypass the validated tool interface and directly execute arbitrary commands. Where the application supports structured output schemas, those schemas should constrain the request to the expected types and required fields.

Tool permissions should follow the principle of least privilege. An agent that prepares a financial report may need read access to approved data and permission to create a draft report, but it does not necessarily need permission to change the general ledger or release payments. High-impact actions, such as sending external communications, deleting records, approving transactions, or submitting official reports, should require stronger controls. Every tool should have a documented purpose, a defined input and output, expected failure modes, and a reliable way to confirm whether the action succeeded.

The Model Context Protocol (MCP) is an open protocol designed to standardise how AI applications connect to external tools and context sources. It can reduce the need for bespoke integrations by providing a common approach to exposing capabilities. However, a standard protocol does not make every connected tool trustworthy or safe. An MCP server still needs authentication, permission controls, careful input validation, and monitoring. The client must also verify that a tool's declared capabilities are appropriate for the task. A standard interface improves interoperability, but application security remains the responsibility of the systems that implement and use the interface.

Tool integration should be implemented incrementally. Read-only operations are generally a sensible starting point because they allow the agent to gather evidence without changing business records. The next stage might permit the creation of draft files or proposed actions in a review queue. Production write access should be introduced only when the workflow has been tested thoroughly and the necessary authorisation controls are in place. This progression makes it easier to demonstrate reliability before increasing the potential impact of the agent's actions.

18. How AI Agents Use the Internet

An agent with an authorised internet-search tool can retrieve information from online sources. It may search for official guidance, read documentation, compare sources, extract relevant facts, and produce a summary. This can be useful for technical documentation, research, current regulations, product specifications, and public information. Internet access does not mean that every result is trustworthy. Search results may be outdated, incomplete, biased, misleading, or unrelated to the task. The agent should evaluate the source, publication date, relevance, and supporting evidence. Official documentation is generally preferable for technical specifications, while government publications and primary regulatory materials are often useful for official rules and requirements.

Independent sources can provide additional context, but their claims should be assessed carefully. An agent should supply references for important factual claims so users can verify them. It must not fabricate URLs, claim to have read an article it did not access, or present a search snippet as proof of a full document's contents. It should distinguish between researching public information and acting on an external website: reading an article is different from logging into an account, submitting a form, purchasing an item, or communicating with another person. The latter actions may create financial, legal, or reputational consequences and should follow the applicable permission and approval rules.

Some browser-enabled agents can interact with websites through browser automation tools. These tools may navigate pages, inspect accessible interface elements, enter data, and submit forms. They can be valuable when an official website has no suitable API, but they are more fragile than a well-defined software interface. Layout changes, pop-ups, authentication requirements, and dynamic page behaviour can cause errors. A browser action should be verified by inspecting the resulting page or the confirmation returned by the site. A tool call that clicks a button does not prove that the desired transaction was completed.

Agents that search the web must also consider source trust and prompt injection. A webpage may contain instructions designed to manipulate the agent into ignoring its task or disclosing sensitive information. These instructions should be treated as untrusted content rather than as commands. The system should separate its governing instructions from retrieved material, restrict the operations that can be triggered by external content, and require appropriate approval before consequential actions. A source can be useful for its factual contents without being authorised to redefine the agent's responsibilities.

A responsible research agent should preserve the chain from claim to evidence. It can record the page title, source organisation, access date when relevant, and the exact passage that supports a conclusion. It should also indicate when sources disagree or when information could not be verified. When dates, regulations, or product details may have changed, it should prioritise recent official sources. These practices make web-assisted work auditable and help prevent a plausible but unsupported statement from becoming part of a decision or publication.

19. How AI Agents Work With Files

A file-capable agent may search a folder, read documents, extract information from spreadsheets, compare versions, and prepare new files. For example, it might locate a monthly financial report, read source tables, identify the reporting period, and prepare a revised summary. Reliable file handling requires more than finding a document with a suitable name. The agent should check whether it has selected the correct file, whether the file is current, whether its contents are readable, and whether it contains the required information. If several files have similar names, it should use metadata and content to identify the correct source. It should not silently substitute a different file when the intended file is unavailable.

Different file types require different handling. Text documents may contain headings, tables, footnotes, and embedded references. PDFs may contain selectable text, scanned images, complex page layouts, or a mixture of these. Spreadsheets can contain formulas, hidden sheets, merged cells, external links, named ranges, and data-validation rules. Presentations may distribute information across slide titles, speaker notes, charts, and images. A file-processing pipeline should therefore use methods appropriate to the source format and retain enough structural information to avoid confusing headings, labels, numbers, and explanatory notes.

For a scanned PDF, optical character recognition may be necessary to convert page images into text. OCR can introduce errors, especially with small text, unusual fonts, decimal points, negative signs, or multi-column layouts. A financial agent should check important extracted values against the original page or another reliable source. If a document contains a table whose row relationships are unclear, the agent should not assume that a number belongs to the nearest visible label. Layout-aware parsing and visual inspection may be necessary before the data can be used safely.

When modifying files, the agent should preserve the original unless replacement has been explicitly authorised. It should report which file it created or changed and where it was saved. For high-value outputs, the application should reopen the saved file and verify the structure, content, formulas, or other required properties. Successful text generation does not prove that a file is structurally valid or usable. A document may contain missing sections, a workbook may have a broken formula, and a presentation may have overflowing text even when the saving operation itself succeeds.

Tools for extracting and normalising document contents can make enterprise retrieval more reliable. They should nevertheless preserve source identifiers and avoid silently removing information that matters to the task. The system should also apply access controls before reading files, not merely after producing an output. Confidentiality, provenance, format validation, and change tracking are essential parts of responsible file handling. These controls help ensure that the agent's result can be verified and that the original records remain available when an issue needs to be investigated.

20. How AI Agents Work With Spreadsheets and Excel

Spreadsheets are useful for business analysis because they combine structured data, formulas, tables, charts, and reporting layouts. An AI agent can assist with interpreting a workbook, mapping columns, checking data quality, generating formulas, preparing reports, and explaining unusual results. However, spreadsheets introduce important risks: columns may be misidentified, dates may be interpreted incorrectly, currencies may be mixed, formulas may reference the wrong cells, blank records may be counted as transactions, and summaries may omit categories or include duplicates. A reliable spreadsheet workflow begins by inspecting the workbook structure. The agent should identify worksheet names, tables, headers, data types, formulas, named ranges, external links, and relevant workbook settings before changing anything.

It should then validate the input data. Checks may include required fields, duplicate identifiers, invalid dates, unexpected currencies, missing account mappings, inconsistent reporting periods, and records outside the approved reporting scope. Calculations should use explicit rules. For example, the definition of a remaining balance must specify how original amounts, cleared amounts, adjustments, and write-offs are treated. The agent should use structured table references or dynamically determined column positions where practical, rather than relying on unexplained fixed cell references. The same validation should be performed after the workbook is generated or modified.

For Excel reporting, structured tables make the calculation logic easier to understand and maintain. If transaction-level data is stored in a table named Transactions, a formula such as =SUMIFS(Transactions[Amount],Transactions[Department],A2,Transactions[Period],B2) can aggregate the amount for a selected department and reporting period, provided the column names and data types match. A mapping operation may use XLOOKUP where it is supported by the workbook's Excel version and the lookup keys are unique or the expected match behaviour is documented. These formulas should be tested against a small known dataset before being used for a full report. If the workbook already contains an established formula, the agent should preserve it when requested and avoid replacing it with a different approach unless the user authorises the change.

Additional checks can be implemented with COUNTIFS, SUMIFS, conditional formatting, data validation, and reconciliation formulas. For example, =COUNTIFS(Transactions[Transaction ID],[@[Transaction ID]]) can help flag repeated transaction identifiers when the intended identifier should be unique. A control-total check can compare the sum of the detail table with the corresponding source total. A variance threshold can flag exceptions for review. These checks are only as good as their assumptions: an identifier may legitimately repeat across separate entities or periods, and a balance difference may reflect an approved adjustment rather than an error. The workbook should state the conditions under which a match is expected and what should happen when it fails.

For important Excel outputs, post-save validation can include reopening the file with a library such as openpyxl or pandas, inspecting worksheet structures, checking formulas, and examining the saved workbook package. A programmatic library may not calculate every Excel formula; depending on the tool, the workbook may need to be recalculated by a compatible spreadsheet engine before formula results can be inspected. The agent should not claim that Excel compatibility has been proven merely because a workbook was created without an error. It should report which structural, formula, and reconciliation checks were actually performed.

Spreadsheet security also matters. An agent should not blindly insert untrusted text into cells that may be interpreted as formulas when a user later opens an exported workbook or CSV file. Formula injection is a known risk in spreadsheet workflows. For example, a malicious user may enter a string like =CMD|'/C calc'!A0 into a web form, hoping the agent will blindly write it into a CSV or Excel file that is later opened by a human analyst, thereby triggering remote code execution on the analyst's machine. This exact example illustrates why untrusted values must be handled carefully. The application should distinguish data from formulas, neutralise dangerous spreadsheet-leading characters where appropriate, and ensure that intended text remains text. Security checks should be tested independently of the model's interpretation.

21. How AI Agents Use Code

Code allows an agent to perform repeatable operations with greater precision than manually generating every result. A coding agent can inspect a project, identify relevant functions, write or revise code, run tests, examine errors, and make corrections. For example, an agent might generate a Python script that reads a YAML configuration file, creates an Excel workbook, applies formatting, adds data validation, and verifies the saved output. The agent should understand the existing project's structure before making changes and preserve required function names and interfaces unless changes are necessary and authorised. It should avoid overwriting user assets unnecessarily and, where practical, make changes incrementally while keeping a clear record of what changed.

Code generation should include syntax checking, dependency checking, edge-case testing, and tests for expected outputs. If the program creates files, the agent should confirm that they exist at the intended paths and inspect the result. If tests fail, the agent should investigate the failure rather than simply changing the test or suppressing the error. A test that is weakened until it passes may conceal the original defect. Likewise, successful code execution does not prove that the implementation satisfies the business requirement; tests should be designed around the intended result, not just the absence of an exception.

Execution security is essential. Generated code should run with permissions appropriate to the task, preferably in an isolated environment that limits access to the host file system, network, credentials, and other applications. Resource limits can help prevent an infinite loop or runaway process from consuming excessive computation. Dependencies should be restricted to approved packages where possible, and package versions should be recorded so that the environment can be reproduced. A code-writing agent should not automatically receive permission to run arbitrary shell commands against a production environment just because it can generate a plausible command.

Static analysis, dependency scanning, and automated testing provide independent checks on generated code. Abstract Syntax Tree (AST) inspection can help identify dangerous or unexpected operations, while linting tools can detect some common errors and style problems. These tools have different purposes and limitations. Passing a linter does not prove that code is correct, and a clean unit-test result does not prove that security risks are absent. For production work, validation should consider functionality, permissions, data handling, error recovery, logging, and the impact of failure.

An agent modifying an existing project should also preserve project conventions. It should inspect configuration files, module structure, naming conventions, tests, and interfaces before implementing a change. It should not invent dependencies or replace a working architecture merely because another pattern is fashionable. When it changes a file, it should report the affected files, explain the purpose of the change, and identify tests that were run. This gives the user enough information to review the result without having to reconstruct the agent's work from scratch.

22. AI Agents and Deterministic Calculations

A deterministic calculation produces the same result when given the same valid inputs and calculation rules. Examples include summing transaction amounts, calculating elapsed days, converting currencies using a specified exchange rate, and reconciling two sets of balances. These calculations are well suited to conventional software. Language models can interpret explanations and describe patterns, but they should not be the sole mechanism for critical numerical calculations when a reliable calculation engine is available. A financial agent should use approved formulas or code to calculate totals and variances, then use AI to explain the results, identify patterns, and draft a narrative based on verified figures.

Suppose the report calculates that expenditure is 12% above budget. The deterministic calculation establishes the variance amount and percentage. The agent can then examine the underlying transactions, compare the result with prior periods, search for approved explanations, and organise potential drivers. If the evidence shows increased travel costs associated with a documented project, it can explain that relationship and reference the relevant records. If no evidence supports a particular reason, the report should leave the cause unresolved rather than infer it solely from the pattern of numbers. The agent's linguistic ability is valuable for explanation, but it should not convert a plausible story into an asserted fact.

Calculation engines such as Python libraries, spreadsheet formulas, and database queries provide more appropriate mechanisms for exact arithmetic and repeatable aggregation than unconstrained text generation. They can also make it easier to test calculations against known examples. The agent can select the relevant calculation method, supply validated inputs, and interpret the returned result. For money-related calculations, the implementation should use suitable numeric representations, explicit currency rules, and appropriate rounding policies. Binary floating-point arithmetic can introduce small representation differences, so financial software should account for the precision requirements of the task rather than assuming every number type is interchangeable.

Validation should operate independently of the calculation itself. If a report calculates total expenditure of 125,000, the system should compare that amount with an independently derived total where possible. A difference may indicate missing rows, duplicated records, a mapping error, or a difference in scope. The system should not automatically change the total to force agreement. It should investigate why the figures differ and document the resolution. A calculation that is mathematically correct for the wrong inputs is still an incorrect business result.

Deterministic calculation and AI interpretation are therefore complementary. The calculation engine provides repeatable numerical operations, while the model assists with the selection of relevant information, explanations, and next steps. The final report should distinguish verified results from interpretations and clearly identify any remaining uncertainties. This separation improves accuracy and makes review more efficient because the user can inspect the numerical evidence separately from the narrative.

23. AI Agents and Data Quality

Data quality is one of the most important factors affecting agent performance. An agent may receive data that is missing, duplicated, outdated, inconsistent, incorrectly classified, or presented in an unexpected format. If it does not detect these issues, it may produce a convincing but incorrect result. Data validation should check that required fields are present, values are within expected ranges, identifiers follow defined rules, dates are valid, and categories match approved lists. Reconciliation should compare related datasets and establish whether totals agree within an explicitly defined tolerance. For example, a finance agent might compare transaction-level expenditure with the general ledger control total. If the totals differ, it should report the difference and investigate possible causes rather than continuing as if the figures were reconciled.

The agent should not alter source transactions simply to make the totals agree. It should preserve the original data and identify the specific records or rules that might explain the difference. Missing information should remain missing until supported evidence is obtained. The agent should not invent an exchange rate, donor classification, approval reference, or transaction explanation to complete a report. If a field can be obtained from an approved authoritative system, the agent may retrieve it and record the source. If it cannot, the report should disclose the limitation and explain how it affects the result.

Structured data contracts can help validate incoming records before an AI model processes them. A schema can define expected fields, data types, permitted values, relationships, and nullability rules. For example, a currency field should contain a recognised currency code, a transaction date should be valid, and a transaction identifier should follow the approved format. Tools such as Great Expectations or Pandera can help implement data-quality checks in suitable Python-based pipelines. If the data violates the expected contract, the workflow can stop the affected process and route the issue to a data owner rather than asking the model to guess the correct value.

Data governance also includes master-data management, ownership, lineage, and change control. If the definition of a department changes or an account mapping is updated, the effect on historical reporting should be understood. A transaction may be valid but mapped to the wrong reporting category because its master-data reference is stale. Conversely, an apparent mismatch may arise from a legitimate change in scope. A useful agent can identify these situations for investigation, but the organisation still needs approved rules for handling them consistently.

Data-quality checks should be proportionate to the task. A public research summary may tolerate minor omissions if they are disclosed. A regulatory report or financial close requires stronger assurance about completeness, accuracy, classification, and provenance. The more consequential the result, the more important independent control totals, source validation, reconciliation, and human review become. Good agent performance begins with controlled data, not with a more elaborate prompt.

24. What Are Hallucinations?

A hallucination occurs when an AI system produces information that appears credible but is incorrect or unsupported. An agent might invent a document reference, misstate a regulation, attribute a quotation to the wrong source, or suggest that a financial exception has been resolved when no evidence supports that conclusion. Hallucinations are particularly dangerous when the output is detailed and confidently written. A fluent answer may sound authoritative even when its central claim cannot be verified. The system should therefore be designed to identify the limits of its evidence rather than relying on confidence of presentation as a measure of accuracy.

Hallucinations can be reduced through retrieval from approved sources, explicit evidence requirements, structured outputs, deterministic calculations, independent validation, and appropriate human review. For high-impact claims, the reviewer should be able to trace the statement to an underlying source. The system should distinguish between what the source explicitly states and what it infers. For example, a policy that says a transaction must be approved above a threshold does not prove that a particular transaction was approved. That conclusion requires a relevant approval record or a reliable system confirmation.

Retrieval-Augmented Generation can reduce the need for unsupported recall by supplying relevant source passages, but retrieval alone does not eliminate hallucination. The search process may miss the controlling document, return outdated material, or retrieve text that is semantically related but not authoritative. The model may misinterpret the passage or combine details from different periods. For this reason, important answers should be checked against the source, and the system should preserve enough information to locate the supporting passage. It should also be willing to abstain when the available evidence is insufficient.

Some systems generate verification questions, perform a separate retrieval pass, or use an independent evaluation component to examine whether the evidence supports a claim. These approaches can identify certain errors, but they are not infallible. Two language models can share the same misunderstanding, and a secondary model can repeat an unsupported statement. For consequential use, verification should combine model-based review with deterministic tests, source-level checking, or confirmation from the relevant system of record.

Hallucinations should be handled as an engineering and governance issue, not simply as an instruction-writing problem. A workflow should define which claims require sources, which calculations must be independently reproduced, and which decisions need human approval. It should record failures and use them to improve the process. If an agent repeatedly invents explanations for missing information, the appropriate response may be to change its retrieval access, required output schema, validation rules, or task scope. The aim is not merely to make the model sound more cautious; it is to ensure that unsupported outputs do not silently become operational facts.

25. Why Agents Can Make Mistakes Even When They Use Tools

Tool use improves capability, but it does not eliminate errors. An agent may choose the wrong file, use an outdated source, misunderstand a tool's response, pass an invalid parameter, or interpret a successful operation incorrectly. It may also use a tool successfully but apply the result to the wrong reporting period or entity. A database query might return a valid set of transactions for the previous month, for example, while the request requires the current month. The result is technically valid but operationally wrong. Every important action should therefore be checked against the task requirements and the context in which the result will be used.

A successful file-save operation proves that the file was saved, not that the calculations are correct. A successful email send proves that the message was sent, not that the recipient or content was appropriate. A successful database update proves that the database accepted the operation, not that the operation was authorised or that the record now represents the correct business outcome. Validation must examine the actual result, not merely the technical success of a tool call. Where a tool has irreversible consequences, the workflow should require stronger pre-action checks and, where appropriate, a confirmation step.

Error handling should distinguish between transient technical failures and errors that require a new business decision. A network timeout might justify a limited retry, whereas an unexpected currency code may require clarification from the data owner. Repeated retries should use suitable limits and backoff to avoid overwhelming the service or duplicating an operation. Before retrying a transaction that could create a side effect, the agent should check whether the original attempt might already have succeeded. Idempotency keys and status queries can help prevent duplicate actions when the receiving system supports them.

Tool hallucination is another possible failure. A model may try to call a function that does not exist, use the wrong argument name, or confuse the parameters of two similar tools. A robust orchestration layer validates the request against registered tool schemas and rejects invalid calls. It should return a clear error message that helps the agent correct the request without exposing secrets or granting additional privileges. Dynamic tool discovery can improve interoperability, but the system should still verify which tools are available and whether their capabilities are appropriate for the current task.

Failures should be logged with the necessary context to support investigation, including the task identifier, tool invoked, validated parameters, result status, and subsequent handling. Sensitive data should be protected in logs, and the records should be retained according to policy. A good error report states what failed, which steps were completed, whether any side effects may have occurred, and what remains to be done. This allows the user to resume safely without assuming that the agent has either failed completely or succeeded completely when the actual state is uncertain.

26. Human Oversight and Approval

Human oversight means that people retain appropriate control over important decisions and actions. The level of oversight should reflect the consequences of a mistake. Low-risk tasks, such as summarising public documentation or formatting a draft, may require relatively light review. Medium-risk tasks, such as classifying records, preparing financial analysis, or drafting management reports, should include explicit validation and review of material results. High-risk tasks, such as releasing payments, approving journals, changing access permissions, submitting regulatory reports, or deleting important records, require stronger authorisation and may need a human decision before execution. Oversight should be built into the workflow rather than relying on a general instruction to "be careful."

The system should define who may approve an action, which evidence the approver must see, and what conditions prevent the action from proceeding. It should distinguish between an agent preparing a recommendation and an authorised person making the decision. A reviewer must be able to reject the proposed action, request further evidence, or stop the workflow. The system should provide a useful record of the proposed action, relevant source material, calculations, assumptions, validation results, and unresolved risks. This is more valuable for meaningful oversight than presenting a confident recommendation without the evidence that supports it.

Human review can also fail through automation bias: a reviewer may trust a computer-generated recommendation more than the evidence warrants. To reduce this risk, review interfaces should make important evidence accessible and highlight uncertainties or exceptions. Reviewers should know what the agent verified, which sources it used, what checks failed, and which judgments remain unresolved. Approval should require an actual decision, not merely the routine clicking of a button at the end of an automated process. For high-impact operations, the system may require the reviewer to confirm specific conditions or select the authorised action explicitly.

Approval rules should also account for segregation of duties. An agent that prepares a journal should not automatically approve the journal it has prepared if policy requires independent review. An agent can assist both the preparer and the reviewer, but the roles and permissions should remain distinct. In regulated financial reporting, the organisation should evaluate the relevant accounting, audit, privacy, and regulatory requirements for the specific use case. The fact that an AI system is technically capable of making a decision does not transfer accountability for the decision away from the people and organisation responsible for the process.

Human oversight should be targeted rather than indiscriminate. Requiring approval for every low-risk operation can create unnecessary delays and encourage reviewers to approve requests without careful attention. A more effective system uses risk thresholds, reversibility, uncertainty, and business impact to determine when approval is needed. Routine tasks can proceed under controlled rules, while unusual, irreversible, or high-impact actions are escalated. This approach makes human judgment available where it adds the greatest value and preserves meaningful accountability without making every interaction unnecessarily burdensome.

27. The Principle of Least Privilege

Least privilege means giving a user or system only the permissions needed to perform its assigned duties. An AI agent that prepares a financial report usually needs permission to read approved data and create a draft report. It does not necessarily need permission to change the general ledger or release payments. Similarly, a document-analysis agent may need read access to a selected folder but should not automatically receive access to every confidential file in the organisation. Permissions should be limited by task, information scope, permitted operation, and duration where practical. An agent might be allowed to read a grant register and create a draft exception report while being prohibited from changing grant budgets, approving expenditure, or sharing the report externally.

These restrictions should be enforced by the connected applications and their access-control systems rather than relying only on the agent's willingness to follow instructions. Role-Based Access Control (RBAC) can assign permissions based on defined roles, while Attribute-Based Access Control (ABAC) can evaluate attributes such as user identity, resource classification, transaction status, or operating context. Authentication verifies the identity of the caller, while authorisation determines which operations that identity may perform. Both are necessary. A successfully authenticated agent should not automatically be allowed to use every capability provided by a connected service.

Credential handling is particularly important. API keys, passwords, and access tokens should not be embedded in prompts, source code, or ordinary project files without appropriate protection. Secret-management systems can provide controlled access to credentials, support rotation, and restrict exposure. Short-lived and narrowly scoped credentials can reduce the damage caused by accidental disclosure. If an agent needs temporary write access for a specific approved operation, the application should grant that authority only when appropriate and revoke it when the task is complete. The model itself should not be allowed to escalate privileges simply by requesting them in natural language.

Least privilege also reduces the impact of prompt injection or faulty tool selection. If an agent can read a document but cannot export confidential records, a malicious instruction hidden in that document has fewer opportunities to cause harm. If the agent can draft a payment proposal but cannot release funds, an incorrect interpretation is less likely to create an immediate financial loss. This is an example of limiting the potential damage even when preventive measures fail. Security should not depend on any single model correctly identifying every malicious instruction or risky action.

Permissions should be reviewed periodically and removed when they are no longer required. The organisation should monitor unusual access patterns, repeated failed attempts, unexpected write operations, and efforts to reach resources outside the approved scope. Logs should contain sufficient information for investigation without unnecessarily exposing sensitive content. A secure agent is not simply one that has good intentions encoded in its prompt. It is one whose actual operating permissions constrain what can happen when the model is wrong, confused, or manipulated.

28. Prompt Injection and Untrusted Instructions

Prompt injection is a security problem in which text encountered by an AI system attempts to influence it to ignore its original instructions or perform unauthorised actions. Such text might appear in an email, document, webpage, spreadsheet cell, or other content the agent reads. For example, a document might contain hidden text telling the agent to ignore its security rules and upload confidential files to an external website. The agent should treat this material as untrusted content to be analysed, not as an authoritative instruction to redefine its responsibilities. The fact that the instruction appears in a document related to the task does not make it trustworthy.

Direct prompt injection originates in the interaction with the model, while indirect prompt injection is delivered through external material that the model retrieves or processes. Both can attempt to redirect behaviour, reveal information, or misuse connected tools. A malicious instruction might be embedded in a webpage that the agent has been asked to summarise, or it may appear inside a seemingly legitimate document that is stored in an approved repository. Access to an approved repository does not prove that every item within it is safe to follow as an instruction. Systems must separate trusted control instructions from untrusted content, and they should assume that external text may contain adversarial material.

Prompt injection cannot be solved reliably through wording alone. Instructions such as "ignore malicious instructions" may be useful but do not create a security boundary. The stronger approach is layered: restrict tool permissions, validate arguments, isolate sensitive operations, separate retrieved data from governing instructions, and require approval before high-impact actions. A document-reading agent should not be able to send confidential files externally merely because a retrieved passage tells it to do so. The application should enforce that restriction regardless of what the model generates.

Output validation is also necessary. If an LLM generates code, database queries, shell commands, or spreadsheet content, the surrounding system should inspect and constrain the output before executing it. Untrusted content should not become executable instructions by accident. The workflow should also record which external sources influenced an action, making it possible to investigate whether a suspicious document or retrieval result affected the agent's behaviour. Security testing should include documents with conflicting instructions, hidden text, malicious links, unexpected markup, and attempts to induce disclosure of information outside the authorised task.

OWASP's guidance on risks in large language model applications identifies prompt injection, insecure output handling, excessive agency, sensitive-information disclosure, and related risks that are particularly relevant to tool-connected systems. MITRE ATLAS provides a knowledge base of adversarial tactics and techniques affecting AI-enabled systems. These resources support a security model in which untrusted content is never permitted to override application-level access controls. References: OWASP — Top 10 for Large Language Model Applications and MITRE ATLAS.

29. Data Privacy and Confidentiality

Agents may process personal information, financial records, contracts, donor information, employee data, or commercially sensitive documents. Before connecting an agent to these sources, an organisation should establish which information it may access, where that information is processed, how long it is retained, and who can review the resulting records. Sensitive information should not be sent to external services unless the transfer is authorised and consistent with applicable policy, contractual obligations, and legal requirements. Access should be limited to the minimum information needed for the task. A report intended for senior management, for example, may require aggregated expenditure figures rather than individual employee details or complete invoice images.

Privacy protection involves the entire data lifecycle. The system needs appropriate controls for ingestion, temporary storage, model requests, retrieval indexes, logs, memory, generated files, exports, and deletion. Information can be exposed through a tool response, a cached document, a debugging log, an overly broad search result, or a final report. Therefore, confidentiality controls should be applied at multiple stages rather than only when a response is sent to the user. Organisations should also examine the data-handling terms of the specific service they intend to use, including retention settings, training use, processing locations, and available administrative controls.

Personal information should be minimised whenever the full record is unnecessary. An agent reviewing invoice totals may not need the supplier's bank-account number. A report summarising staffing costs may not require employees' names. Pseudonymisation, redaction, and tokenisation can reduce exposure, although they do not automatically make data anonymous. A secure design should preserve the information necessary to complete the task without exposing unrelated details. If sensitive identifiers must be retained for reconciliation, their handling should be restricted and justified by the purpose of the process.

Data protection requirements vary by jurisdiction and context. GDPR, HIPAA, and CCPA have different scopes, definitions, duties, and exceptions. Organisations should not assume that using an AI model automatically establishes compliance or that applying a redaction tool is sufficient to satisfy every legal requirement. Appropriate legal, privacy, security, and operational reviews may be necessary before deploying a system that processes regulated information. The system should also support the applicable rights and obligations around access, correction, retention, and deletion where they apply.

Privacy must be considered when designing memory and retrieval. A persistent memory should not contain confidential information merely because it could improve future responses. Search results should respect the permissions of the user and task, preventing information from one project, client, or legal entity from leaking into another. Generated reports should inherit appropriate confidentiality classifications, and external sharing should require proper authority. Strong data governance enables agents to provide useful assistance while reducing unnecessary exposure of personal and organisational information.

30. Cybersecurity, Resilience, Evaluation, and the Future of AI Agents

An agent connected to software systems creates additional security considerations because it can potentially act on information or systems rather than merely describe them. A secure implementation should authenticate the agent, enforce access permissions, validate tool inputs, protect credentials, and monitor important actions. Secrets such as passwords, API keys, and access tokens should not be embedded in prompts or stored in ordinary project files without appropriate protection. They should be managed through suitable credential-management systems and provided only to the components that need them. Resilience is equally important. An agent may encounter missing files, invalid input, rate limits, network interruptions, or partially completed operations. A robust workflow defines how such cases are handled, with controlled retries, explicit timeouts, recovery procedures, and safeguards against duplicate side effects.

Evaluation should be part of the full development lifecycle. Before deployment, the agent should be tested on representative tasks, unusual cases, missing information, conflicting instructions, malicious inputs, and failed tool operations. The tests should assess not only whether the system completes the requested work but also whether it respects permissions, identifies uncertainty, preserves source data, and escalates decisions appropriately. For a finance agent, the evaluation may include reconciliation accuracy, completeness of the report, correctness of variance calculations, traceability of explanations, and the number and severity of unresolved exceptions. A system that performs well on ordinary examples but fails when a file is missing or a period is mismatched is not ready for unsupervised use.

Monitoring should continue after deployment. Model updates, changes to prompts, new integrations, changes to source data, and shifts in user behaviour can affect reliability. Operational records should capture task outcomes, validation failures, tool errors, approval decisions, and other relevant events. Observability tools can help trace a task across model calls, retrieval operations, and external APIs. However, logs should be designed with privacy and data-minimisation requirements in mind. They should provide enough evidence to diagnose problems without indiscriminately copying confidential data into long-lived diagnostic systems.

Governance frameworks can help organisations structure this work. NIST's AI Risk Management Framework provides a general approach to governing, mapping, measuring, and managing AI-related risks. Its Generative AI Profile discusses risks associated with generative systems and suggests actions that organisations can use to manage those risks throughout the lifecycle. OWASP's LLM application guidance helps teams identify common implementation vulnerabilities, while MITRE ATLAS provides a threat-oriented view of attacks against AI-enabled systems. These resources are complementary: risk management helps establish organisational processes, application-security guidance identifies technical weaknesses, and adversarial threat knowledge supports security testing. None of them automatically certifies an agent as safe, and each must be applied to the actual deployment context.

The future of agentic systems will likely include more capable tool use, better planning, stronger retrieval, more specialised coordination, and deeper integration with enterprise software. Model Context Protocol and other interoperability efforts may simplify how applications expose tools and data, while graph-based retrieval may improve discovery across large document collections. Research on tool use and reasoning-action loops provides useful foundations for these developments, but real-world reliability will depend on disciplined implementation. More capable agents will also require more careful attention to permissions, evaluation, data protection, operational limits, and accountability.

The central objective should not be to maximise autonomy for its own sake. It should be to build systems that can carry out the tasks they are authorised to perform, demonstrate that their results meet the relevant requirements, and remain controllable when uncertainty or failure arises. This means separating interpretation from execution, keeping high-impact decisions subject to appropriate controls, and making evidence available to reviewers. An agent should be judged by the quality and reliability of its completed work, not by how humanlike its explanations sound or how many actions it can attempt without interruption.

Authoritative resources for further study include NIST's AI Risk Management Framework, NIST's Generative AI Profile, OWASP's Top 10 for Large Language Model Applications, MITRE ATLAS, the Model Context Protocol documentation, and Microsoft Research's GraphRAG project. Foundational books include Russell and Norvig's Artificial Intelligence: A Modern Approach and Wooldridge's An Introduction to MultiAgent Systems. Research papers such as Toolformer, ReAct, Tree of Thoughts, and Reflexion provide further technical perspectives on tool use and agentic problem solving. Together, these sources illustrate the relationship between agent architecture, action selection, software engineering, evaluation, and security.

The practical conclusion is that AI agents should be designed as controlled systems capable of interpreting goals, gathering authorised evidence, coordinating tools, executing bounded operations, and validating outcomes. The model provides flexible language and pattern-recognition capabilities, but the surrounding architecture determines what the system is permitted to do and how its results are checked. The most effective implementation combines AI where interpretation is valuable with deterministic software where correctness and reproducibility are essential. When these responsibilities are separated carefully, agents can reduce repetitive work, improve access to information, and help people focus on judgment-intensive tasks without removing the oversight and accountability that responsible operation requires.

1. Introduction: Why AI Needs Water

Artificial intelligence (AI) operates through computing infrastructure rather than through a biological process. Nevertheless, that infrastructure can require considerable water. AI models run on servers equipped with central processing units, graphics processing units, memory, storage, and networking components. These systems consume electricity and generate heat during computation. Data centers must remove that heat to keep their equipment within acceptable operating temperatures. Depending on their design, they may use water-based cooling, evaporative cooling, air cooling, closed-loop liquid cooling, or combinations of these technologies. Water can also be consumed indirectly when electricity is generated and during the manufacture of computer chips.

AI agents make this subject particularly important because they can perform extended workflows rather than simply produce one response. An ordinary chatbot interaction might involve a single model response, while an agent may interpret an objective, develop a plan, retrieve documents, call external tools, evaluate the results, revise its approach, and generate a final report. Each additional model invocation can require further computation. If the agent performs many unnecessary retries or repeatedly analyses the same information, the resources required to complete its task may increase without a corresponding improvement in quality.

However, an AI agent does not literally drink water, and water consumption is not the same as a fixed physical resource attached to each question. The water footprint depends on the model, workload, hardware, cooling infrastructure, electricity supply, location, and methodology used to allocate environmental impacts to individual tasks. Some computing environments use relatively little direct water for cooling while still having an indirect water footprint associated with electricity and hardware. The central issue is therefore how efficiently AI-agent workflows use computing resources and how responsibly the infrastructure supporting them is managed. References: Google Cloud — Measuring the Environmental Impact of AI Inference and International Energy Agency — Energy and AI.

2. Understanding the Water Footprint of AI

A water footprint describes the water associated with an activity, product, or service. For AI, it can include water used directly by data-center facilities, water associated with electricity generation, and water consumed or withdrawn during the manufacture of computing hardware. These components can occur at different locations and at different stages in the hardware and software lifecycle. A user might operate an AI agent in one country while the model runs in a data center in another country and the electricity-generating facilities and semiconductor factories are located elsewhere.

The distinction between direct and indirect water use is important. Direct use occurs at the data center, including water consumed through evaporative cooling. Indirect use occurs outside the data center, such as when a power plant consumes water to generate the electricity that runs the servers. Manufacturing-related impacts arise when water is used in semiconductor fabrication and the production of other computing equipment. The total footprint therefore cannot always be determined by looking at a data center's water meter alone.

Another important distinction is between water withdrawal and water consumption. Withdrawal refers to water taken from a source, some of which may subsequently be returned. Consumption refers to the portion that is not returned to the immediate local water system in the same usable form or time frame, commonly because it evaporates or is incorporated into a process or product. The precise accounting boundary depends on the methodology used. These quantities must not be treated as interchangeable.

For AI-agent evaluation, the organisation should specify whether its assessment covers direct cooling water, indirect electricity-related water, hardware manufacturing, or the entire lifecycle. Otherwise, different assessments may appear to disagree simply because they measure different things. A transparent water-footprint estimate identifies its scope, data sources, assumptions, geographic boundaries, and uncertainty. This is especially important when comparing agents hosted by different providers or operating in different regions. Reference: Li et al. — Making AI Less 'Thirsty'.

3. How Data Centers Use Water

Data centers contain racks of servers and the associated infrastructure needed to provide reliable computing services. AI workloads can place high demands on processors, especially when large models perform training or inference. The resulting heat must be removed through an engineered cooling system. In a cooling tower, water can absorb heat from a building's cooling system and then evaporate, carrying heat away. The facility needs additional water to replace the water lost through evaporation and to maintain suitable water chemistry. Some water may also be discharged as blowdown to prevent excessive concentrations of dissolved minerals.

Not every data center uses this type of cooling. Some use air-side economisation, where suitable external air conditions reduce the need for mechanical cooling. Others use liquid cooling to transfer heat directly from components. A closed-loop system can circulate coolant repeatedly, although the facility may still use water elsewhere in its cooling chain. Designs that avoid evaporative cooling can substantially reduce direct operational water requirements, but they should be evaluated alongside electricity consumption, equipment efficiency, heat rejection, and other environmental impacts.

The relevant water demand also changes with operating conditions. Ambient temperature, humidity, server utilisation, equipment density, cooling design, and seasonal conditions may influence the amount of water required. A workload running in a hot, dry location may have a different direct water footprint from an identical workload operating in a climate where outside air can be used efficiently. The timing of a workload can therefore matter, not just its total computational demand.

These characteristics explain why it is misleading to assume that every AI query has an identical water cost. Even identical model operations can be hosted on different infrastructure and supplied by different energy systems. Sustainable AI-agent design should consider the infrastructure on which an agent runs and the efficiency of its computational workload, rather than treating the model as an isolated software component. Reference: U.S. Department of Energy — Cooling Water Efficiency Opportunities for Federal Data Centers.

4. The Three Main Components of AI Water Consumption

AI's water footprint can be organised into three main categories. The first is direct operational water, used at data-center facilities for cooling and other operational needs. The second is indirect operational water, associated with the generation of electricity consumed by the data center. The third is embodied or lifecycle water, associated with producing servers, accelerators, storage devices, networking equipment, and semiconductors. This third category may be relevant when the objective is to estimate a technology's environmental impact over its lifecycle rather than only during operation.

Direct water consumption is affected by cooling technology and local weather. Indirect water consumption depends on the electricity supply, because power-generation technologies have different water requirements. Nuclear, fossil-fuel, hydroelectric, wind, and solar technologies have different operational and lifecycle profiles; a comparison must use consistent boundaries to avoid misleading conclusions. Hardware manufacturing introduces another source of uncertainty because the production of advanced chips requires specialised water treatment and process management.

An AI agent draws on these resources indirectly through the models and tools it uses. If a task causes more electricity consumption, it may increase the workload's allocated indirect water footprint. If an agent's activity contributes to demand for additional server capacity or new hardware, a broader lifecycle analysis may also examine manufacturing impacts. However, a single agent request cannot automatically be assigned a known quantity of chip-manufacturing water without a documented allocation methodology.

These categories should be reported separately before being combined into a total. Doing so makes it possible to identify whether a proposed improvement reduces direct water use but increases electricity demand, or reduces the footprint in one location while shifting it to another. A credible sustainability assessment should avoid presenting a single total without explaining which environmental components it includes. References: Li et al. and Sustainable AI Infrastructure.

5. Why AI Agents May Use More Resources Than a Simple AI Response

An AI agent typically coordinates a series of actions towards a specified outcome. Depending on its architecture, it may invoke a language model for task interpretation, planning, document analysis, tool selection, error recovery, reflection, and final response generation. Some workflows use one model call for several of these activities, while others make multiple separate calls. Consequently, the computational cost of completing an agent task can exceed that of generating a single short response, especially when the agent operates over many documents or uses an elaborate reasoning process.

Consider the difference between asking a chatbot to explain how to reconcile a suspense account and asking an agent to carry out the investigation. The chatbot might answer in one response. The agent might search for the account register, inspect transaction details, retrieve relevant policy documents, compare source totals, classify discrepancies, draft an exception report, and check its findings. The latter task may require multiple model invocations and external operations. Its resource consumption depends on how the workflow is implemented, the amount of input processed, and whether the tools require additional computation.

Agentic behaviour does not automatically mean higher water use in every case. A well-designed agent may avoid repeated manual searches, use a smaller model for routine steps, cache reusable results, and perform exact calculations with efficient software. An agent can also finish a task with fewer total resources than a poorly designed workflow that repeatedly sends large documents to a model. The correct comparison is the resource footprint required to achieve an equivalent verified outcome, not simply the number of calls made.

For this reason, a useful efficiency measure is the amount of computation or water allocated to a completed task that meets its acceptance criteria. If two agents produce equivalent, verified reports but one uses considerably more model calls and computation, the more expensive workflow needs a clear justification. It may offer higher accuracy, broader coverage, or stronger verification, but such benefits should be measured. The aim is not to minimise every operation; it is to avoid unnecessary resource use while preserving the quality and safety of the work.

6. How the Architecture of an AI Agent Affects Its Environmental Footprint

An AI agent is a software system comprising a model, instructions, context, tools, workflow control, state management, and validation mechanisms. Each component influences the workload and, therefore, potentially influences its environmental footprint. The model determines much of the computation required for language understanding and generation. Context management determines how much input data is processed. Tool design determines how the agent retrieves information and performs operations. Workflow control determines how many steps are executed, while validation determines whether work needs to be repeated or escalated.

An inefficient architecture may submit the same large document to multiple calls, repeatedly search for information already retrieved, or use an expensive model to perform trivial tasks. A better architecture can retrieve only relevant passages, retain validated task state, use deterministic code for arithmetic, and reserve more intensive model calls for genuinely complex decisions. Where the infrastructure supports it, efficient batching or caching can also reduce redundant computation.

Validation is essential because reducing computation at the expense of correctness is not necessarily sustainable. If an agent skips an important reconciliation and produces a report that must later be corrected, the apparent saving may be offset by rework and the consequences of the error. Conversely, if an agent repeatedly rechecks information without any measurable improvement, the extra computation may provide little value. The architecture should balance efficient execution with risk-appropriate verification.

Component boundaries should be explicit. The language model can interpret a request and propose an action, while an orchestration layer checks permissions and invokes the relevant tool. A calculation engine can compute financial totals, and a separate validation mechanism can compare the results with control figures. This separation makes it easier to understand which operations consumed resources and which components were responsible for the final result. It also enables improvements to the agent's efficiency without weakening business controls.

7. The Resource Lifecycle of an AI-Agent Task

A complete agent task usually begins when a user submits an objective. The agent interprets the request, determines the necessary information, and establishes an execution plan. It may then retrieve source material, select tools, execute calculations, evaluate intermediate results, and revise its plan. Once the requirements are met, it prepares the deliverable and reports the outcome. Each stage may use different computing resources, so estimating the footprint of the complete task requires considering the full workflow rather than measuring only the final response.

For example, an agent preparing a financial report might perform several language-model calls, execute a database query, run a Python calculation, retrieve supporting documents, and create an Excel workbook. The database query and calculation may run on separate infrastructure from the language model. The spreadsheet may be generated locally or through a cloud service. Some operations may involve negligible additional model computation, while others may be substantial. A sound assessment therefore identifies the relevant components and their actual workloads instead of assuming that every step consumes the same resources.

Retries and failures deserve special attention. If a model call fails before producing a usable result, the agent might retry. If a tool call times out after executing successfully, blindly retrying could duplicate work or a business action. If a validation failure triggers another round of analysis, the additional workload may be justified when it corrects a genuine error. Task-state management and safe recovery procedures help prevent unnecessary repeated computation.

The agent should maintain a record of completed operations, pending decisions, and validation results. This enables it to resume work without needlessly repeating completed steps. The system should also distinguish successful actions from proposed actions, because a written plan does not establish that the work occurred. A complete resource assessment considers the entire path from task initiation through verified completion, including unsuccessful attempts and recovery work where measurement data is available.

8. Why There Is No Universal Water Cost Per AI Prompt

There is no reliable universal quantity of water that applies to every AI prompt or agent task. Different estimates may refer to different models, token lengths, hardware, data centers, cooling systems, energy sources, or definitions of water consumption. Some estimates include only direct cooling water, while others also allocate electricity-related water. Lifecycle estimates may include a further share associated with hardware manufacturing. A numerical comparison is meaningful only when the methods and system boundaries are sufficiently similar.

Google's August 2025 analysis reported that its median Gemini Apps text prompt used an estimated 0.26 milliliters of water, approximately five drops, under the company's stated measurement methodology. That figure is specific to the system and assumptions studied. It should not be interpreted as a universal measurement for ChatGPT, every AI model, or a multi-step autonomous agent. Long requests, different models, different operating conditions, and multi-call workflows may have different footprints.

Research published by Pengfei Li and colleagues examined the water footprint of AI training and inference and highlighted the importance of location, timing, infrastructure, and electricity supply. Their estimates were developed using a defined methodology and historical assumptions. Such research is useful for understanding the scale and variability of the issue, but it should not be treated as a live meter reading for a modern agent running on unspecified hardware.

For an AI agent, the appropriate unit of evaluation is often the complete task rather than the individual message. A task may produce one response, or it may trigger dozens of model calls and many external tool operations. A useful report identifies the measured workload, number of calls, model configuration, relevant energy data, cooling boundary, and uncertainty of any water estimate. Without those details, statements such as "every AI question uses a fixed amount of water" create a misleading impression of precision. Reference: Google Cloud — Measuring the Environmental Impact of AI Inference.

9. AI Training, Inference, and Autonomous Agent Workloads

AI training is the process of adjusting a model's parameters using data and computational methods. It can require substantial computing resources, particularly for large models. Inference is the use of a trained model to generate predictions or responses. Ordinary chatbot interactions are predominantly inference workloads. AI agents also rely on inference, often in a series of invocations as they interpret requests, plan, select tools, summarise retrieved material, and evaluate results.

Training and inference have different resource profiles. Training usually involves a large computational job that may run for an extended period. Inference costs are incurred repeatedly as the model serves users and performs agent tasks. A single agent workflow may use considerably less computation than a major training run, but the cumulative demand of many repeated workflows can become significant. The overall environmental impact therefore depends on both the infrastructure used to develop models and the scale and efficiency of their ongoing use.

Inference workload size is influenced by the model's architecture, input and output token counts, hardware efficiency, serving configuration, and processing requirements. An agent that reads thousands of pages, repeatedly summarises the same documents, or uses several expensive model calls may require more computation than a concise workflow with targeted retrieval. Similarly, an agent that produces long outputs when a short structured result would satisfy the task may use resources without improving the outcome.

Developers should measure training and inference separately where their system boundaries allow it. They should also avoid allocating the entire water footprint of training to each individual response without a transparent amortisation method. If lifecycle accounting includes training, the allocation method should explain how that cost is distributed across the useful outputs or workload volume. This makes comparisons between models and agent architectures more meaningful and prevents the double counting of environmental impacts.

10. Planning Loops, Reflection, and Repeated Model Calls

Planning, reflection, and iterative problem-solving can make AI agents more effective. A system may develop an initial plan, perform an action, inspect the result, and adjust its next step based on new information. When a task is complex or the consequence of error is high, this loop can be useful. For example, an agent reconciling two financial data sources may need to discover a mismatch, retrieve additional evidence, and revise an initial hypothesis before presenting its findings.

However, an agent can also spend excessive computation in poorly controlled loops. A workflow may repeatedly ask a model to review the same answer without defining what new evidence is required. It may continually generate alternative plans even after a suitable plan has been established. It may also restart an entire workflow because one optional item is missing. These patterns can increase inference demand while providing diminishing returns.

A well-designed workflow defines the objective, required checks, maximum retries, and stopping conditions. Reflection should be tied to specific acceptance criteria, such as whether the report reconciles, whether the required fields are present, or whether each material claim has supporting evidence. If those criteria are satisfied, further review should have a defined justification. If they cannot be satisfied because evidence is unavailable, the agent should stop and report the limitation rather than continuing indefinitely.

Efficient loops can use different approaches for different stages. A simple rules engine may validate required fields. Deterministic code may recalculate totals. A language model may examine ambiguous explanations. Only the problematic portion of a task needs to be retried, provided that the workflow preserves the integrity of the overall result. This targeted recovery approach helps control resource use without removing important safeguards.

11. The Role of Tools and External Integrations

Tools allow agents to access resources and perform operations outside the language model itself. These include file search, database queries, spreadsheet processing, code execution, web research, and enterprise APIs. A tool-connected agent can potentially achieve a useful outcome with fewer language-model calls when tools provide structured data and reliable operations. For instance, a SQL query may aggregate millions of transactions more efficiently than asking a language model to inspect every row as text. A spreadsheet library can calculate totals precisely, while an AI model helps interpret an unexpected discrepancy.

Nevertheless, tool calls can introduce additional computing work, especially if they trigger remote processing, browser automation, document conversion, or another AI service. A tool may also run on infrastructure with a separate energy and water footprint. The overall task should therefore be evaluated based on what was executed, not merely on the number of calls made to the primary model.

Efficient tool design uses focused operations, bounded queries, pagination, and caching where appropriate. It retrieves the relevant data instead of returning an entire database unnecessarily. It avoids repeating the same search when the earlier result remains valid. It also uses deterministic functions for repetitive calculations and transformations. These practices can improve execution speed, reliability, and resource efficiency at the same time.

Tool access must remain controlled. An agent should have only the permissions necessary for the requested task. The system must validate inputs, handle errors, protect credentials, and confirm the outcome of significant operations. Environmental efficiency is not a reason to omit a required audit check or use unapproved data sources. A responsible agent optimises its work within the boundaries of its purpose and authorisation, rather than sacrificing correctness for a lower computational footprint.

12. Retrieval-Augmented Generation and Document Processing

Retrieval-Augmented Generation (RAG) allows an AI application to retrieve relevant information from documents or databases and provide it to a model as context. This can help an agent answer questions using approved knowledge sources without placing an entire document collection into each model request. A retrieval system may combine metadata filtering, keyword search, semantic search, and ranking to select the passages that are most relevant to the current question.

Good retrieval can reduce unnecessary computation. If a policy question can be answered from three relevant passages, there may be little reason to process hundreds of unrelated documents. The agent can also retain verified references to previously retrieved evidence and reuse them when the same information remains applicable. These improvements can reduce redundant model processing, although the retrieval index and search infrastructure still require resources to operate.

Document processing introduces its own trade-offs. Large files may require parsing, text extraction, OCR, segmentation, indexing, and embedding generation. For a persistent enterprise knowledge base, these preparation costs may be distributed across many future tasks. For a one-off task involving a small document, a simpler approach may be more efficient. The architecture should select the retrieval strategy that fits the volume, complexity, frequency of reuse, and accuracy requirements of the task.

Retrieval must not be used as a substitute for source verification. An indexed passage may be outdated, incomplete, or incorrectly associated with a document. A model may also misinterpret a passage even when it is retrieved correctly. The agent should preserve source identifiers, dates, and relevant excerpts so that material claims can be checked against the original evidence. This approach supports reliable answers and avoids repeatedly regenerating information when a verified result already exists.

13. Memory and Context Management

An agent may maintain task state or memory to retain useful information across its operations. Working context can record which documents have been inspected, which calculations have been completed, which questions remain unresolved, and what evidence supports a conclusion. Longer-term memory may store approved preferences or recurring instructions. When implemented carefully, memory can reduce repeated searches and prevent the agent from needlessly reconstructing information that is already available.

Context management should be selective. Sending large collections of historical conversations or documents into every model call can increase processing requirements and distract the model from relevant information. A more efficient design retrieves or supplies the information needed for the current decision. It also distinguishes current source data from older summaries and checks whether previously stored information remains applicable.

Memory is not necessarily equivalent to training the model. A system may simply store structured records, document summaries, or previous tool results and retrieve them when needed. These mechanisms need data-retention policies, source references, timestamps, and access controls. A stored conclusion should not be treated as permanently true when the underlying information can change. If a stored summary conflicts with current authoritative evidence, the agent should identify and resolve the discrepancy rather than rely on an outdated result.

Memory must also be managed securely. Sensitive business data should not be retained indefinitely just because it might reduce future computation. Information should be stored only where there is a legitimate purpose, with suitable permission boundaries and retention periods. Efficiency measures must respect confidentiality and privacy obligations. A good memory architecture reduces unnecessary computation while preserving source integrity, data minimisation, and the ability to verify important results.

14. Multi-Agent Systems and Their Combined Footprint

A multi-agent system distributes work among two or more specialised agents or components. One agent might retrieve evidence, another analyse the data, and a third review the result. A coordinating agent then assembles the output. This division can be useful for complex work when the tasks are genuinely independent or require specialised processing. It may also improve fault detection if the review mechanism uses independent evidence and well-defined tests.

However, multi-agent designs can create extra computation. Each agent may use a separate model call, receive repeated context, produce lengthy intermediate messages, or request additional review from other agents. Poorly managed systems may duplicate searches or repeatedly send the same records to several models. Adding more agents does not automatically improve quality, and agreement among agents does not establish correctness if they rely on the same flawed information.

A resource-aware multi-agent architecture defines each component's role, input, output, permissions, and stopping condition. The system shares only the information needed for the delegated task. It avoids duplicating work and uses deterministic validation for results that can be checked precisely. A lightweight coordinator may be sufficient for a simple workflow, while a more elaborate system should be justified by measurable improvements in accuracy, coverage, or completion time.

The environmental comparison should consider the complete system. A multi-agent design may use more computation per run but identify errors that prevent expensive rework or materially improve the final result. Conversely, it may consume additional resources without a measurable benefit. Evaluation should therefore compare the resource use of equivalent completed tasks, including the quality and reliability of their outputs. The appropriate architecture is the simplest one that satisfies the task's performance, verification, and safety requirements.

15. Model Selection and Routing for Efficient Agents

Different AI models have different capabilities, computational requirements, latency, and costs. A large model may be appropriate for interpreting ambiguous instructions or analysing complex evidence. A smaller model or conventional program may be sufficient for classifying well-defined inputs, extracting structured fields, or generating a short status message. Choosing a suitable component for each stage can reduce unnecessary computation while preserving performance.

Model routing allows a system to choose a model based on task complexity, required accuracy, latency, or other criteria. A practical agent might use a smaller model to classify an incoming request, deterministic code to calculate variances, and a more capable model to investigate an ambiguous explanation. The exact routing policy depends on the available models and the results of testing. A smaller model should not be assigned a high-impact task merely because it consumes fewer resources if it cannot meet the required reliability threshold.

Model selection should account for more than parameter count. Hardware efficiency, inference configuration, input and output length, batching, utilisation, serving architecture, and the need for repeated calls also affect computing demand. A model that is efficient for one kind of task may be less efficient for another. Likewise, a complex model may reduce the number of retries required to complete a task successfully. These trade-offs should be evaluated empirically rather than assumed.

The objective is to minimise unnecessary resource use for a validated result. Teams should compare candidate configurations against a representative test set, including difficult cases and failures. The evaluation should measure accuracy, completeness, resource demand, latency, and the frequency of human escalation. A routing change should be accepted only when it preserves the required standard of performance and does not weaken privacy, security, or governance controls.

16. Managing Agent Workloads Through Efficient Scheduling

Scheduling determines when and where an agent performs its work. Some tasks are time-sensitive, while others can be completed in a flexible window. Where operational requirements permit, non-urgent processing can be scheduled when the relevant infrastructure is more efficient or when renewable electricity is more available. Workload scheduling may also help avoid overloading a particular system or reduce unnecessary peaks in demand.

Water-related scheduling requires more than considering electricity alone. A facility's water efficiency may vary with ambient conditions and cooling demand. A time that provides relatively low-carbon electricity may not necessarily provide the best direct water efficiency at a particular site. Water scarcity also varies by watershed and season. A truly resource-aware schedule should therefore consider the relevant constraints rather than assuming that one scheduling policy minimises every environmental impact.

Agent runtimes should use explicit timeouts, safe retries, and queue limits. They should cancel obsolete work when the user withdraws a request or when new information makes the task unnecessary, subject to the system's operational requirements. They should avoid running duplicate workflows because of repeated triggers, and they should reuse valid results where appropriate. These controls can reduce wasted computation and help keep resource demand predictable.

Scheduling must remain compatible with business deadlines and system reliability. A regulatory report cannot be delayed solely to wait for a preferred energy window when it must be completed on time. Similarly, a water-leak detection agent may need to operate continuously because delay has real consequences. The correct approach balances resource efficiency with availability, urgency, and the risks of missed work.

17. Water Efficiency Metrics: Understanding Water Usage Effectiveness

Water Usage Effectiveness (WUE) is a recognised data-center performance indicator used to assess water consumption in relation to IT equipment energy use. ISO/IEC 30134-9:2022 specifies WUE as a key performance indicator for measuring the water consumption of a data center during its operational use phase. It provides a method for reporting water intensity, allowing facilities to examine their relationship between water consumption, IT equipment, and supporting infrastructure.

WUE can be useful for comparing how much water a facility consumes relative to a unit of IT energy. However, it does not independently describe every aspect of an AI workload's water footprint. It may not capture the full water footprint of the electricity supply or the manufacturing of the equipment. Comparisons also require consistent measurement boundaries, time periods, and reporting methods. A data center with a lower direct WUE does not necessarily have a lower total lifecycle water footprint if other components differ substantially.

For agent evaluation, facility-level WUE can be combined with workload energy measurements when the provider can supply suitable data. The organisation may record the model used, the number of calls, input and output tokens, estimated or measured IT energy, and the relevant infrastructure's water metrics. These data can support an estimate of direct cooling water allocated to the task, with indirect water and hardware manufacturing reported separately when those figures are available.

WUE should be interpreted as a metric rather than as proof that a facility is environmentally sustainable. A facility could improve its water intensity while total water consumption rises because its workload expands substantially. Likewise, a high WUE value needs context about the climate, cooling technology, local water scarcity, and the kind of computing being performed. Reporting the absolute consumption and the intensity together is more informative than reporting only a single ratio. Reference: ISO/IEC 30134-9:2022 — Water Usage Effectiveness.

18. Electricity Generation and Indirect Water Consumption

AI agents consume electricity indirectly through the servers and other systems that execute their workflows. Electricity generation can itself involve water consumption. Thermal power plants may use water for cooling, while other energy technologies have different operational and lifecycle water requirements. The water footprint associated with electricity therefore depends on the mix of generation technologies, the characteristics of the plants, and the location where the power is produced.

Improving data-center energy efficiency can reduce electricity demand and potentially reduce the associated water footprint. However, the size of that benefit depends on the power system supplying the workload. The same reduction in electricity demand can have different water implications in different regions. Water-related accounting should use suitable grid or generation data rather than assume that every kilowatt-hour has a fixed water cost.

Renewable energy procurement can support decarbonisation, but it should not be automatically equated with zero water impact. Technologies have different direct and lifecycle water requirements, and the system boundary matters. A credible assessment considers the electricity actually consumed, the accounting method used to attribute generation to that consumption, and the relevant water factors. Such accounting is particularly important for cloud-hosted agents whose computing workloads may move across facilities or regions.

Organisations cannot always observe the exact water impact of each model call because providers may not expose sufficiently detailed data. In that case, an estimate should use documented assumptions and clearly indicate uncertainty. It is preferable to report a transparent range or an incomplete but well-defined measure than to provide a precise-looking figure that is unsupported by the available evidence. Reference: International Energy Agency — Energy and AI.

19. Semiconductor Manufacturing and the Hidden Water Footprint

AI depends on semiconductor devices, including processors, memory, and accelerators. Manufacturing these components requires water for activities such as wafer rinsing, cleaning, cooling, and other specialised production steps. Semiconductor fabrication uses highly purified water because impurities can affect the quality and reliability of electronic components. Water treatment and wastewater management are therefore important parts of semiconductor manufacturing infrastructure.

The manufacturing footprint is different from the direct cooling footprint of a data center. It occurs in the hardware supply chain, often before the equipment is installed. As a result, a data-center operator's operational water report may not represent the full lifecycle water associated with the hardware. Allocating manufacturing water to an agent task requires information about the hardware, expected service life, utilisation, production impacts, and a defensible allocation method.

It is important not to assign the full water footprint of a processor to every request it serves. The hardware is shared across many tasks and operates over a service lifetime. Lifecycle accounting should explain how manufacturing impacts are allocated across productive use, while recognising that detailed production data may not be publicly available. Comparisons should also avoid double counting hardware impacts already included in another part of the assessment.

Hardware efficiency, longer useful service life, responsible recycling, and effective utilisation may contribute to lower environmental impacts, although each choice should be assessed in context. Replacing equipment more frequently in pursuit of small performance gains may introduce additional manufacturing impacts. Conversely, more efficient new hardware may reduce operational demand substantially. A balanced assessment considers both operational efficiency and the resources embedded in the equipment. Reference: SEMI — Guide for Ultrapure Water Used in Semiconductor Processing.

20. Water Scarcity, Geographic Location, and Community Impact

The environmental significance of water use depends partly on where and when the water is consumed. A litre of water used in a water-abundant region does not necessarily create the same local pressure as a litre consumed in a drought-affected watershed. Data centers are physical facilities that depend on local infrastructure, including water supplies, electricity systems, land, and cooling conditions. As facilities expand, their effects may be concentrated in the surrounding community even when their digital services are used globally.

Location decisions should consider watershed conditions, seasonal scarcity, existing community needs, water rights, infrastructure capacity, and the likely operational life of the facility. Using reclaimed or recycled water may reduce competition with potable-water uses, but the actual effect depends on local water quality, treatment, return flows, and other users. A project should not be described as water-neutral solely because it purchases or supports a replenishment activity without explaining the relationship between that activity and its local water impacts.

AI-agent providers may operate multiple data centers and choose where to deploy workloads. Where available and appropriate, resource-aware routing could consider facility efficiency and local water conditions alongside performance, resilience, cost, and data-residency requirements. Such routing must not compromise privacy, contractual obligations, or legal requirements about where data may be processed.

Community impacts should remain visible in environmental reporting. A global average can hide a concentrated local burden, just as a very efficient facility can still consume substantial absolute quantities of water when demand is large. Organisations should therefore consider both aggregate use and geographic context. Responsible implementation includes transparent reporting, stakeholder engagement, and a willingness to adjust operational plans where local water risks are material.

21. Measuring the Water Footprint of an AI-Agent Workflow

Measuring an agent's water footprint is difficult when the provider does not disclose workload-level energy and water data. Nevertheless, an organisation can establish a measurement framework. It should record the complete task, the model invocations, token usage where available, tool operations, retries, and final task outcome. The measurement boundary should specify which components are included and whether the calculation concerns direct operational water, indirect electricity-related water, or a broader lifecycle estimate.

A conceptual accounting model is to estimate three components separately: direct facility water allocated to the workload, indirect water attributable to the electricity it consumes, and an optional allocation of embodied water associated with the relevant hardware. The totals should be combined only when the components use compatible definitions and do not overlap. If a cloud provider supplies a task-level environmental measurement, the organisation should still examine the stated methodology before comparing it with other services.

Where detailed metering is unavailable, the system can record proxies such as energy use, token counts, and workload duration. These proxies are useful for comparing versions of the same workflow under consistent conditions, but they should not automatically be converted into litres using an arbitrary universal coefficient. If an energy-to-water conversion factor is used, the report should identify its source, geographic relevance, period, and uncertainty. Direct facility WUE and electricity-grid water intensity should remain separate where necessary.

Measurements should be repeatable. The same benchmark tasks can be run against alternative agent architectures, provided that the quality and acceptance criteria remain equivalent. The organisation can then compare compute use, number of retries, latency, error rate, and, where data permits, estimated water footprint. A successful measurement program records assumptions and makes it possible for another reviewer to understand how the result was produced. This is more useful for operational improvement than publishing an unsupported estimate of litres per conversation.

22. Calculating an Illustrative AI-Agent Water Estimate

An illustrative estimate can show how an AI-agent task's water footprint depends on the underlying assumptions. Suppose an agent uses a language model, retrieves information from a cloud database, and creates an output document. The model's energy demand may be available from a provider or estimated from measured workload data. The data center's operational water intensity may be supplied through an appropriate WUE metric. Electricity-related water can be estimated separately using data relevant to the electricity source. Hardware manufacturing can be excluded from a narrowly operational estimate, or included in a lifecycle assessment if suitable information is available.

For the direct component, an analyst can combine the workload's allocated IT energy with a compatible facility water-intensity metric. For the indirect component, the analyst can combine the relevant electricity use with a suitable water-intensity factor for the power supply. If manufacturing impacts are included, an additional method is needed to allocate hardware lifecycle water to the workload. This calculation must avoid counting the same water twice, such as including a direct water measure and then adding a second estimate that already contains that same facility component.

Any resulting figure is an estimate, not necessarily an exact measurement of the water used by that particular task. It depends on the completeness of the source data, the chosen allocation method, the model and infrastructure involved, and the boundaries of the assessment. The report should state which components were included and which were omitted. It should also avoid comparing an operational estimate with another result that includes manufacturing impacts as though both covered the same footprint.

For most agent developers, the immediate priority is likely to be consistent workload-level measurement rather than claiming an exact water cost for every invocation. Tracking model calls, energy consumption, retries, and verified outcomes can reveal inefficient behaviours. More detailed water accounting can be introduced as provider data and measurement methods become available. Clear assumptions and honest uncertainty are essential to the credibility of any reported result.

23. Using AI Agents to Monitor Their Own Resource Use

AI agents can be designed to monitor aspects of their own operating behaviour. A workflow controller can record model calls, token usage, retries, duration, tool invocation counts, and the completion status of each task. These records can be analysed to determine which workflows repeatedly consume resources without delivering a corresponding improvement in quality. Where the system has suitable provider data, energy and water indicators can be added to the operational dashboard.

For example, a document-analysis agent might detect that it repeatedly processes the same large reference file in multiple stages. The developer can redesign the workflow to retrieve relevant sections once and reuse verified passages. A report-generation agent might repeatedly ask a model to review a calculation that can instead be checked using deterministic code. A task controller may identify unusually long chains of tool calls and flag them for investigation. These changes can improve efficiency without reducing the quality of the final deliverable.

Monitoring should distinguish genuine complexity from waste. A task that involves a high-risk investigation may appropriately require additional validation, while a simple formatting operation may not. The system should not use an arbitrary model-call limit that prevents required safety checks. Instead, it should define justified thresholds, track the reasons for retries, and escalate cases that cannot be completed safely within the expected resource budget.

The monitoring system should itself be designed efficiently and securely. Logging all input documents and model outputs may create additional storage and processing demands while exposing confidential information. Metrics should be collected in a way that supports analysis without unnecessary data retention. Resource monitoring is most useful when it leads to clear architectural improvements and makes the system's performance more transparent.

24. AI Agents Can Also Help Save Water

AI's water footprint is not exclusively a cost. Properly designed AI agents can help organisations find and address water inefficiencies elsewhere. A facility-management agent could analyse sensor readings, identify unusual water-flow patterns, detect probable leaks, and generate maintenance requests. An agricultural agent could combine soil-moisture readings, weather forecasts, crop information, and irrigation schedules to recommend when watering is needed. An industrial agent could monitor process data and identify opportunities to reduce wastage or improve water reuse.

A data-center operations agent could help compare cooling-system readings, identify unusual water demand, examine operating conditions, and recommend investigation of a potential problem. It may also support predictive maintenance by detecting conditions that precede equipment failures. However, automated changes to a cooling plant must respect engineering limits, operating procedures, and safety requirements. The agent should not independently reduce cooling in a way that risks overheating servers or damaging equipment.

These applications require trustworthy sensor data, suitable models, validated decision rules, and clear escalation procedures. An unusual flow reading may indicate a leak, a calibration problem, a maintenance event, or a change in operating conditions. The agent should distinguish confirmed findings from hypotheses and request inspection where appropriate. Any claimed saving should be measured against a defensible baseline and adjusted for changes in production, weather, and operational demand.

An AI agent can therefore contribute to water conservation, but benefits must be demonstrated rather than assumed. Its own environmental footprint and the resources required to deploy and maintain the solution should be considered alongside the water savings it helps achieve. Net environmental benefit depends on the actual operating conditions and the reliability of the intervention. Reference: International Energy Agency — AI for Energy Optimisation and Innovation.

25. Balancing AI's Environmental Costs and Benefits

Evaluating AI agents solely by the resources they consume can overlook the activities they help improve. An agent may use computing resources to reduce water losses, improve industrial efficiency, or identify leaks that would otherwise remain undetected. However, such benefits should be demonstrated with measured evidence. A plausible use case is not proof that the deployment saves more water than it requires over its lifecycle.

A useful assessment establishes a baseline, defines the intended outcome, measures the agent's own workload, and measures the change in the target process. If an agent is expected to reduce irrigation use, the organisation should measure water use and agricultural outcomes before and after implementation under comparable conditions. It should also examine whether the results persist, whether other resources are consumed, and whether the system causes unintended changes in behaviour.

Efficiency improvements can also produce rebound effects. If AI makes it cheaper to run large numbers of computational tasks, total usage may rise enough to offset some of the savings per task. Similarly, improved irrigation efficiency may lead to expanded cultivation rather than a reduction in total water withdrawal. Such effects do not mean that efficiency improvements are useless, but they show why absolute resource use and workload growth should both be monitored.

A balanced assessment considers the benefits, costs, alternatives, uncertainty, and distribution of impacts. It asks whether AI is the appropriate tool for the problem, whether a simpler method could achieve the same result, and whether the deployment remains justified at scale. Environmental responsibility requires evidence that the intervention provides meaningful value rather than assuming that all AI-enabled activities are beneficial because they are digital.

26. Responsible Implementation, Security, and Human Oversight

An agent deployed for environmental monitoring can affect operational systems, financial resources, or public infrastructure. A cooling-system agent may influence equipment settings, while an irrigation agent may alter water delivery. A model that misinterprets sensor values or responds to malicious input could recommend an unsuitable action. Consequently, water-saving objectives must be pursued within explicit safety, authorisation, and governance boundaries.

The agent should distinguish between observing, recommending, and executing an action. Read-only monitoring can usually be introduced before automated control. Recommendations can be reviewed by qualified personnel, and permitted low-risk operations can be automated after suitable testing. High-impact changes should require the appropriate approval and independent checks. The control system should enforce operating limits regardless of the model's instructions, and the agent should stop or escalate when measurements are missing, contradictory, or outside validated conditions.

Security controls are important because connected agents may encounter untrusted documents, web pages, tool responses, or sensor inputs. Prompt injection and other forms of manipulation can attempt to redirect the system or misuse its permissions. Tools should follow least privilege, credentials should be protected, and external content should not override application-level controls. Monitoring should record important actions and their outcomes while protecting sensitive information.

Environmental performance must not be improved by weakening reliability or exposing confidential data. A resource-aware system should be tested against normal conditions, edge cases, missing data, erroneous readings, and malicious inputs. The developer should define acceptable performance thresholds, stopping conditions, recovery procedures, and human escalation rules. This enables the agent to use resources efficiently while retaining control, safety, and accountability. References: NIST — AI Risk Management Framework and OWASP — Top Risks for Large Language Model Applications.

27. Environmental Transparency and Vendor Accountability

Many users cannot directly observe the data centers that process their agent tasks. They may not know which model version was used, where the workload ran, which cooling system was involved, or how much electricity the workflow consumed. Providers may publish overall sustainability information without providing detailed water data for each model, product, or task. This limits the precision of comparisons between AI services and makes transparent methodology particularly important.

Organisations procuring AI-agent services should ask providers about their environmental reporting boundaries, direct water consumption, electricity-related impacts, water-use measurement methods, and the availability of workload-level metrics. They should determine whether published figures refer to a specific product or the provider's broader operations, which reporting year is covered, and whether water use is measured or estimated. Comparisons should distinguish between absolute water consumption and intensity metrics.

Water replenishment commitments can be part of responsible water stewardship, but they should be evaluated separately from reductions in operational consumption. Replenishment projects may differ in location, timing, water benefits, and relevance to the watershed where consumption occurs. A claim of being water-positive should therefore be understood within the provider's stated methodology rather than treated as proof that a particular AI task has no environmental impact.

Contractual requirements can support better reporting. Providers may be asked to disclose appropriate environmental metrics, explain changes over time, and document the methodology used. Procurement teams should also evaluate reliability, privacy, security, service availability, and the provider's ability to meet the organisation's actual needs. Environmental performance is one element of a broader evaluation, but it can be an important factor in the selection and ongoing review of AI services.

28. Water Footprint, Ethics, and Sustainable AI Governance

Water is a shared resource, and its availability affects households, agriculture, industry, ecosystems, and public services. The environmental consequences of data-center expansion may therefore extend beyond the organisation operating the facility. Even when a company pays for its water supply, local resource constraints and competing community needs remain relevant. Responsible AI governance should consider the location and timing of water consumption instead of relying exclusively on global totals or corporate efficiency ratios.

Transparency helps communities, customers, investors, regulators, and researchers evaluate environmental performance. Reporting should distinguish actual measurements from estimates and explain the assumptions behind each figure. It should also recognise uncertainty and avoid presenting incomplete lifecycle calculations as comprehensive totals. Water-related information should be sufficiently clear to support informed decisions without disclosing security-sensitive infrastructure details or personal information.

Organisations should evaluate whether an AI deployment is justified by its expected value and whether a lower-resource alternative can achieve the same objective. Some tasks may be handled with deterministic software, conventional analytics, or a simpler model. Others may need sophisticated agentic workflows because they involve ambiguity, multiple sources, or important verification steps. The decision should reflect the requirements of the task rather than a presumption that greater autonomy is always better.

Governance should assign responsibility for measuring the footprint, maintaining the system, evaluating changes, and responding to material risks. A sustainability claim should be supported by evidence and reviewed when the model, hosting environment, workload, or data-center infrastructure changes. Sustainable AI is a continuing operational responsibility rather than a one-time decision made during procurement or development.

29. Practical Checklist for Developing a Water-Aware AI Agent

A water-aware agent project should begin by defining the task and the measurable outcome it is expected to achieve. The team should determine whether an AI agent is necessary or whether a simpler script, query, or conventional automation process would be sufficient. It should then select a model and tools that meet the task's performance and reliability requirements without unnecessary computation.

The architecture should minimise repeated processing, retrieve relevant context, reuse valid results where appropriate, and use deterministic tools for exact calculations. Planning and reflection loops should have explicit stopping conditions. The system should avoid duplicate work, apply safe retry mechanisms, and record why a task required additional computation. These controls improve both operational efficiency and the ability to explain unusual resource consumption.

The organisation should measure model invocations, token usage, tool activity, retries, execution time, and, where data is available, energy consumption. If water-use metrics are available, it should document the system boundary, reporting period, geographic relevance, allocation method, and uncertainty. It should distinguish operational water from electricity-related and manufacturing impacts, and it should avoid combining figures that overlap.

Before deployment, the agent should be tested for task accuracy, completeness, error recovery, permission enforcement, and performance under unusual conditions. Human approval should be required where actions could affect physical infrastructure, regulated operations, or other high-impact processes. The system should also include monitoring, logging, version control, incident response, and periodic review of its resource footprint.

Finally, the organisation should evaluate environmental performance alongside the actual benefit delivered. It should compare equivalent outcomes, investigate increases in resource use, and revise workflows that repeatedly consume computation without adding measurable value. The result should be an agent that performs its authorised task reliably while using resources proportionately and transparently.

30. Conclusion: Building Sustainable and Responsible AI Agents

AI does have a water footprint, primarily through the infrastructure that runs models and stores or processes information. That footprint can include direct water consumption in data-center cooling, indirect water use associated with electricity generation, and water involved in manufacturing semiconductor hardware. The size of the impact varies according to the workload, model, hardware, cooling system, energy supply, location, and accounting method. There is consequently no single water-consumption figure that accurately describes every AI model or every agent task.

AI agents introduce an important additional consideration because they coordinate multiple activities. Planning, tool use, retrieval, reflection, validation, and retries may each require additional computation. A poorly designed agent can waste resources through duplicated retrieval, excessive model calls, unnecessary context, or unbounded loops. A well-designed agent can reduce that waste by selecting appropriate models, using deterministic tools for repetitive operations, maintaining verified task state, and retrying only the parts of a workflow that actually require correction.

Reducing computation is not the only objective. Verification, security, privacy, and safe operation remain essential. An agent that produces a lower-resource but incorrect result may create rework or operational harm. Similarly, a system that claims to save water should demonstrate the benefit through suitable measurements rather than rely on assumptions. Sustainable implementation means achieving a verified and useful result with an appropriately proportionate amount of computing and other resources.

Organisations should therefore evaluate the full lifecycle and operating context of AI agents, including the data centers, electricity supply, hardware, workflow architecture, and local water conditions. They should use reliable metrics where available, state the limits of their estimates, and seek better transparency from providers. AI agents can also help detect leaks, improve irrigation, optimise cooling, and support better resource management, but those benefits should be assessed against the resources needed to deliver them.

The practical conclusion is that AI agents do not need to avoid computation altogether; they need to use it responsibly. Efficient architecture, controlled tool access, meaningful validation, transparent environmental reporting, and risk-appropriate human oversight provide a foundation for agent systems that are useful, auditable, and more resource-conscious. The objective is to minimise unnecessary environmental impact while preserving the accuracy, reliability, security, and social value of the work the agent is designed to perform.
