Expert Analysis
Ten-Pass Verdict — After repeated expert passes against render.py, the YAML corpus, the Meridian visual-system slides, and the sub-award knowledge base, the correct conclusion is that the renderer is not fundamentally limited. It is already a layered slide engine with a low-level canvas, a semantic strategy registry, a composite component layer, theme and layout tokens, and per-slide error isolation. The expansion opportunity is to add missing geometry, layout, data-binding, measurement, and component infrastructure beneath the existing strategies, not to replace the renderer and not to create a new strategy for every business diagram. The architecture is sound enough to carry a very large visualization surface; what it lacks is a formal semantic component layer between YAML and canvas.
Architecture Verdict — The system can expand substantially without being replaced. Its principal constraints are higher-level rather than fundamental: richer connectors, generic paths, automatic layouts, structured data binding, analytical scales, repeatable component contracts, deterministic measurement, and semantic validation. Once those are added, most requested visualization families can be served by a small reusable library plus thin domain templates. The decisive insight is that the hard problems are layout and semantics, not drawing; python-pptx already gives us enough drawing power, so the investment should go into the layer that decides where things go and what they mean.
Verified Layer Map — render.py separates four concerns: SlideCanvas for primitive drawing, SlideComponents for reusable visual assemblies, SlideRenderStrategy subclasses for slide-type semantics, and SlideRenderer for dispatch, error capture, and fail-fast behavior. New capabilities should be inserted at the correct layer instead of forcing every feature into the top-level dispatcher. This layering is the single most important fact about the codebase: it means we can add a graph engine, a chart engine, or a layout engine without touching the dispatcher, and we can add domain templates without touching any engine. Discipline about which layer owns which responsibility is what keeps the system from decaying into a pile of special cases.
Dispatch Pipeline Should Remain Explicit — The effective pipeline is SlideSpec → strategy resolution → canvas construction → component construction → strategy chrome → body rendering → notes writing → error capture. Component expansion, layout calculation, and data binding should occur before or inside body rendering, not by mutating the presentation object outside the canvas abstraction. Keeping this sequence explicit matters because it gives us a single place to insert validation, a single place to insert measurement, and a single place to catch errors. If components start writing shapes directly to the slide outside the canvas, we lose error isolation, we lose theming, and we lose the ability to reason about what a slide contains.
Strategy Registry Is Already Semantic — The registry already includes title, title-only, section, content, summary, quote, comparison, end, diagram/accounting-cycle, custom, checklist, table, matrix, decision-tree, process-flow, timeline, infographic, and product-vision paths. This proves semantic abstraction is already accepted by the codebase and is not a foreign concept being imposed. The next step is enriching the component layer, not proliferating strategies for every domain visualization. A useful test: if two strategies would differ only in which components they call and how they arrange them, they are the same strategy with different data, and should be one strategy.
Canvas Primitive Inventory — The canvas already supports background fill, generic shapes, textboxes, bullet lists, cards, rule lines, and arrow connectors. This is sufficient for cards, KPI tiles, matrices, tables, dashboards, simple charts, process steps, hierarchy boxes, and annotation panels. The missing primitives are expressive geometry and layout-aware composition: path/polyline, group/container, richer connectors, and measurement-aware layout helpers. It is worth emphasizing that the existing primitives are already enough to render roughly eighty percent of the supplied YAML corpus; the gap is not that we cannot draw the shapes, but that we are hand-placing them instead of letting a component place them.
Composite Component Inventory — The components layer already draws headers, footers, content headers, section headers, main content cards, fallback cards, sidebars, comparison columns, title-right panels, title-only blocks, quote blocks, timelines, and process flows. This is the correct home for new reusable composites such as graphs, waterfalls, heatmaps, small multiples, funnels, swimlanes, scorecards, control boards, staircases, and dashboard grids. Every one of these new composites should follow the exact same contract as the existing ones: receive normalized semantic data plus theme and layout tokens, compute geometry internally, and emit canvas calls. That uniformity is what makes the library learnable and testable.
Existing Strategies Provide Reusable Patterns — Timeline shows semantic data can become deterministic layout. Process flow establishes sequence semantics. Checklist demonstrates adaptive sizing and column splitting. Table provides a starting point for structured grids. Comparison supports decision-oriented slides. Summary demonstrates adaptive card layout. Custom strategy is the escape hatch and laboratory. These patterns should be generalized rather than duplicated. In particular, the checklist strategy's adaptive font-sizing and column-splitting logic is the closest thing in the current codebase to a real layout engine, and it should be studied and extracted as the seed of a general measurement-and-fit service.
Custom Shape Normalization Is a Design Precedent — _normalize_custom_shape_kind() accepts flexible authoring aliases and normalizes them into stable internal kinds: rectangle, circle, arrow, and text. This precedent should be preserved and extended. Future aliases should remain expressive in YAML but normalize into a small internal vocabulary such as rect, text, path, group, connector, table, chart, graph, annotation, and repeat. The design principle is that the authoring vocabulary can be generous and domain-flavored, but the internal vocabulary must be small, stable, and closed, because every internal kind is a contract that the layout engine, the validator, and the tests must all understand.
Coordinate Model Is Multi-Mode and Practical — The custom renderer supports inches, centi-inches, EMU, points, and percent-like interpretation. This matches the YAML corpus, including the 1333 × 750 centi-inch canvas used throughout the Meridian deck. Expansion should preserve coordinate flexibility while adding semantic layout modes that compute coordinates automatically from data, gaps, padding, and available space. A subtle but important point: because the corpus uses centi-inches, all internal math should convert to EMU once at the boundary and then work in integer EMU thereafter, to avoid accumulating floating-point drift across nested calculations.
Vertical Fit Scaling Shows Layout Responsibility — The custom renderer computes minimum and maximum Y extent and scales Y positions and heights when authored drawing exceeds available vertical space. This is useful but remains fit-after-authoring. The next evolution is layout-before-drawing: deterministic engines that prevent overflow and produce stable coordinates from component contracts. Fit-after-authoring is a safety net; layout-before-drawing is a guarantee. We should keep the safety net for hand-authored custom shapes, but every reusable component should be responsible for fitting itself before it emits geometry, so that scaling is the exception rather than the rule.
Theme and Layout Tokens Are the Correct Style Boundary — ThemeTokens and LayoutTokens centralize colors, fonts, spacing, and slide geometry. New components must inherit these tokens instead of introducing private palettes. Semantic statuses such as good, warning, critical, upward, downward, verified, and at-risk should resolve through theme tokens rather than hardcoded color choices. The Meridian brand system in the YAML corpus already demonstrates this discipline: navy carries authority, gold is reserved for the verified reference line, gray carries context, and white is breathing room. The renderer should treat that palette as a contract, and any component that introduces a new color should be treated as a design-system change, not a renderer change.
Text System Is Strong but Needs Measurement — Text handling already includes normalization, placeholder filtering, font-size estimation, text-to-fit behavior, alignment, wrapping, and vertical anchoring. The missing capability is reliable intrinsic measurement: predicting wrapped height, remaining space, card fit, and annotation placement before neighboring elements are positioned. This is the single most consequential gap for layout quality. Without measurement, components must guess at heights, which is why so many hand-authored boxes in the corpus have generous padding. A real text-measurement service, even an approximate one, would let components tighten layouts dramatically and would make adaptive components like checklist and summary far more reliable.
Bullet System Supports Semantic Content — Bullet rendering already accepts strings and BulletItem structures with title and description behavior. This is useful for summaries, controls, policies, findings, recommendations, and executive takeaways. The next improvement is allowing bullets to carry status, owner, evidence, severity, and date metadata without losing the simple rendering contract. In the sub-award domain especially, bullets are rarely just text; they are claims that carry an owner, a control reference, and an evidence link. Letting a bullet carry that metadata means the renderer can later produce evidence callouts or audit annotations from the same data, without a second authoring pass.
Sidebar and Footer Flags Are Explicit Visibility Controls — The renderer supports explicit suppression of executive lens, action focus, and custom footer bands through meta/render flags. This is a good model for future expansion: visibility should be declarative and explicit. New components should likewise support show/hide controls for legends, axes, annotations, totals, headers, source notes, and evidence links. The deeper principle is that every optional visual element should be governed by a named flag with a sensible default, so that a slide's visual complexity can be tuned without editing geometry, and so that a deck can be globally re-styled (for example, hiding all source notes for a board version) by flipping flags rather than touching shapes.
Error Isolation Enables Safe Expansion — SlideRenderer records render failures in structured render_errors, draws an error box, and only raises when fail_fast is enabled. New components should fail locally and predictably. Component validation should produce structured errors containing component ID, kind, field, expected contract, and corrective hint. This matters enormously for a generation pipeline where an LLM or template engine is producing YAML: a single malformed component should degrade one slide, not abort the deck, and the error record should be machine-readable so the generator can self-correct on the next pass. Error isolation is therefore not just robustness; it is what makes automated generation viable.
Main Architectural Gap — The current YAML is mostly a display list: author specifies shapes and coordinates. The target architecture should be a component scene graph: author specifies semantic components, data, layout hints, relationships, and status; the renderer validates, expands, lays out, and draws them as primitives. This converts manual authoring into reproducible analytical rendering. The distinction is the difference between a page description and a document model. A display list tells you what marks to make; a scene graph tells you what things exist and how they relate, and lets the renderer decide the marks. Every capability in this analysis is, at root, a step toward turning the renderer into a scene-graph engine.
Expansion Doctrine — Expand through three layers: Level 1 primitives, Level 2 reusable composites, and Level 3 domain templates. Level 1 adds drawing and layout power. Level 2 converts repeated visual structures into components. Level 3 wraps components with finance, audit, risk, HR, operations, policy, sub-award, and executive semantics. This prevents both primitive starvation and strategy explosion. A useful governance rule: Level 1 changes require review of the canvas contract, Level 2 changes require golden-slide tests, and Level 3 changes require only YAML and no Python. If a Level 3 template ever needs Python, that is a signal that a Level 2 component is missing.
Determinism and Reproducibility — A world-class renderer must be deterministic: the same YAML, the same theme, and the same fonts must produce the same PPTX every time, byte-for-byte or at least visually identical. This requires controlling all sources of nondeterminism: dictionary iteration order, floating-point rounding in EMU conversion, font metric lookups that might differ across platforms, and any timestamp or random value embedded in the file. Determinism is what makes golden-slide regression testing possible, what makes caching safe, and what lets a team review a generated deck knowing it will not silently change on re-render. Any new layout engine must be written to be pure and order-stable.
EMU Precision and Rounding Discipline — OOXML geometry is expressed in English Metric Units, with 914400 EMU per inch. Because the corpus works in centi-inches on a 1333 × 750 canvas, every coordinate passes through a multiply-and-round step. A world-class implementation rounds consistently (for example, half-away-from-zero), performs all layout accumulation in integer EMU, and only converts to points for font sizes. It also snaps hairline rules and connector endpoints to whole EMU to avoid sub-pixel gaps. Rounding is not a cosmetic detail: accumulated rounding error is what causes boxes to drift by one pixel, connectors to miss their targets, and adjacent cards to show a hairline seam.
Z-Order and Paint Semantics — python-pptx appends shapes in creation order, and that order is the paint order. A component system must therefore be deliberate about the order in which it emits shapes: backgrounds before borders before fills before text before connectors before annotations. Connectors deserve special attention because they often need to paint above fills but below labels, and graph edges may need to paint below nodes. The renderer should expose a small set of named layers (background, chrome, body, connectors, annotations, overlay) and emit into them in a fixed sequence, so that z-order is a property of the architecture rather than an accident of call order.
Text Metrics and Cross-Platform Fidelity — Text is the hardest rendering problem in the whole system because python-pptx does not measure text; it only writes it. True measurement requires a font rasterizer or a metrics table. A pragmatic world-class approach is to build a calibrated estimator: characters-per-line as a function of font family, size, and box width, plus a line-height model, validated against a corpus of known slides. This estimator will never be pixel-perfect, but it can be good enough to prevent overflow and to drive adaptive sizing. The estimator must be versioned, because when it improves, layouts shift, and golden slides must be re-baselined deliberately rather than silently.
Font Fallback and Internationalization — The Meridian deck uses specific display, text, and mono registers. A robust renderer records the requested font but also a fallback chain, and it must handle the case where a font is unavailable on the rendering or viewing machine without corrupting the layout. Internationalization matters even for an English-first deck: right-aligned tabular numerals, en-dashes, curly quotes, and the occasional non-Latin string all appear in the corpus. The layout engine must measure using the actual glyphs, not an ASCII assumption, and must not hardcode left-to-right assumptions in a way that would break if a future deck adds Arabic or Hebrew. At minimum, keep text direction a per-textbox property.
Color Semantics, Contrast, and Accessibility — The palette is small and disciplined, but the renderer should still enforce contrast and should reason about color semantically rather than chromatically. That means components request status.warning or emphasis.primary, and the theme resolves that to a concrete RGB. It also means the theme can carry contrast metadata, so that when gold is placed on white versus on navy, the renderer can choose the legible text color. Accessibility is not a bolt-on: board packs and donor reports are read by people with low vision and on projectors, so the default treatments should already meet reasonable contrast ratios, and the semantic-token approach is what makes that enforceable across hundreds of components.
Overflow, Clipping, and Graceful Degradation — Every component must define what happens when its content exceeds its box. The options are: shrink text (text-to-fit), truncate with an ellipsis, wrap and grow, or overflow into a continuation. A world-class renderer makes this choice explicit per component and per field, rather than leaving it to PowerPoint's defaults. For analytical components, truncation is dangerous because a truncated number is worse than a small number; for narrative components, shrinking is usually acceptable. The renderer should log a warning whenever it degrades content, so that a generator can learn that a particular field is consistently too long and adjust the data or the layout.
Performance Budget and Rendering Latency — Deck generation should have a budget: a target number of milliseconds per slide and a target total for a full deck. Because generation is often interactive (an analyst iterating, or an LLM pipeline producing many decks), latency matters. The budget should be measured and reported in render_errors or a parallel timing record. Expensive operations to watch are repeated font measurement, large table construction, and any per-shape OOXML manipulation that touches the XML tree directly. When a component exceeds budget, the fix is almost always to hoist a calculation out of a loop or to cache a measurement, not to optimize the drawing calls themselves.
Memory Model for Large Decks — python-pptx holds the entire presentation in memory, and a deck with hundreds of slides and thousands of shapes can become large. A world-class pipeline monitors memory and, for very large decks, considers chunked generation or streaming where the library permits it. More practically, it avoids holding redundant references to shape objects after they are placed, and it avoids deep-copying large structures. For the current use case (tens to low hundreds of slides) memory is unlikely to be the bottleneck, but the architecture should not paint us into a corner: components should not assume they can keep every shape object alive, and should treat the canvas as a write-only surface.
Observability, Debugging, and Render Manifests — A mature renderer emits enough information to debug a bad slide without re-rendering it. The most useful artifact is a per-slide render manifest: a list of the components that ran, the geometry they produced, the data they bound, and any warnings they raised. Combined with the existing render_errors record, this gives an operator a complete picture of why a slide looks the way it does. For an LLM-driven pipeline, the manifest is also the feedback signal: the generator can read the warnings and correct the YAML. Observability is therefore not operational overhead; it is a core capability of a generative rendering system.
Versioning and Contract Stability — The component contract, the YAML schema, the theme tokens, and the text-measurement model all need explicit versions, and the renderer should stamp the generated deck with the versions it used. This is what lets us evolve the system without silently breaking existing decks. A deck generated under component-contract v1 should still render identically after we ship v2, either because v2 is backward-compatible or because the deck pins v1. Versioning also structures the migration story: we can say precisely which decks need re-baselining when a measurement model changes, rather than discovering it visually.
Data Provenance and Audit Trail in Generated Decks — In the NGO-finance and audit domain, a generated number must be traceable to its source. The renderer should support attaching provenance metadata to any bound value: the source system, the as-of date, the query or line item, and the verification state. This metadata can be rendered visibly (a source note), or carried invisibly in the notes slide or in a custom property. For sub-award reporting this is not optional: a donor or auditor who sees a figure will ask where it came from, and the deck should be able to answer. Provenance turns a pretty chart into an auditable record, which is exactly the Meridian brand promise.
The Meridian Brand System as a Renderer Constraint — The YAML corpus defines a visual identity: one reference line, a strict palette, three type registers, eight icons, six symbols, two patterns, and explicit do/don't rules. A world-class renderer treats this not as content but as a constraint system. That means the theme tokens encode the palette and type; the layout tokens encode the grid and the line position; and components encode the rules (gold only when verified, one line per slide, variances always annotated). When the renderer enforces the brand, a generated deck cannot be off-brand, and the design system stops being a document people have to remember and becomes a property of the output.
Intent-Driven Layout — The corpus tags slides with intent: persuasion-first, strategy-first, decision-first, synthesis-first. This is a layout signal, not just a label. Persuasion-first slides should lead with a hero number or a metaphor and minimize chrome; strategy-first slides should lead with a framework and evidence; decision-first slides should lead with the ask and the options and should surface a clear callout band. The renderer can use intent to choose emphasis, default footer treatment, and whether the takeaway or the callout is visually primary. Mapping intent to layout is a cheap way to make generated decks feel art-directed, because it encodes a designer's judgment as data.
The Takeaway and Callout Bands as Semantic Primitives — Almost every slide in the corpus ends with a takeaway and often a callout. These are not afterthoughts; they are the point of the slide. The renderer should treat them as first-class semantic primitives with their own layout slots, their own typography, and their own visibility flags. The takeaway states what is true; the callout states what to do. Keeping them structurally separate means a deck can be re-purposed: an update deck can keep the takeaways and rewrite the callouts, or a board deck can elevate callouts into a decisions page. This two-band pattern is one of the most valuable reusable structures in the whole corpus.
Component Lifecycle Governance — Components should have a lifecycle: draft, stable, and deprecated. A draft component can change its YAML contract freely; a stable component must be backward-compatible and is covered by golden-slide tests; a deprecated component still renders but emits a warning and points to its replacement. This lifecycle is what lets us experiment with new visualization patterns (draft) without risking existing decks, and it is what lets us retire a pattern cleanly when a better one appears. Governance without lifecycle either freezes the system (nothing can change) or destabilizes it (everything changes); the lifecycle gives us both safety and motion.
Level 1 Primitive — Path/Polyline — Add a generic path/polyline primitive accepting points, stroke color, width, dash pattern, join, cap, optional fill, closure, and arrowhead. Keep it domain-agnostic. This one primitive unlocks line charts, confidence bands, radar polygons, ribbons, fishbone branches, curved connectors, annotation leaders, control-loop feedback paths, and scenario fan boundaries. Implementation should build on python-pptx freeform or connector primitives, but expose a clean points-based contract so that callers never touch OOXML. Because paths are the substrate for all analytical geometry, their coordinate handling must be exact and their rendering must be deterministic.
Level 1 Primitive — Rich Connectors — Upgrade connectors from straight point-to-point lines to semantic connectors preserving from/to while adding route, label, arrowhead, style, node anchors, and optional control points. Routes should include straight, orthogonal, elbow, polyline, and curved. When node IDs exist, connectors should attach to named nodes rather than raw coordinates. The routing engine should choose clean paths that avoid overlapping nodes where feasible, and should be stable: the same graph should route the same way every render. Connector labels need their own small layout logic so they sit on the path without colliding with nodes or with each other.
Level 1 Primitive — Group/Container — Add group/container with local coordinate space, optional background, border, padding, clipping, and layout mode. This is essential for metric cards, dashboards, annotated documents, swimlanes, nested architecture diagrams, policy-rule cards, and workshop canvases. Without groups, complex components remain brittle because every child depends on absolute coordinates. With groups, a component can be moved, resized, or re-themed as a unit, and nested layout becomes possible: a dashboard is a grid of cards, each card is a stack of a label, a value, and a delta. Groups are the enabling primitive for composition itself, and should be introduced early.
Level 1 Primitive — Layout Engines — Add small deterministic layout primitives: absolute, stack, grid, split, flow, lane, and radial. Do not build a browser-style constraint solver. The goal is predictable slide layout from component data, gaps, padding, and available space. These layout calculators should produce stable coordinates before drawing. Each layout should be a pure function of its inputs (children sizes, gaps, available box), which makes it testable and cacheable. The stack and grid layouts will carry ninety percent of real usage; split and lane carry the comparison and swimlane cases; radial carries the lifecycle and hub-and-spoke cases. Keep the set small and make each one excellent.
Level 1 Primitive — Repeat/Template Expansion — Add repeat/grid expansion that converts a data collection into component instances before rendering. It should support child templates, columns/rows, gaps, per-item bindings, stable IDs, and template overrides. This directly addresses the largest authoring inefficiency in the YAML corpus: manually repeated cards, bars, rows, and panels. In the corpus, the executive dashboards, the HR scorecards, and the regional breakdowns all hand-author near-identical blocks; a repeat primitive collapses each of those into a data list plus a template. Repeat is also the foundation for data-driven rendering, because it is the mechanism by which a dataset becomes a set of components.
Level 1 Primitive — Scale/Axis System — Add analytical scales: linear, categorical, temporal, percentage, and radial. A scale should map data domains to plot ranges and generate ticks, labels, gridlines, zero baselines, and threshold bands. Without shared scales, every chart component independently invents coordinate math, producing inconsistent visuals and brittle maintenance. The scale system should also own nice-number tick selection and should handle degenerate domains (all-zero, single-point, empty) gracefully. Temporal scales need unit awareness (months, quarters, fiscal periods) because the finance domain thinks in periods, not raw dates. A good scale system is the difference between charts that look professional and charts that look generated.
Level 1 Primitive — Annotation/Marker System — Add annotations supporting anchors, labels, callout boxes, leader lines, priority, and collision avoidance. This is critical for commentary-linked charts, audit evidence callouts, document review, exception highlighting, and executive insight slides. Annotations make explanation bindable to data instead of manually positioned. The collision-avoidance requirement is real: a chart with five callouts will have overlapping labels unless the system places them deliberately. Annotations should also respect the Meridian rule that a variance is never unexplained; the annotation system is what makes that rule enforceable at scale.
Level 1 Primitive — Measurement Service — Add reusable measurement helpers: text height at width, estimated wrapped line count, remaining space after padding, card count that fits a grid, and label collision detection. This turns existing font-size estimation into layout-aware measurement and allows components to adapt to content volume without manual tuning. The service should be the single source of truth for all size estimates, so that when the estimation model improves, every component improves at once. It should also expose its estimates to the render manifest, so that when a layout misbehaves, an operator can see the numbers the layout engine was working from.
Level 1 Primitive — Semantic Status Tokens — Formalize semantic tokens such as status, severity, trend, priority, confidence, direction, verification state, and risk state. Theme resolution should map these semantics to fills, lines, and text treatments. This prevents business meaning from becoming coupled to arbitrary colors and supports future themes without rewriting YAML. In the corpus, gold already means verified and the triangle already means variance; those are de facto semantic tokens that should be made explicit. Once explicit, they can be validated (you cannot mark an unverified number as verified), which turns a stylistic convention into a data-integrity rule.
Level 1 Primitive — Table/Grid-Cell Primitives — Promote table cells into semantic primitives supporting spans, alignment, numeric formatting, status tokens, wrapping, truncation, row/column headers, and conditional fills. This reduces duplication between table strategy, matrix strategy, and custom-shape tables, and unifies schedules, registers, matrices, scorecards, and decision tables. The finance domain is table-heavy: budgets, variance analyses, control matrices, and compliance matrices all appear in the corpus. A strong table primitive with numeric formatting and status fills would serve more real slides than almost any chart, and should be prioritized accordingly.
Level 2 Composite — Generic Graph — Build a generic graph component with nodes, edges, groups, and layout strategy. Layouts should include manual, sequence, tree, hierarchy, layered, radial, and flow. Nodes should reuse existing rectangle, circle, and text styling. Edges should use upgraded connector/path routing. This one component covers evidence chains, account flows, org trees, causal maps, operating models, exception genealogies, ownership networks, and traceability diagrams. Graphs are the highest-leverage composite because so many domain patterns are secretly graphs; investing once in a good graph engine pays across audit, risk, finance, HR, and operations simultaneously.
Level 2 Composite — Generic Series Chart — Build a generic series chart model defining plot area, scales, series, marks, labels, legends, thresholds, and annotations. Bar, line, area, stacked bar, scatter, Pareto, control chart, tornado, fan chart, burn-down, and trend views should be configurations of one series engine rather than separate renderers. The corpus already hand-builds bar charts from rectangles and trend lines from positioned boxes; a series engine replaces all of that with data. The key design decision is that marks are bound to scale positions, so that adding a series or changing a domain reflows the whole chart correctly.
Level 2 Composite — Waterfall/Bridge — Build a waterfall component accepting start, ordered steps, optional subtotals, and end. It should compute running totals, positive/negative bar placement, connectors, labels, subtotal markers, and semantic styling. This covers budget bridges, FX bridges, cash movement, headcount changes, grant income bridges, contribution analysis, fund restriction bridges, and program-output bridges. The waterfall is the single most domain-appropriate chart for NGO finance because almost every financial story is a story of movement from one position to another, and the corpus contains several hand-built waterfalls that confirm the demand.
Level 2 Composite — Heatmap/Matrix — Build a heatmap/matrix component accepting rows, columns, values, scale mode, semantic fills, labels, legends, quadrant borders, and cell annotations. It covers risk heatmaps, control matrices, capability matrices, data quality scorecards, performance grids, compliance matrices, donor compliance maps, and finding-aging boards. The component should support both continuous scales (a numeric value mapped to a color ramp) and categorical scales (a status mapped to a discrete color), because the corpus uses both: data-quality scores are numeric, while control effectiveness is categorical.
Level 2 Composite — Small Multiples — Build a small-multiples component accepting records, child template, columns, gaps, and per-item style. Each child can be a metric card, mini bar chart, sparkline, status card, mini timeline, or narrative block. This is one of the highest-leverage composites because executive reporting repeatedly uses grid-based panels. The corpus's executive dashboards and HR overviews are exactly this pattern, hand-authored. Small multiples also compose naturally with repeat and with measurement: the component measures the available area, chooses a column count, and sizes each cell to fit.
Level 2 Composite — Funnel — Build a funnel component accepting stages, values, conversion rates, labels, leakage annotations, and orientation. It should calculate narrowing widths and stage-to-stage conversion. It covers recruiting pipelines, grant acquisition pipelines, onboarding progression, exception resolution funnels, and program delivery pipelines. The corpus contains a recruiting funnel and a grant-acquisition funnel, both hand-built from progressively narrower rectangles. A funnel component should also surface the leak explicitly (where the biggest drop is), because in both HR and fundraising the leak is the actionable insight.
Level 2 Composite — Swimlane — Build a swimlane component accepting lanes, items, item positions, connectors, and lane headers. Items should be positioned relative to lanes, not absolute slide coordinates. This supports service workflows, approval processes, incident response, grant lifecycle, finance close, HR onboarding, and sub-award management flows. The corpus's service-management section and the sub-award lifecycle both need swimlanes. The component should support both horizontal lanes stacked vertically and vertical lanes side by side, and connectors should route across lane boundaries cleanly, which is where the rich-connector primitive pays off.
Level 2 Composite — Control Board — Build a control board component accepting records with status, owner, severity, age, due date, trend, and action. It should render cards, tiles, or compact table rows with semantic status colors. It covers traffic-light boards, finding-aging boards, queue boards, exception boards, risk boards, and executive action trackers. Control boards are the operational heartbeat of the audit and service domains, and the corpus contains several. The component should make the status token visually dominant, because the whole point of a control board is to let a reader scan for red in under two seconds.
Level 2 Composite — Adaptive List/Register — Generalize the checklist strategy into an adaptive list/register component. It should estimate line counts, adapt font size, calculate row heights, split into columns when needed, and support checkbox/status states. This is useful for registers, controls, findings, policies, onboarding tasks, and compliance checklists. The corpus's onboarding checklists, control checklists, and policy registers are all this pattern. Because the existing checklist strategy already does adaptive sizing, this composite is largely an extraction and generalization of working code, which makes it one of the lowest-risk, highest-value Level 2 items.
Level 3 Template — Finance Templates — Finance templates should be thin wrappers over generic components: variance bridge, cash runway, grant burn-down, fund restriction waterfall, close critical path, budget execution dashboard, revenue concentration, cost composition, and donor reporting status. They should translate finance semantics into component contracts and keep chart geometry out of domain code. The corpus's Data & Analytics section is effectively a finance-template library already, hand-authored; promoting those into templates would let a generator produce a budget-execution slide from a dataset alone. Finance templates should also carry the period and as-of semantics that make the numbers auditable.
Level 3 Template — Audit Templates — Audit templates should include evidence chain, audit trail reconstruction, control-to-evidence matrix, finding aging, exception genealogy, issue remediation tracker, three-way match, and obligation-to-control traceability. These should be composed from graph, table, timeline, heatmap, and annotation components. The sub-award knowledge base maps almost one-to-one onto these templates: pre-award assessment becomes a checklist, monitoring becomes an evidence chain, close-out becomes a checklist plus a bridge, and the audit pack becomes a traceability matrix. Audit templates are where the provenance and annotation primitives become visibly valuable.
Level 3 Template — Risk Templates — Risk templates should include risk heatmap, bow-tie model, risk register board, likelihood/impact matrix, control effectiveness matrix, scenario sensitivity tornado, and concentration risk view. They should rely on matrix, graph, series, and status components rather than bespoke risk drawing code. The corpus contains tornado and scenario-fan slides and several risk matrices. Risk templates should encode the convention that severity is a semantic token, so that a risk's color is always consistent with its rating, and so that a heatmap and a register board for the same risks always agree.
Level 3 Template — Operations Templates — Operations templates should include escalation ladder, swimlane workflow, SLA tracker, queue aging board, incident command view, support coverage model, service channel map, and operational pulse. The existing service-management YAML already demonstrates these patterns and should be promoted into reusable templates. The service-management section of the corpus is notably well-structured and is the best source of golden examples for these templates. Operations templates benefit strongly from the control-board and swimlane composites, and they are a good early proof that the component layer works across domains.
Level 3 Template — HR Templates — HR templates should include workforce dashboard, headcount forecast, hiring funnel, candidate pipeline, onboarding checklist, succession map, capability model, engagement pulse, compensation fairness view, and attrition risk board. The supplied HR YAML contains many manual versions of these structures and is a strong candidate for componentization. The HR section of the corpus is the largest single domain and covers the full employee lifecycle, which makes it an ideal proving ground: if the component layer can express all eight HR batches, it can express almost anything.
Level 3 Template — Policy/Compliance Templates — Policy templates should include policy-rule card, policy register, policy lifecycle, obligation-to-control matrix, compliance status board, regulatory traceability map, and donor-condition flow. These are document-centric and table/graph-centric, making them ideal for table, matrix, graph, and annotation components. The sub-award knowledge base is essentially a policy-compliance corpus: every Q&A describes a rule, an owner, an evidence requirement, and a control. That structure maps directly onto policy-rule cards and obligation-to-control matrices, which makes sub-awards a natural first deployment for policy templates.
Level 3 Template — Sub-Award Templates — Sub-award templates should include lifecycle map, partner risk matrix, pre-award due-diligence board, payment control checklist, monitoring evidence map, amendment trail, close-out checklist, and audit pack traceability. These should reuse timeline, graph, matrix, checklist, and annotation components rather than becoming bespoke sub-award renderers. The thirty Q&As in the sub-award knowledge base define a complete control lifecycle, and each stage of that lifecycle has a natural visual: selection is a checklist, payment is a three-way match, monitoring is an evidence chain, and close-out is a checklist plus a bridge.
Pattern — Sankey Diagrams — Support: not native. Composition: partial approximation only. New primitive: path/ribbon plus flow layout. YAML change: nodes, links, values. Difficulty: high. Best abstraction: Level 2 flow graph plus Level 3 Sankey template. Implementation should compute node columns, vertical ordering, link thickness, and ribbon paths from normalized link values. Sankey is genuinely hard because ribbon thickness must be proportional and must not overlap, so it belongs in Tier 3. In the NGO-finance domain, a Sankey is the ideal way to show donor funds flowing through programs to beneficiaries, which makes it worth the investment eventually.
Pattern — Account-to-Account Flow Maps — Support: composable now for small cases. Composition: yes. New primitive: graph layout and richer connectors for scale. YAML change: semantic nodes and edges. Difficulty: low to medium. Best abstraction: generic graph with an account-flow template. Supports ledger movement, donor fund flow, grant disbursement paths, intercompany movement, and reconciliation traces. Account-flow maps are a direct expression of double-entry bookkeeping, which the Meridian brand explicitly draws on; showing money moving between accounts as a graph is on-brand and auditor-friendly, because it makes the trail visible.
Pattern — Evidence-Chain and Traceability Maps — Support: composable now. Composition: yes. New primitive: no immediate requirement. YAML change: nodes, edges, evidence metadata. Difficulty: low. Best abstraction: Level 2 evidence graph. Nodes can represent claim, document, transaction, control, approval, and exception; edges can represent supported-by, paid-by, approved-by, evidenced-by, and contradicted-by. Evidence chains are the visual embodiment of the sub-award framework's emphasis on a complete evidence trail, and they are one of the strongest arguments for the graph composite because they recur across audit, compliance, and finance.
Pattern — Decision Trees — Support: semantically present via decision-tree strategy. Composition: yes. New primitive: no. YAML change: structured branch schema. Difficulty: low. Best abstraction: reusable decision-tree composite with question, condition, children, branch labels, result styling, owner, and optional status. Tree layout should be automatic with manual override. The existing decision-tree strategy is a good start but is specialized; generalizing it into a tree layout within the graph engine preserves the investment and lets decision trees, exception genealogies, and KPI decomposition trees share one engine.
Pattern — Swimlane Diagrams — Support: composable with minor additions. Composition: yes. New primitive: lane/container layout. YAML change: lanes, items, connectors. Difficulty: low to medium. Best abstraction: Level 2 swimlane composite. Connectors should reference item IDs, not raw coordinates, allowing reflow when lanes are added, removed, or resized. The sub-award lifecycle, with its distinct actors (prime, partner, donor, auditor), is a natural swimlane subject, and so is the month-end close with its function handoffs. Swimlanes are where the group/container and rich-connector primitives combine most visibly.
Pattern — Control-Loop Diagrams — Support: composable now for simple loops. Composition: yes. New primitive: connector/path routing for polished feedback paths. YAML change: stages and feedback edges. Difficulty: low to medium. Best abstraction: control-loop composite over generic graph. The component should place stages around a loop and route feedback edges cleanly. Control loops appear in monitoring (the sub-award framework is explicitly a loop of assess-fund-monitor-report-correct) and in continuous improvement. A radial layout with a clear feedback arrow is the canonical form, and it needs curved connectors to look right.
Pattern — Exception Genealogy Diagrams — Support: composable for bounded hierarchies. Composition: yes. New primitive: not initially. YAML change: parent/child relationships. Difficulty: low to medium. Best abstraction: generic hierarchy graph. Nodes can carry exception ID, date, owner, control, severity, and status; the same component supports root-cause trees and finding lineage. Exception genealogy is the visual answer to the sub-award framework's requirement to track exceptions and remediation; showing an exception's ancestry (which control failed, which check missed it) is powerful for audit committees.
Pattern — Escalation Ladders — Support: native/composable now. Composition: yes. New primitive: no. YAML change: optional stage metadata. Difficulty: very low. Best abstraction: process-flow template with vertical or tiered orientation. Fields can include threshold, owner, response time, severity, and notification channel. Escalation ladders appear in service management and in sub-award monitoring (when does a partner issue become a prime issue become a donor issue). Because they are just sequences, they are a cheap early win and a good template to ship in Tier 1.
Pattern — Journey Maps — Support: native at composite level. Composition: yes. New primitive: no. YAML change: structured journey stages. Difficulty: very low. Best abstraction: timeline/journey composite. Stages can include owner, status, metric, dependency, risk, emotion, and evidence. Covers employee journeys, donor journeys, sub-award lifecycles, and service experiences. The employee-experience journey in the HR corpus is a journey map, and the sub-award lifecycle can be rendered as one too. Journey maps are timelines enriched with per-stage metadata, so they cost almost nothing once the timeline component exists.
Pattern — Operating-Model Maps — Support: composable now. Composition: yes. New primitive: no immediate requirement. YAML change: layers, owners, interactions. Difficulty: low. Best abstraction: Level 3 template built from groups, cards, process flows, and connectors. The template should standardize governance bands, functional lanes, handoffs, and ownership labels. The people-operating-model slide in the HR corpus and the support-operating-model slide in the service corpus are both operating-model maps; they differ in content but not in structure, which is exactly the signal that a template is warranted.
Pattern — Audit-Trail Reconstruction — Support: composable now for chronological cases. Composition: yes. New primitive: no immediate requirement. YAML change: event schema. Difficulty: low to medium. Best abstraction: event timeline plus audit-trail template. Events should include timestamp, actor, action, document, transaction, control, and exception, and should support both linear and evidence-graph views. Audit-trail reconstruction is one of the most auditor-valued artifacts, and the ability to flip between a chronological view and an evidence-graph view from the same event data is a genuinely differentiating capability.
Pattern — Waterfall and Bridge Charts — Support: visually composable now. Composition: yes. New primitive: not necessarily. YAML change: start, steps, subtotals, end. Difficulty: low to medium. Best abstraction: Level 2 waterfall component. It should compute cumulative totals, bar bases, connector positions, subtotal markers, labels, and semantic positive/negative styling. The corpus contains a contribution waterfall and several variance bridges, confirming that this is a recurring need. Because waterfalls are arithmetic, the component should validate that the steps reconcile to the end value, and should raise a clear error when they do not.
Pattern — FX Bridge Charts — Support: composable once waterfall exists. Composition: yes. New primitive: none beyond waterfall and scale. YAML change: domain template. Difficulty: low after waterfall. Best abstraction: Level 3 FX bridge template. Categories can include opening balance, transaction effects, rate movement, translation effects, and closing balance. FX logic belongs in the template, not the renderer. The multi-currency reality of NGO finance (the corpus references four currencies) makes FX bridges a recurring board artifact, and the template can carry the currency labels and rate footnotes that make the bridge credible.
Pattern — Pareto Charts — Support: requires analytical component. Composition: partial. New primitive: path, scale, axis. YAML change: categories, values, cumulative series. Difficulty: medium. Best abstraction: bar series plus cumulative line series, with a Level 3 Pareto template. The architectural win is dual-scale composition reused across management charts. Pareto is the classic quality tool and fits the error-analysis and exception-tracking slides in the corpus; showing that a few root causes drive most errors is exactly the insight a control function wants to communicate, and it needs the dual-axis capability to be convincing.
Pattern — Radar Charts — Support: requires radial capability. Composition: poor today. New primitive: radial scale and polygon path. YAML change: dimensions and series. Difficulty: medium to high. Best abstraction: radial-series chart. The same engine supports capability wheels, stakeholder maps, maturity assessments, and control-effectiveness profiles. Radar charts suit capability models and control-effectiveness profiles, both of which appear in the HR and audit corpora. Because radar charts are visually busy, the template should cap the number of dimensions and should prefer two series (current versus target) over many.
Pattern — Stacked Contribution Charts — Support: composable with minor additions. Composition: yes. New primitive: no. YAML change: structured series. Difficulty: low to medium. Best abstraction: bar series with stacked mode. Supports budget composition, headcount composition, program portfolio contribution, cost category mix, and revenue source composition. The segment-breakdown and channel-breakdown slides in the corpus are stacked contributions. The component should label segments clearly and should order them consistently (largest first or logical order), because inconsistent ordering is the most common way stacked charts confuse readers.
Pattern — Small Multiples and Mini-Panels — Support: effectively native by composition. Composition: yes. New primitive: no. YAML change: repeat/grid. Difficulty: low. Best abstraction: small multiples plus generic repeat. This is one of the highest-return capabilities because it compresses repeated manual geometry into data-driven templates. The executive dashboards, the KPI scorecards, and the regional breakdowns in the corpus are all small multiples. Shipping small multiples early would immediately shrink the YAML corpus and would give generators a reliable way to produce dashboard slides from metric datasets.
Pattern — Heat Maps — Support: composable now for fixed matrices. Composition: yes. New primitive: no. YAML change: matrix values and scale. Difficulty: low to medium. Best abstraction: Level 2 heatmap. The missing abstraction is data-to-color mapping through semantic theme tokens, not basic shape capability. Heatmaps serve risk, capability, data quality, and performance. The key decision is the color ramp: it should be semantic (worse is warmer) and should be defined in the theme so that all heatmaps in a deck agree about what red means.
Pattern — Split-Screen Comparisons — Support: native. Composition: already implemented. New primitive: no. YAML change: optional structured comparison data. Difficulty: very low. Best abstraction: existing comparison composite enhanced with deltas, evidence, scores, risks, and recommendation fields. Do not over-engineer this capability. The before/after and do/don't slides in the corpus are split-screen comparisons. The enhancement worth making is letting each side carry a verdict and a delta, so that the comparison does not just show two states but tells the reader which one is better and by how much.
Pattern — 2x2 Matrices — Support: composable now. Composition: yes. New primitive: no. YAML change: optional matrix schema. Difficulty: very low. Best abstraction: Level 2 matrix2x2. It supports urgency/importance, impact/probability, effort/value, risk prioritization, maturity positioning, and management prioritization. The 9-box performance grid in the HR corpus is a 3x3, which suggests the matrix component should generalize to n-by-m rather than being limited to 2x2. Quadrant labels and axis titles should be first-class, because the meaning of a matrix lives in its axes.
Pattern — Decision Matrices — Support: composable now. Composition: yes. New primitive: no. YAML change: criteria, options, weights, scores. Difficulty: low. Best abstraction: decision matrix over semantic table. It should calculate weighted totals, highlight recommendations, and preserve score rationale. Decision matrices are the analytical companion to decision boards: the board shows the ask, the matrix shows the reasoning. Keeping the score rationale visible matters for governance, because a board that cannot show why it chose an option will not survive an audit committee.
Pattern — Before/After Transformations — Support: native/composable now. Composition: yes. New primitive: no. YAML change: before, after, delta, driver, commentary. Difficulty: very low. Best abstraction: narrative comparison component. Supports process improvement, financial transformation, control maturity, organizational change, and policy change slides. The baseline-comparison slide in the corpus (before and after ERP) is this pattern. The delta should be rendered with a trend token, and the driver should be annotated, so the transformation is explained, not just asserted.
Pattern — Management Decision Boards — Support: composable now. Composition: yes. New primitive: no. YAML change: decision, evidence, options, recommendation, owner, deadline. Difficulty: low. Best abstraction: Level 3 domain template. It standardizes executive decision structure without inventing new geometry. The spotlight slide in the corpus (the one decision) is the minimal decision board. A full decision board adds evidence and options. Decision boards are where the callout band shines, because the callout is literally the decision being requested.
Pattern — Control Matrices — Support: native/composable now. Composition: yes. New primitive: no. YAML change: semantic control columns. Difficulty: very low. Best abstraction: matrix/control composite. Fields can include control ID, objective, owner, evidence, frequency, effectiveness, exception, and remediation. YAML Evolution — Preserve Existing Outer Contract — Existing YAML using type, section, section_label, title, layout, and shapes must remain valid. Expansion should be additive. Semantic components should be optional, and raw shapes should remain the escape hatch for exact editorial control. Forced migration would be a mistake. The corpus is large and carefully authored; the migration path must let every existing slide keep rendering unchanged, and new capabilities must be opt-in. This is the single most important compatibility commitment.
YAML Evolution — Add Optional Data Namespace — Introduce slide-level or component-local data. Components bind fields to visual roles such as label, value, status, date, owner, severity, and trend. This separates information from geometry and enables one template to render many datasets. The data namespace is what turns a slide definition into a slide template, and it is the foundation for all data-driven rendering. Bindings should be explicit and validated, so that a missing field is a clear error, not a silent blank.
YAML Evolution — Add Optional Components List — Add a components list beside shapes. Components should compile to the same internal scene representation after validation and layout calculation. This keeps authoring declarative while preserving manual shape control. The compile step is important: components expand into primitives, so the rest of the pipeline does not need to know whether a shape came from a component or was hand-authored. That uniformity keeps the renderer simple.
YAML Evolution — Add Layout Objects — Preserve current string layout values but permit richer objects such as grid with columns, gap, padding, and alignment. This is a backward-compatible transition from slide-level hints toward deterministic component layout. Layout objects should be declarative and should not embed logic; if a layout needs behavior, that behavior belongs in a layout engine, not in the YAML. Keeping layout declarative is what makes it cacheable and testable.
YAML Evolution — Add Semantic Connector Objects — Connectors should reference object IDs and specify route, label, arrowhead, and style. The compiler resolves IDs to geometry and sends the resulting route to the connector/path renderer. Raw coordinate connectors remain an escape hatch. ID-based connectors are what make graphs and flow diagrams maintainable, because moving a node then automatically moves its connectors, which is the single biggest authoring win for relationship diagrams.
YAML Evolution — Establish Common Component Contract — Every reusable component should accept a predictable subset: id, optional x/y/w/h, optional parent slot, data, bindings, style, theme, children, and component-specific semantic properties. A component should return a scene fragment, not directly manipulate the presentation object outside the canvas interface. A uniform contract is what makes components composable and what lets a generator learn one interface and apply it everywhere.
YAML Example — Generic Graph — Example contract: kind graph, layout hierarchy, nodes with id and label, edges with from, to, and label. This one structure serves evidence chains, account flows, org charts, causal maps, related-party networks, and architecture diagrams. The example should show a node carrying a status and an edge carrying a relationship label, because those two fields are what lift a graph from a picture to a semantic model.
YAML Example — Waterfall — Example contract: kind waterfall, start label/value, ordered steps with signed values, optional subtotal, end label/value. The component calculates cumulative totals, bar heights, connector positions, and semantic styling. The example should include a subtotal to show that the component understands running totals, and it should use signed values so that direction is data, not styling.
YAML Example — Small Multiples — Example contract: kind small_multiples, columns, gap, template metric_card, items with label/value/status. Child templates can later include mini_bar, sparkline, status_card, or mini_timeline. The example should show three or four items so the grid behavior is visible, and it should show one item with a status to demonstrate semantic styling inside a repeated component.
YAML Example — Heatmap — Example contract: kind heatmap, rows, columns, values, scale min/max or categorical semantic scale. The renderer converts values to cell geometry and semantic fills. The example should show a categorical scale mapped to status tokens, because that is the more common case in the corpus and it demonstrates the theme integration.
YAML Example — Timeline — Example contract: kind timeline, items with time, title, description, optional status and owner. This formalizes the existing timeline strategy rather than inventing a new language. The example should mirror the fields the timeline strategy already reads, so that existing timeline YAML is already valid under the new contract, which is the cleanest possible migration.
YAML Example — Swimlane — Example contract: kind swimlane, lanes with id and label, items with id/lane/start/end/title, connectors with from/to. Lane-relative positioning allows reflow without hand-editing every object. The example should show two lanes and a connector crossing lanes, because the cross-lane connector is the case that proves the layout and routing work together.
YAML Example — Decision Board — Example contract: kind decision_board, decision, evidence list, options with scores, recommendation, owner, deadline. This produces a consistent executive decision structure with almost no manual geometry. The example should include a recommendation and an owner, because a decision board without an owner is not a decision, and the template should make that omission visible.
Validation — Structural Contracts — Validate at the component boundary before rendering. Check known component kind, finite non-negative dimensions, unique IDs, graph edges pointing to existing nodes, consistent matrix row/column lengths, accessor fields present, parseable dates, and finite numeric values. Errors should identify component ID, kind, field, and violated contract. Structural validation is cheap and catches the large majority of generation errors, which is why it should run before any geometry is computed.
Validation — Semantic Contracts — Validate meaning, not just types. Waterfall end should match cumulative total when explicit. Matrix dimensions should be compatible. Timeline dates should be ordered when proportional placement is requested. Graphs should detect orphan references and cycles where trees are required. Heatmap scales should cover supplied values. Semantic validation is where analytical generation becomes reliable, and it is also where the renderer can enforce domain invariants, such as "a verified figure must have a verification date."
Defaults — Theme and Layout Inheritance — Components should inherit THEME and LAYOUT instead of requiring explicit colors and spacing for every instance. This keeps new components visually coherent with existing decks and avoids introducing a second design system. Inheritance should be explicit in the contract (a component reads tokens unless overridden), and overrides should be rare and visible, because every override is a place where a deck can drift off-brand.
Style Contract — Semantic Styling — Recommended style properties include tone, status, emphasis, severity, trend, density, verification state, and risk state. For example, status: warning should resolve through theme to the existing warning treatment. This is superior to requiring authors to know that warning should be gold, and it supports future alternate themes. Semantic styling is also what makes accessibility enforceable, because the theme can guarantee that every semantic state has a legible treatment.
Roadmap — Tier 1: High Value, Low Complexity — Add semantic layout primitives, repeat/grid, richer table cells, semantic status tokens, annotations, measurement helpers, and initial composites: metric cards, small multiples, matrices, heatmaps, funnels, timelines, staircases, scorecards, and control boards. These build directly on the existing rectangle/text/card/arrow vocabulary and address the biggest YAML maintenance problem: repeated geometry. Tier 1 is deliberately conservative: everything in it is an extension of working code, which keeps risk low and learning high.
Why Tier 1 First — Tier 1 creates immediate leverage across management reporting, HR, finance, audit, service operations, and program reporting without requiring difficult mathematical rendering infrastructure. It also tests the component API before graph and chart layout become complex. Most importantly, it makes the existing YAML corpus easier to maintain. A second reason: Tier 1 components are the ones a generator will use most often, so improving them first improves the majority of generated output fastest.
Roadmap — Tier 2: High Value, Medium Complexity — Add path/polyline, connector routing, data binding, scale/axis, generic series charts, graph layouts, waterfall, stacked bars, Pareto, swimlanes, and reusable graph components. This is the architectural core because it converts the renderer from "draw manually specified geometry" into "draw geometry derived from structured semantics." Tier 2 is where the renderer becomes a real layout engine, and it should be approached as a single coherent program of work rather than a bag of features, because the pieces (scales, connectors, groups, measurement) depend on each other.
Why Tier 2 Matters — A shared scale engine pays dividends across chart families. A shared graph engine pays dividends across diagram families. A shared data-binding layer pays dividends across every repeated component. This is where capability grows superlinearly because each new primitive supports several families at once. The economics are decisive: one graph engine serves ten diagram types, one series engine serves ten chart types, and one data-binding layer serves every component, so the marginal cost of each new visualization drops sharply after Tier 2.
Roadmap — Tier 3: Strategic, High Complexity — Add Sankey/ribbon flows, radial/radar charts, circular lifecycle layouts, sophisticated scenario charts, complex auto-routing, multi-axis charts, and document annotation systems only after generic infrastructure is stable. These features are expensive because they combine several lower-level capabilities. Building them earlier would duplicate infrastructure and create brittle code. Tier 3 is also where taste matters most: Sankey and radar are easy to make ugly, so they should arrive only when the theme, scales, and annotation system are mature enough to keep them on-brand.
Why Tier 3 Comes Last — Sankey requires flow layout and path geometry; radar requires radial scale and polygon paths; circular lifecycle requires radial placement and curved connectors; document annotations require anchors, grouping, and leader routing. Each becomes much smaller once the underlying generic system exists. Sequencing them last is not deferral; it is the difference between building each one on a foundation versus building each one from scratch, and the cost difference is large.
Placement — What Belongs in render.py — render.py should remain the engine. Add path/polyline, richer connectors, group/container, table/cell drawing, scale/axis drawing, semantic theme resolution, measurement helpers, and deterministic layout helpers. Keep SlideRenderer focused on strategy resolution and error isolation. Do not add donor-specific, audit-specific, finance-specific, HR-specific, or policy-specific business logic to the renderer core. The renderer should know how to draw a waterfall; it should not know what a waterfall means in a particular report.
Placement — What Belongs in Reusable Components — SlideComponents should receive normalized semantic data and calculate layout internally. Add components such as metric_card_grid, small_multiples, waterfall, funnel, heatmap, matrix, graph, swimlane, bar_series, line_series, control_board, scorecard, staircase, and adaptive_register. Each component should be independently testable with golden slides, and each should document its YAML contract, so that generators can target them precisely.
Placement — What Belongs in Domain Templates — Domain templates should translate business concepts into component contracts. FX bridge wraps waterfall. Evidence chain wraps graph. Audit trail wraps timeline plus evidence links. Control matrix wraps matrix. Management decision board assembles cards, evidence, options, and recommendation. Sub-award lifecycle wraps timeline/graph/checklist components. Domain templates should live in YAML or thin wrapper modules, and they should be the only place domain vocabulary appears, keeping the engine domain-free.
Anti-Pattern — Strategy Explosion — Do not turn every visualization into a new SlideRenderStrategy. That would duplicate lifecycle handling, theme injection, title treatment, spacing rules, and error handling. It would also increase test surface and make the system harder to maintain. Only genuinely different slide-level rendering modes should become strategies. A good heuristic: if the new thing can be expressed as components inside an existing strategy, it is a component, not a strategy.
Anti-Pattern — Bespoke Domain Renderers — Do not create SankeyRenderer, FXBridgeRenderer, EvidenceChainRenderer, BowTieRenderer, PolicyMatrixRenderer, or SubAwardLifecycleRenderer as isolated classes. These are templates over generic components. Bespoke renderers duplicate geometry, fragment validation, and make future changes expensive. Every bespoke renderer is a promise to maintain a second copy of layout logic forever, and that debt compounds.
Anti-Pattern — Hardcoded Semantic Colors — Do not let components hardcode that warning is gold or that verified is gold. That couples business meaning to a specific palette and breaks the moment the theme changes or a second brand appears. All semantic states must resolve through the theme's status tokens, so that meaning and appearance stay decoupled. This is the difference between a renderer that can support one brand and one that can support many.
Anti-Pattern — Geometry in Domain Logic — Do not let domain templates compute coordinates. The moment a finance template is calculating x/y, it has become a renderer, and it will break when the layout changes. Domain templates should express structure and data; components should own geometry. This separation is what allows a layout improvement to upgrade every domain at once.
Empirical Evidence from YAML Corpus — The supplied YAML proves the renderer can already produce sophisticated visuals from a small primitive set. The main gap is semantic compression, not drawing power. Repeated manual rectangles, arrows, and text boxes should become data-driven components. The low-level escape hatch should remain, but it should no longer be the default for repeated patterns. The corpus is effectively a requirements document written in shapes, and it tells us precisely which components to build first.
Cross-Corpus Consistency — The Visual & Expressive, Technical & Engineering, Data & Analytics, Service Management, and HR sections all use the same canvas, the same palette, and the same card-and-line grammar. This consistency is an asset and a constraint: any new component must render in a way that is indistinguishable in quality and style from the existing corpus. Golden-slide tests drawn from each section are the way to lock that in, so that expansion does not quietly erode the deck's coherence.
Sub-Award Domain Mapping — The sub-award knowledge base provides a ready-made domain template library. Partner selection maps to a checklist plus a risk matrix. Agreements map to a policy-rule card. Payments map to a three-way match and a pre-payment checklist. Monitoring maps to an evidence chain and a control board. Close-out maps to a checklist plus a bridge. Continuous improvement maps to a driver tree. This near-total coverage confirms that the component layer, once built, can serve the entire sub-award lifecycle without new primitives.
Testing Strategy for Expansion — Every new primitive/component should have golden-slide tests: input YAML, expected shape count, expected coordinates or coordinate ranges, expected text content, and expected theme tokens. Graph components need orphan-edge and cycle tests. Charts need scale tests. Tables need span/wrapping tests. Repeat needs expansion-count tests. This keeps expansion deterministic and prevents visual regressions. Golden slides should be drawn from the real corpus, because they encode the brand as well as the geometry.
Testing — Determinism and Diffing — Golden-slide tests need a comparison method. Because PPTX is XML, a robust approach is to compare the shape manifest (counts, types, positions, texts) rather than byte-compare files, which is brittle to benign differences. A shape-diff report that names the first divergent shape makes failures diagnosable. Determinism guarantees that a passing test stays passing, and the render manifest makes a failing test explain itself.
Migration Strategy for Existing YAML — Do not force migration. Keep existing custom shapes valid. Identify repeated patterns in the YAML corpus and promote them incrementally: first metric cards, then dashboards, then timelines, then process flows, then matrices, then graphs. Each promotion should reduce YAML size while preserving visual output. The migration should be measured in YAML lines removed and in generation errors reduced, because those are the concrete benefits.
Migration — The Escape Hatch Doctrine — The custom-shape escape hatch is a feature, not a failure. Some slides are art direction and should stay hand-authored. The doctrine is: components are the default for repeated patterns; the escape hatch is reserved for one-off editorial compositions. A healthy deck is mostly components with a small amount of bespoke art, and the renderer should make both paths first-class.
Smallest High-Leverage Extension Set — If capacity is constrained, implement in this order: path/polyline, semantic connector, group/container, grid/stack/split/flow/lane, repeat, semantic data binding, scale/axis, generic graph layout, generic table, and semantic status/theme tokens. This set unlocks most of the requested visualization surface without a large number of bespoke renderers. The ordering is deliberate: geometry primitives first, then layout, then data binding, then the composites that use them.
Capability Expansion Thesis — The full requested list compresses into a small number of visual families: graph, series chart, matrix, timeline, flow, card/grid, and document/table. Sankey is specialized flow graph. Evidence chains and account maps are graph layouts. Fishbone and bow-tie are causal graph templates. Pareto is bar plus line. FX bridge is waterfall. Heatmap is matrix plus color scale. Journey maps are timelines. Management boards are card/grid compositions. The architecture should reflect these families, not individual names, because families are stable and individual diagram names are fashion.
Final Architecture Recommendation — Keep the renderer fundamentally primitive/compositional, but introduce a formal semantic component layer between YAML and canvas. The target pipeline should be: YAML → normalization → validation → component expansion → layout/geometry → primitive scene graph → python-pptx. SlideCanvas remains the low-level renderer, SlideComponents becomes the reusable composite library, domain templates stay above it, and SlideRenderer remains a compact strategy dispatcher. This preserves every working part of the system while giving it the abstraction it lacks.
Final Combined Answer — The system can expand very far without being replaced. Its principal constraints are not fundamental rendering limits; they are missing higher-level abstractions: richer connectors, generic paths, automatic layouts, structured data binding, analytical scales, semantic status tokens, deterministic measurement, and repeatable component contracts. Once those are added, nearly the entire visualization surface can be covered by a small component library plus thin domain templates, while explicit coordinates remain the escape hatch for bespoke slide art. The renderer's future is not more drawing code; it is more judgment, encoded as components, about where things go and what they mean.
