Relational Databases and SQL Fundamentals
1. Q: What is a relational database, and why is it important?
A: Show answer
A relational database is an organized collection of related tables used to store, manage, retrieve, and maintain structured data. Each table represents an entity or a relationship between entities. Data is organized into rows and columns, with relationships established through keys. Relational databases are important because they help organizations maintain data consistency, enforce integrity, reduce unnecessary duplication, control access, and retrieve information efficiently. They are particularly useful when applications need to manage growing volumes of interconnected information reliably.

A: Show answer

7. Q: What is a primary key, and why is it essential?
A: Show answer
A primary key is a column or combination of columns that uniquely identifies every row in a table. For example, ProductID can identify each product independently of its name or description. A primary key must contain unique, non-NULL values. It prevents duplicate identification and provides a reliable reference for relationships with other tables. Primary keys are also important for record updates, deletions, joins, and maintaining referential integrity. A good primary key should be stable, consistently assigned, and independent of changeable business information whenever practical.

10. Q: What is a foreign key, and how does it establish relationships between tables?
A: Show answer
A foreign key is a column or combination of columns in one table that references a candidate key, usually the primary key, of another table. It establishes a relationship between records and helps enforce referential integrity. For example, an Invoice table may contain SupplierID referencing Supplier.SupplierID. This ensures that an invoice refers to a supplier that exists in the Supplier table, subject to the applicable constraint rules. Foreign keys help prevent orphan records and maintain consistency when related information is inserted, updated, or deleted.

11. Q: What is referential integrity?
A: Show answer
Referential integrity is the principle that relationships between related records must remain valid. A foreign key constraint is a common mechanism for enforcing this principle. For example, every non-NULL SupplierID recorded in an Invoice table must correspond to an acceptable referenced supplier record. Referential integrity prevents transactions from referring to nonexistent master records. It also governs how the database handles changes or deletion of referenced records through actions such as RESTRICT, NO ACTION, CASCADE, SET NULL, or SET DEFAULT, depending on the database system and constraint definition.

20. Q: What is the difference between AND and OR in SQL?
A: Show answer
AND requires all specified conditions to evaluate to TRUE for a row to qualify. OR requires at least one condition to evaluate to TRUE. For example:
SELECT *
FROM product
WHERE price < 30
AND manufacturer = 'Mad Inventors Inc.';
This retrieves products that satisfy both conditions. Replacing AND with OR retrieves products satisfying either condition. Parentheses should be used when combining multiple logical operators to make the intended evaluation explicit and avoid incorrect filtering caused by operator precedence.

25. Q: What is the difference between IS NULL and = NULL?
A: Show answer

This retrieves employees whose termination date is missing. Correct NULL testing is essential for accurate reporting and exception identification.

1. Q: How can you evaluate and strengthen the security of a relational database design?
A: Show answer
Database security should be evaluated through two fundamental dimensions: integrity and confidentiality. Integrity ensures that stored information remains accurate, complete, consistent, and trustworthy. Confidentiality ensures that sensitive information is accessible only to authorized users and applications. A comprehensive security review should examine data types, primary keys, foreign keys, constraints, access permissions, authentication, encryption, and the handling of sensitive information. Start by reviewing the database schema to identify missing constraints, inappropriate data types, weak relationships, and unnecessary duplication. Next, examine user privileges to determine whether each role has only the permissions required for its responsibilities. Finally, review how sensitive information is stored and protected. Security should be considered throughout database design, implementation, testing, deployment, and ongoing maintenance rather than treated as a separate activity after development is complete.

- Integrity protects the correctness and consistency of data.
- Confidentiality protects data against unauthorized access and disclosure.

2. Q: What does data integrity mean in relational database design?
A: Show answer
Data integrity means maintaining the accuracy, completeness, consistency, and reliability of information throughout its lifecycle. In relational databases, integrity is supported through appropriate data types, primary keys, foreign keys, NOT NULL constraints, UNIQUE constraints, CHECK constraints, and other rules that enforce business requirements. For example, a book record should not reference an author who does not exist. A product price should not contain arbitrary text, and a required customer identifier should not be NULL. Integrity controls prevent invalid records from entering the database and reduce the need for application developers to repeatedly check the same conditions. Database constraints should reflect documented business requirements rather than arbitrary assumptions. Integrity also requires appropriate transaction management, validation, monitoring, and controlled access to prevent unauthorized or inconsistent changes.

3. Q: Why are appropriate data types important for maintaining database integrity?
A: Show answer
Data types determine what kind of information a column can store and which operations can be performed on it. Choosing appropriate data types prevents incompatible values, reduces unnecessary storage consumption, and improves the reliability of database operations. For example, an order date should use a DATE or DATETIME-compatible type rather than an unrestricted text column. A quantity should use an appropriate numeric type, while a customer identifier should use a consistent identifier type across related tables. Monetary values generally require an exact decimal representation rather than floating-point approximations when financial precision is important. Data types should also account for the expected range, maximum length, precision, and character requirements. Choosing excessively large types can waste storage, while choosing types that are too small can cause truncation or failed transactions. Data-type decisions should therefore be based on actual business requirements and expected data volumes.

4. Q: Why should every relational database table have a primary key?
A: Show answer
A primary key uniquely identifies each record in a table. It prevents two records from being treated as the same entity and provides a reliable reference for relationships with other tables. For example, an author table can use author_id as its primary key, while a book table stores author_id as a foreign key. A primary key must contain unique values and cannot contain NULL. A well-designed primary key should be stable, consistently represented, and appropriate for the entity being identified. A primary key also normally receives an automatically created supporting index, depending on the database management system. Without a reliable primary key, updating, deleting, referencing, and reconciling individual records becomes more difficult. Composite primary keys can also be appropriate when the combination of multiple columns uniquely identifies a record, such as a purchase_id and product_id combination in a purchase-product junction table.

5. Q: What is a foreign key constraint, and why is it essential for database integrity?
A: Show answer
A foreign key constraint establishes and enforces a relationship between a child table and a referenced parent table. It ensures that a foreign key value corresponds to an existing referenced record, subject to the configured NULL and constraint rules. For example, a book table may contain author_id referencing author.author_id. Without a foreign key constraint, the database could accept a book record referencing an author who does not exist. Such a record is called an orphan record. Foreign keys also help control what happens when referenced records are updated or deleted through actions such as RESTRICT, NO ACTION, CASCADE, and SET NULL, where supported. The appropriate action depends on business requirements. A foreign key should be implemented in the actual database schema because merely showing a relationship in an entity-relationship diagram does not necessarily enforce it.

6. Q: What happens when a child table does not have the required foreign key constraint?
A: Show answer
Without a foreign key constraint, the database may accept records containing references to nonexistent parent records. For example, a book table may contain author_id = 999 even though author 999 does not exist. The database cannot automatically prevent this inconsistency. Applications may display incomplete information, joins may produce unexpected results, and deletion or update operations may leave inconsistent records. Such weaknesses also complicate database maintenance and can create opportunities for malicious or accidental manipulation. The corrective action is to identify and investigate existing orphan records, determine whether they should be corrected or removed, and implement the appropriate foreign key constraint. Before adding the constraint to an existing database, verify that all existing records satisfy the relationship requirements. The database designer should also determine appropriate deletion and update rules.

7. Q: What is database confidentiality, and how can it be protected?

Database confidentiality means protecting information against unauthorized viewing, disclosure, or extraction. Two major approaches are access control and encryption. Access control determines which users and applications can access particular database objects and what operations they can perform. 8. Q: What is the difference between mandatory access control (MAC) and role-based access control (RBAC)?
A: Show answer
Mandatory access control (MAC) determines access through centrally managed security policies and data classifications. Users receive security clearances, while information is assigned sensitivity classifications. Access is permitted only when the established policy authorizes it. Role-based access control (RBAC) assigns permissions to predefined roles and assigns users to those roles. For example, a school database might classify student disciplinary records as highly sensitive under MAC. Under RBAC, it might assign teacher, registrar, analyst, and administrator roles with different permissions. MAC is useful when strict centrally controlled information classification is required. RBAC is particularly practical when many users perform similar organizational functions. The two approaches address access control differently and can be combined in more complex security environments.

9. Q: How does role-based access control work in a relational database?
A: Show answer
RBAC works by grouping database permissions into roles and assigning users to those roles. Instead of granting individual privileges to every user, administrators create roles corresponding to responsibilities. For example, a standard_user role may receive SELECT access to products and INSERT access to purchases and reviews. An analyst role may receive SELECT access to relevant reporting tables. An administrator role may receive the permissions necessary to maintain database records. When a user is assigned a role, the user receives the privileges associated with that role, subject to the database management system's role activation and privilege rules. This approach simplifies administration and supports consistent access policies. Roles should be designed according to actual business responsibilities and should avoid unnecessary combinations of permissions.

13. Q: What are the main SQL steps for implementing role-based access control?
A: Show answer
A typical RBAC implementation follows three main stages. First, create the role using CREATE ROLE. Second, grant the required privileges using GRANT. Third, assign the role to the appropriate database user. For example, a MySQL implementation may use CREATE ROLE standard_user; followed by GRANT SELECT ON database_name.product TO standard_user; and GRANT INSERT ON database_name.purchase TO standard_user;. A user account can then be created and assigned the role using CREATE USER and GRANT standard_user TO the_account. In MySQL 8.0 and later, the DEFAULT ROLE mechanism can be used to configure roles that are activated automatically when the account connects. Syntax and role activation behavior differ among database management systems. Always verify the effective permissions after implementation rather than assuming that assigning a role automatically activates it in every environment.

14. Q: Why should database privileges follow the principle of least privilege?
A: Show answer
The principle of least privilege requires each user, application, and service account to receive only the permissions necessary to perform its assigned functions. It reduces the potential damage caused by compromised credentials, accidental modifications, malicious activity, or software vulnerabilities. For example, an application that only retrieves product information should not receive DELETE privileges on the product table. A reporting account should not receive UPDATE permissions merely because those privileges are convenient to grant. Permissions should be granted at the narrowest practical scope, such as specific tables, views, or operations. Privileges should also be reviewed when users change responsibilities or leave the organization. Excessive permissions increase the attack surface and make it more difficult to investigate unauthorized changes.

15. Q: What is the difference between one-way hashing and symmetric encryption?
A: Show answer
One-way hashing transforms an input into a fixed-length digest that is designed to be computationally infeasible to reverse. It is commonly used for password verification. When a user submits a password, the authentication system verifies the submitted value against the stored password hash using the appropriate password-hashing procedure. Symmetric encryption, by contrast, transforms plaintext into ciphertext using a cryptographic key and allows authorized parties to recover the original information using the appropriate decryption key. Hashing is suitable for information that does not need to be recovered, such as passwords. Encryption is appropriate when the original information must remain retrievable, such as certain sensitive customer details. These techniques serve different purposes and should not be treated as interchangeable security mechanisms.

16. Q: Why should passwords never be stored in plain text?
A: Show answer
Plain-text password storage exposes users to serious security risks if database records are accessed by unauthorized individuals. Attackers who obtain the database may immediately read the original passwords and potentially use them to access other systems where users have reused the same credentials. Passwords should instead be processed using a dedicated password-hashing algorithm such as Argon2id, bcrypt, or PBKDF2, with appropriate work factors and unique salts. Modern password-hashing libraries should manage the salt and verification process. A general-purpose hash such as ordinary SHA-512 should not be used alone as a password-storage mechanism because it is designed for speed rather than resistance to large-scale password guessing. Additional controls should include secure authentication, password reset procedures, rate limiting, and protection against credential theft.

18. Q: What is the difference between hashing and encryption when protecting sensitive database information?
A: Show answer
Hashing is generally a one-way transformation, whereas encryption is designed to permit authorized recovery of the original information. Passwords should generally be hashed because authentication requires verification rather than recovery of the original password. Certain personal or financial information may require encryption because authorized applications need to retrieve the original values. Encryption introduces key-management responsibilities, including secure key storage, access restrictions, rotation, backup, and recovery procedures. Hashing also requires careful algorithm selection, secure implementation, and protection against guessing attacks. The correct choice depends on whether the application needs to retrieve the original information. Choosing encryption for passwords introduces unnecessary recovery capability, while choosing hashing for information that must be displayed or processed in its original form makes the intended application functionality impossible.

24. Q: What is database indexing, and why is it important?
A: Show answer
An index is an additional database structure that helps the database engine locate records more efficiently. Instead of examining every row in a table for certain searches or sorting operations, the database may use an index to identify relevant rows more quickly. 25. Q: How does a standard database index work?
A: Show answer
A standard index maintains an organized representation of selected column values and references to the corresponding table records. When the index is created, the database engine processes the existing table data and builds the required index structure. When a query searches for an indexed value, the optimizer may use that structure to locate relevant records without performing a complete table scan. B-tree indexes are commonly used because they support efficient searching and ordered retrieval. They are useful for equality conditions, range conditions, and many sorting operations. However, the optimizer may choose a table scan when the table is small, a large proportion of rows is required, or the index does not provide an efficient access path. The existence of an index does not guarantee that every query will use it.

32. Q: How should an index be designed for a frequently executed foreign key lookup?
