002 Document Intent
This blueprint defines a production-grade NGO Excel workbook generator that follows the same engineering discipline as a DeckGenerator-style system.
It is not a loose script description.
It is a buildable platform specification covering content contracts, module boundaries, taxonomy governance, sheet archetypes, formulas, validation, printing, reporting, VBA policy, testing, and operational maintenance.
The goal is to make workbook generation repeatable, auditable, and safe for NGO program, finance, M&E, compliance, and operations teams.
003 Engineering Vision
The generator should behave like a workbook compiler.
YAML is the source contract.
The Python engine is the compiler.
The workbook model is the intermediate representation.
The Excel file is the compiled artifact.
The build report is the compiler log.
This separation allows the same content to be rebuilt consistently, tested automatically, and extended without turning every new NGO workbook into a bespoke manual file.
004 Product Scope
The system should generate structured NGO workbooks for donor reporting, budget tracking, M&E indicator tracking, attendance registers, beneficiary registration, procurement tracking, asset registers, compliance evidence tracking, volunteer management, risk registers, issue logs, and monthly reporting packs.
It should support formatted sheets, formulas, dropdown validation, named ranges, print setup, conditional formatting, build reports, and optional macro-enabled output through a controlled template strategy.
005 Explicit Non-Goals
The generator is not intended to become a full database application.
It should not replace a secure case management system for highly sensitive beneficiary data.
It should not rely on VBA as the primary data transformation engine.
It should not silently produce macro-enabled files without explicit configuration.
It should not encourage scattered manual formatting, hardcoded worksheet logic, or undocumented sheet structures that cannot be regenerated from source content.
006 Primary Personas
Program teams need clean activity and progress workbooks.
Finance teams need budget vs actual trackers with variance formulas and donor-friendly print layouts.
M&E teams need indicator catalogs, baselines, targets, actuals, and achievement calculations.
Compliance teams need evidence registers, due dates, owners, and audit trails.
Operations teams need attendance registers, procurement logs, asset registers, and volunteer trackers.
Automation staff need deterministic YAML contracts, CLI tooling, validation output, and regression tests.
007 Primary Use Cases
A country office can generate a quarterly donor report from one YAML manifest and one data extract.
A finance team can rebuild a budget tracker with consistent formulas every month.
An M&E team can generate an indicator workbook with target achievement formulas and dashboard summaries.
A compliance team can generate an evidence register with status dropdowns and conditional formatting.
An operations team can generate attendance sheets with participant counts and printable sign-in areas.
008 Primary MVP
The first MVP should be a Donor Report Workbook Generator.
This is the best first product because it forces the engine to support cover pages, summary tables, finance tables, indicator tables, risk registers, annex trackers, sign-off sheets, formulas, validations, print settings, and optional macro output.
If the donor report works well, the same architecture can be reused for most other NGO workbook families with limited extension.
009 MVP Success Metrics
The MVP is successful if a user can run one command and produce a complete donor report workbook from YAML.
The output should have correct sheet order, consistent formatting, working formulas, dropdown validation, printable sheets, and a build report.
It should require no manual cleanup before sharing.
It should be reproducible from the same input.
It should fail with clear diagnostics when required fields, sheet definitions, formulas, or macro settings are invalid.
010 Secondary MVP
If the organization prioritizes internal learning and measurement over donor reporting, the second-best MVP is an M&E Indicator Tracker.
This workbook validates the engine through indicator definitions, units, baselines, targets, actuals, disaggregation, data sources, verification status, achievement formulas, and dashboard summaries.
It is also an excellent test of taxonomy governance because indicator language varies widely across NGO programs.
011 High-Level Architecture
The architecture should have six layers.
The Content Layer holds YAML manifests and source data references.
The Language Layer holds taxonomy terms, aliases, keywords, and shared labels.
The Model Layer holds workbook, sheet, column, formula, validation, and print objects.
The Render Layer writes Excel output.
The Audit Layer produces validation results and build reports.
The Orchestration Layer coordinates the full pipeline through the CLI.
012 Content Layer Requirements
The Content Layer should store workbook definitions in YAML and keep source data separate where practical.
Inline rows are useful for small examples and tests.
CSV, JSON, or database extract references are better for operational workbooks.
The content layer should be human-readable, version-controlled, and stable enough for non-developer specialists to review and maintain with guidance.
013 Language Layer Requirements
The Language Layer should provide a controlled NGO vocabulary.
It should define preferred terms, aliases, deprecated labels, domain categories, and matching rules.
This layer allows the engine to understand that spend, expenditure, and actual spend may belong to the same financial concept while still enforcing a preferred canonical label in generated sheets.
It also supports consistent archetype inference across workbook families.
014 Model Layer Requirements
The Model Layer should normalize raw YAML into a deterministic internal representation.
It should contain workbook metadata, theme settings, sheet plans, column definitions, formula plans, validation rules, named ranges, print rules, macro requirements, and dependency order.
No renderer should need to reinterpret raw YAML directly.
This protects the system from fragile parsing and makes testing much easier.
015 Render Layer Requirements
The Render Layer should write the final Excel workbook from the workbook model.
It should create sheets in the planned order, write titles and headers, insert data rows, apply styles, configure freeze panes, add formulas, apply data validation, configure conditional formatting, set print options, and save the correct output format.
It should not make high-level content decisions that belong to the builder or validator.
016 Audit Layer Requirements
The Audit Layer should record what happened during the build.
It should report schema errors, semantic warnings, taxonomy matches, sheet archetype decisions, formula coverage, validation coverage, print coverage, macro status, output path, and build duration.
This layer is essential for donor-grade traceability because teams need to know not only that a workbook was generated, but also why it was generated in that exact form.
017 Orchestration Layer Requirements
The orchestration layer should expose a clean CLI and coordinate the pipeline.
It should support arguments such as content path, output path, format, template, theme, report path, validate-only mode, strict mode, verbose logging, and optional macro override.
It should return a non-zero exit code on critical failure so the generator can be used safely in automated batch workflows and future CI checks.
018 Canonical Build Pipeline
The canonical pipeline should be: read CLI arguments, load configuration, read YAML, validate schema, normalize taxonomy terms, infer sheet archetypes, build workbook model, resolve dependencies, plan formulas, plan validations, plan print settings, render sheets, apply styles, insert formulas, apply validation rules, optionally preserve or attach VBA, save output, verify output, and write build report.
Each step should be observable and testable.
019 Deterministic Build Requirement
Given the same YAML manifest, data inputs, template version, generator version, and configuration, the system should produce the same workbook structure and behavior.
Deterministic output supports donor submissions, audit reviews, regression testing, and troubleshooting.
Random sheet order, unstable naming, unpredictable formula insertion, or environment-dependent formatting should be treated as defects.
020 Contract-First Design
The YAML manifest should be treated as the contract between content authors and the generator.
If the contract is valid, the engine should produce a predictable workbook.
If the contract is invalid, the engine should fail fast with actionable diagnostics.
This prevents silent drift and reduces the need for users to guess how the generator interprets ambiguous workbook definitions.
021 Top-Level YAML Schema
The top-level schema should include workbook_name, workbook_type, org_name, project_name, donor_name, reporting_period, currency, language, locale, version, confidentiality_level, theme, sheets, named_ranges, validations, print_config, vba, output, and build_report.
Optional extension blocks should be explicitly documented and versioned so that schema evolution does not break existing workbook definitions.
022 Workbook Metadata Fields
Workbook metadata should define the identity of the generated artifact.
workbook_name should describe the product.
workbook_type should identify the family.
org_name should identify the NGO or partner.
project_name should identify the program or project.
donor_name should identify the funder when relevant.
reporting_period should drive titles and file names.
version should support audit and regeneration.
023 Currency and Locale Fields
currency should control monetary formatting and currency labels.
language should control display labels.
locale should control date formats, number separators, and regional conventions.
These fields should be global defaults that can be overridden at sheet or column level only when necessary.
This is important for NGOs operating across countries, donors, and bilingual program environments.
024 Confidentiality and Audience Fields
confidentiality_level should classify the workbook as public, internal, restricted, or confidential.
audience should identify intended users such as donor, program team, finance team, auditor, or management.
These fields can drive cover sheet labels, warning notes, file naming suffixes, and optional protection policies.
They are especially important for beneficiary registers, safeguarding files, and HR-related workbooks.
025 Theme Block Requirements
The theme block should define visual identity in a controlled way.
It should include font_family, title_color, header_color, accent_color, neutral_color, warning_color, note_color, border_style, and optional print_theme settings.
The theme should not allow unrestricted decorative chaos.
It should produce professional, readable, auditable workbooks that look consistent across all generated NGO workbook families.
026 Sheets Block Requirements
The sheets block should define the workbook narrative in explicit order.
Each sheet entry should declare identity, archetype, content source, columns, formulas, validations, notes, dependencies, visibility, print behavior, and optional macro hooks.
The sheet list should be the primary content structure and should be readable by program staff without requiring deep Python knowledge.
027 Sheet Entry Contract
A sheet entry should support id, type, title, description, source, columns, rows, formulas, validations, styles, notes, print_config, dependencies, visibility, and vba_hooks.
id should be stable and machine-readable.
title should be human-readable.
type should map to a supported archetype.
description should support documentation, auditing, and archetype inference.
All optional fields should be validated when present.
028 Sheet ID Rules
Sheet IDs should be stable identifiers such as cover, summary, budget, indicators, risks, compliance, sign_off.
They should not change casually because formulas, named ranges, dependencies, macros, and tests may reference them.
Titles can change for readability, but IDs should remain stable unless a documented breaking-change process is followed.
029 Sheet Type Rules
Sheet type should map to a known archetype.
The type determines default layout, header behavior, freeze panes, formula opportunities, validation patterns, print settings, and conditional formatting rules.
If a sheet type cannot be resolved, the builder should either fall back to a generic table with a warning or fail in strict mode, depending on configuration.
030 Sheet Description Rules
Sheet description should explain the purpose of the sheet in plain language.
This supports documentation, explainability, and automated matching.
For example, a sheet described as tracking approved amounts, actual expenditure, and remaining balance should strongly indicate a budget or variance archetype rather than a generic table.
031 Source Field Strategy
The source field should define where sheet data comes from.
Supported source types should include inline rows, CSV files, JSON files, JSON payloads, and future database extract references.
The builder should normalize these inputs into a common row model before rendering.
Source references should be validated early to avoid late failures during rendering.
032 Column Contract
Each column should define name, label, type, width, format, source field, formula, validation, visibility, and optional style overrides.
Column names should be stable machine identifiers.
Labels should be display text.
Types should include text, date, currency, number, percent, boolean, status, formula, lookup, and identifier.
This contract allows consistent rendering and validation across workbook families.
033 Row Data Contract
Rows should be represented as structured mappings keyed by column name.
The builder should validate that required columns are present and that values conform to declared types.
Missing values should be rendered as blank or placeholder according to configuration.
Inline rows should be useful for examples and tests, while operational workbooks should prefer external data sources for maintainability.
034 Formula Strategy
Formulas should be declared centrally and generated safely.
The engine should support row-level formulas, summary formulas, cross-sheet formulas, conditional formulas, and named-range formulas.
Formula expressions should be validated before rendering.
The system should avoid brittle hardcoded coordinates unless explicitly declared as fixed anchors in the workbook contract.
035 Formula Library
The formula library should include common NGO calculations.
Examples include variance, remaining budget, burn rate, percent spent, percent achieved, target gap, completion rate, overdue flag, missing evidence flag, count of open risks, count of completed activities, sum by budget line, sum by donor category, and conditional status text.
Each formula should be reusable, named, and testable.
036 Formula Safety Rules
Formula generation should fail when references are missing, column names are unknown, expressions are malformed, or target cells conflict with data regions.
Formula templates should be preferred over raw strings.
Formula results should be checked for likely error patterns such as division by zero, missing lookup values, invalid sheet references, and circular dependencies.
037 Named Range Strategy
Named ranges should be used for important summary cells, validation lists, dashboard anchors, and stable references used by formulas or macros.
Named ranges improve readability and reduce brittleness.
They should be declared in the YAML manifest or generated deterministically by the builder using documented naming conventions.
038 Cross-Sheet Dependency Rules
If a sheet depends on another sheet, the dependency should be declared explicitly.
For example, a dashboard may depend on budget, indicators, and risks.
A compliance summary may depend on a compliance register.
The builder should order sheets and resolve references accordingly.
Undeclared dependencies should be treated as warnings or errors depending on strictness settings.
039 Conditional Formatting Strategy
Conditional formatting should be archetype-aware and rule-driven.
Budget sheets should highlight negative variances or overspend.
M&E sheets should highlight low achievement or missing actuals.
Compliance sheets should highlight overdue evidence.
Risk sheets should highlight high risk scores.
Registers should highlight incomplete owners, missing dates, or stalled statuses.
040 Data Validation Strategy
Data validation should be declared centrally and applied consistently.
It should support dropdown lists, numeric ranges, date constraints, text length limits, required fields, and custom formulas.
Validation values should come from taxonomy-approved lists or configuration sheets.
The generator should avoid scattering manual dropdown values across unrelated sheets.
041 Dropdown Governance
Dropdown values should be governed as shared vocabulary.
Status values, donor categories, site names, risk ratings, evidence types, approval states, and implementation stages should be defined once and reused everywhere.
If a workbook needs local values, they should be declared explicitly and validated against naming rules to prevent inconsistent data entry.
042 Print Strategy
All NGO workbook families should be print-ready.
The generator should support orientation, margins, scaling, fit-to-page, repeat header rows, repeat columns, page breaks, headers, footers, and print areas.
Donor reports and attendance registers should be especially careful about print output because field teams and reviewers often use printed or PDF versions.
043 Page Setup Rules
Table sheets should usually use landscape orientation when wide and portrait when narrow.
Register sheets should repeat header rows.
Cover sheets should fit on one page.
Dashboard sheets should fit on one page where possible.
Budget and indicator tables should use clear page breaks and avoid splitting important summary rows across pages.
044 Export and PDF Strategy
The export layer should support .xlsx and .xlsm output.
It should generate predictable file names, protect against accidental overwrite, verify file creation, and record output metadata.
When PDF export is required, it should be treated as a downstream macro or manual export step unless a controlled automation path is available in the deployment environment.
045 Number Format Library
The number format library should define currency, integer, decimal, percent, ratio, date, text ID, and nullable formats.
Currency formats should respect workbook currency and locale.
Percent formats should be consistent across M&E and finance sheets.
Negative numbers should be visually clear, especially in variance and budget sheets.
046 Date Format Library
Date formats should be locale-aware but predictable.
Common formats should include ISO date, short date, month-year, quarter-year, and reporting period display formats.
Date columns used in registers and timelines should be validated as real dates, not free text, wherever possible.
This improves sorting, filtering, conditional formatting, and audit reliability.
047 Sheet Archetype Catalog
The archetype catalog should include COVER, SECTION, TABLE, BUDGET_TABLE, VARIANCE_TABLE, INDICATOR_TABLE, KPI_DASHBOARD, ATTENDANCE_REGISTER, BENEFICIARY_REGISTER, RISK_REGISTER, COMPLIANCE_TRACKER, PROCUREMENT_TRACKER, ASSET_REGISTER, VOLUNTEER_TRACKER, TIMELINE, LOOKUP_TABLE, DROPDOWN_CONFIG, VALIDATION_RULES, ANNEX_TRACKER, SIGN_OFF, and CLOSING.
Each archetype should have documented behavior.
048 Cover Archetype Rules
The cover archetype should render workbook title, organization, project, donor, reporting period, version, prepared by, generated date, confidentiality label, and optional disclaimer.
It should not contain editable operational tables.
It should be visually clean and printable.
It should use workbook metadata as the primary source of all displayed values.
049 Section Archetype Rules
The section archetype should provide navigational separation between workbook groups.
It can introduce Finance, Program, M&E, Compliance, Risk, Annexes, or Sign-off sections.
It may include a short description, sheet index, or summary metadata.
It should be simple and should not carry complex formulas or data entry regions.
050 Table Archetype Rules
The table archetype should be the default structured data sheet.
It should support headers, rows, filters, freeze panes, column widths, notes, totals, and optional formula columns.
It should be usable for summaries, activity logs, lesson learned tables, staffing tables, and other general NGO workbook content.
051 Budget Table Archetype Rules
The budget table archetype should support budget line, approved budget, actual spend, variance, remaining amount, percent spent, donor category, and notes.
It should apply currency formatting, total rows, variance highlighting, and print-friendly column widths.
It should be compatible with finance review workflows and donor reporting expectations.
052 Variance Table Archetype Rules
The variance table archetype should emphasize explanation and analysis.
It should support approved amount, actual amount, variance, variance percent, explanation, owner, and corrective action.
Conditional formatting should flag significant negative or positive variances.
It is especially useful in grant management and monthly finance packs.
053 Indicator Table Archetype Rules
The indicator table archetype should support indicator code, indicator name, unit, baseline, target, actual, achievement rate, gap, data source, verification status, and notes.
It should calculate achievement safely and handle division by zero or missing target values.
It should support disaggregation references where needed.
054 Dashboard Archetype Rules
The dashboard archetype should summarize key results from detailed sheets.
It should show KPI cards, exception counts, budget burn rate, indicator achievement, open risks, overdue compliance items, and activity progress.
It should not duplicate raw data.
It should use formulas or named ranges to read from source sheets.
055 Attendance Register Archetype Rules
The attendance register archetype should support activity name, date, location, facilitator, participant name, role, gender, age group, organization, signature, attendance status, and notes.
It should include count summaries and printable sign-in layouts.
It should support field use and quick review without excessive formatting.
056 Beneficiary Register Archetype Rules
The beneficiary register archetype should support registration ID, household ID, consent status, location, household size, vulnerability flags, services received, referral notes, and follow-up dates.
It should support confidentiality labels and masked identifiers.
It should not be used for sensitive case management unless organizational policy explicitly allows it.
057 Risk Register Archetype Rules
The risk register archetype should support risk ID, risk description, category, likelihood, impact, risk score, mitigation action, owner, status, due date, review date, and comments.
It should support conditional formatting for high risk scores and overdue reviews.
It should be printable for management and donor review.
058 Compliance Tracker Archetype Rules
The compliance tracker archetype should support requirement ID, requirement description, evidence type, owner, due date, status, evidence location, reviewer, comments, and audit notes.
It should flag missing evidence and overdue items.
It should support audit-friendly sorting, filtering, and stable identifiers.
059 Procurement and Asset Archetype Rules
The procurement tracker archetype should support item, quantity, supplier, request date, approval status, purchase date, delivery date, and status.
The asset register archetype should support asset tag, description, category, location, custodian, purchase date, value, condition, and disposal status.
Both should support stable IDs and dropdown validation.
060 Volunteer Tracker Archetype Rules
The volunteer tracker archetype should support volunteer ID, name, role, team, start date, end date, hours contributed, assignment, status, and recognition notes.
It should support simple summary counts and total hours calculations.
It should respect privacy expectations and avoid unnecessary personal data where possible.
061 Timeline Archetype Rules
The timeline archetype should support milestone, owner, planned start, planned end, actual start, actual end, dependency, status, and completion percent.
It should support date validation and overdue highlighting.
It is useful for implementation plans, donor reporting, compliance milestones, and monthly pack summaries.
062 Config Sheet Archetype Rules
Configuration sheets should store lookup values, dropdown sources, status codes, category lists, site lists, currency lists, evidence types, and rule parameters.
They may be visible or hidden.
If hidden, the workbook model should still document them so testers, auditors, and power users can understand where validation values come from.
063 Sign-off and Closing Archetype Rules
The sign-off archetype should capture prepared by, reviewed by, approved by, date fields, comments, and approval status.
The closing archetype can provide final notes, annex references, distribution list, and next reporting period information.
These sheets should be formal, printable, and stable across reporting cycles.
064 Taxonomy Domains
The taxonomy should include domains for donor, grant, program, project, beneficiary, indicator, baseline, target, actual, budget_line, expense_type, procurement, asset, compliance, audit, risk, issue, volunteer, attendance, safeguarding, reporting_period, approval_status, evidence_type, site, currency, unit_of_measure, and data_quality_status.
Each domain should have preferred terms and aliases.
065 Taxonomy Governance
Every taxonomy term should have a canonical name, human label, optional aliases, domain, status, description, and version.
Deprecated terms should remain documented for historical compatibility but should trigger warnings when used in new manifests.
Term changes should be reviewed because they can affect matching, validation, and generated sheet labels.
066 Alias Management Rules
Aliases should help recognize equivalent language without allowing chaos.
For example, actual spend, expenditure, and spent amount may map to actual_spend.
Aliases should be auditable.
If two aliases conflict or map to different meanings, the validator should raise an error or warning rather than silently choosing one interpretation.
067 Keyword Inference Rules
Keyword inference should help map ambiguous sheet definitions to archetypes.
Financial keywords such as budget, variance, spend, approved, and burn rate should suggest budget archetypes.
M&E keywords such as indicator, baseline, target, actual, and achievement should suggest indicator archetypes.
Compliance keywords such as evidence, requirement, due date, and audit should suggest compliance archetypes.
068 Explainability Requirements
The system should explain why a sheet was assigned to an archetype.
The explanation should include matched keywords, column signals, sheet description signals, and confidence level.
This helps users understand generator behavior and reduces the perception that sheet assignment is random or hidden.
069 Validation Engine Levels
Validation should happen at three levels.
Schema validation checks required fields and structure.
Semantic validation checks meaning, dependencies, formula references, taxonomy terms, and archetype suitability.
Output validation checks the generated workbook model or file for missing sheets, broken references, invalid formulas, and macro-format mismatches.
070 Schema Validation Rules
Schema validation should reject manifests missing workbook_name, workbook_type, sheets, or required sheet fields.
It should reject duplicate sheet IDs, unsupported sheet types, invalid column types, unknown top-level blocks, and malformed source references.
It should produce error messages with precise locations so authors can fix problems quickly.
071 Semantic Validation Rules
Semantic validation should catch content that is structurally valid but logically weak.
Examples include dashboard sheets with no source dependencies, budget sheets without currency columns, risk registers without owner or status, compliance trackers without due date, and indicator tables without target or actual columns.
These issues can be warnings in lenient mode or errors in strict mode.
072 Output Validation Rules
Output validation should confirm that the planned workbook was actually produced.
It should check sheet count, sheet order, required sheets, named ranges, formula presence, validation presence, print settings, output format, and macro preservation when requested.
Output validation is important for donor-grade reliability and regression testing.
073 Error Taxonomy
The error taxonomy should include schema_error, source_error, taxonomy_error, archetype_error, formula_error, validation_error, render_error, export_error, macro_error, and permission_error.
Each error should have a code, message, location, and suggested remedy.
This makes the generator easier to operate and easier to integrate into automated pipelines.
074 Warning Taxonomy
The warning taxonomy should include missing_optional_field, unknown_alias, low_match_confidence, empty_data_source, duplicate_label, deprecated_term, print_setting_missing, formula_coverage_low, validation_coverage_low, and macro_template_not_found.
Warnings should not block builds by default, but strict mode should promote selected warnings to errors.
075 Build Report Specification
The build report should record workbook name, source file, generator version, template version, taxonomy version, output file, output format, sheet count, archetype summary, warnings, errors, formula count, validation count, named range count, print coverage, macro status, build duration, and final status.
It should be written as JSON, Markdown, or both.
076 Logging Specification
Logging should be structured and level-based.
Debug logs should show matching and model decisions.
Info logs should show major pipeline steps.
Warning logs should show recoverable issues.
Error logs should show failures with context.
Logs should not contain sensitive beneficiary or safeguarding data unless explicitly sanitized and required for diagnostics.
077 Testing Strategy
The project should include unit tests, schema tests, taxonomy tests, formula tests, rendering tests, export tests, and golden workbook tests.
Tests should cover valid manifests, invalid manifests, missing sources, macro mismatches, duplicate sheet IDs, broken formulas, and edge cases such as empty rows or missing targets.
Testing is what turns the generator from a convenience script into a trusted platform.
078 Golden Workbook Tests
Golden workbook tests should compare generated output structure against approved reference definitions.
They should check sheet names, sheet order, column headers, named ranges, formula presence, validation presence, and output format.
They do not need to compare every binary property, but they should detect meaningful structural regressions.
079 Versioning Strategy
The generator version, template version, taxonomy version, and manifest version should be recorded in the build report and workbook metadata.
Versioning supports audit trails and reproducibility.
When defaults change, the change should be documented and, where possible, controlled through explicit version selection.
080 Security Requirements
The generator should not bypass Excel security settings.
Macro output should be explicit.
Template locations should be trusted and documented.
Generated macro-enabled files should be labeled clearly.
Sensitive workbooks should support confidentiality metadata and restricted distribution notes.
The system should never silently inject macros into output files.
081 Confidentiality Rules
Confidential workbooks should display appropriate labels on the cover sheet and headers where configured.
Beneficiary and safeguarding workbooks should encourage masked identifiers, minimal personal data, and controlled access.
The generator should support confidentiality levels but leave access control and data governance to the organization’s wider security policies.
082 Localization Requirements
Localization should support translated labels, locale-specific date formats, number separators, currency display, and regional reporting conventions.
The engine should keep canonical field names stable while allowing display labels to change by language.
This allows bilingual workbooks and country-specific templates without breaking the model.
083 Accessibility Requirements
Generated workbooks should be readable and navigable.
Headers should be clear.
Colors should not be the only signal for exceptions.
Text should have sufficient contrast.
Sheet names should be meaningful.
Print output should preserve logical order.
These practices help reviewers, auditors, and field users who may rely on printed or screen-reader-assisted workflows.
084 Performance Requirements
The generator should perform well for typical NGO workbooks with dozens of sheets and thousands of rows.
It should avoid repeated full-file scans, inefficient formula string construction, and unnecessary style duplication.
Large workbooks should stream or batch data where possible, and validation should fail early when critical errors are detected.
085 Scalability Requirements
The platform should scale from one workbook family to many without redesign.
New workbook families should be added through YAML manifests, archetype configuration, taxonomy terms, and documentation.
Core engine changes should be reserved for generic capabilities such as new formula patterns, new validation types, or new output behaviors.
086 Extensibility Rules
Extension points should include new sheet archetypes, new formula templates, new validation rules, new taxonomy domains, new workbook families, new theme tokens, and new output formats.
Extensions should be registered explicitly and documented.
The system should avoid monkey-patching behavior or special-case code hidden inside unrelated modules.
087 Anti-Patterns to Avoid
Avoid hardcoded sheet names inside formulas without declared references.
Avoid VBA performing core data transformation.
Avoid manual formatting that cannot be regenerated.
Avoid duplicate dropdown lists scattered across sheets.
Avoid ambiguous taxonomy terms without canonical mapping.
Avoid macro output being created when the user requested standard workbook output.
088 VBA Strategy
VBA is supported only when the output format is macro-enabled.
The safest production pattern is a trusted .xlsm template containing stable macros.
Python fills workbook content and preserves the macro project where supported.
VBA should assist the user after generation, not replace the generator.
Macro behavior should be explicit, documented, and security-conscious.
089 Template-Based Macro Pattern
The recommended macro pattern uses a macro-enabled template.
The template contains approved VBA modules, buttons, and workbook-level behaviors.
The generator opens the template, writes generated sheets, preserves existing VBA where supported, and saves a new .xlsm output.
This reduces risk and avoids fragile runtime VBA source generation.
090 VBA Module Organization
VBA source should be organized by responsibility.
modReport can handle report preparation and refresh.
modBudget can handle budget checks and finance navigation.
modDashboard can handle dashboard refresh and export helpers.
modCompliance can handle compliance checks and evidence status summaries.
Modules should be version-controlled and mapped to workbook families.
091 Macro Security Policy
Macro-enabled files can be blocked by security policies.
The system should warn when generating .xlsm output.
It should recommend trusted template locations, digital signing where possible, and controlled distribution.
It should not attempt to disable Excel security features or bypass user protections.
Macro usage should be optional and clearly documented.
092 COM Automation Option
Windows COM automation with Excel and pywin32 can be used when direct VBA injection or advanced workbook automation is required.
This path requires Windows, installed Excel, trusted VBA object model access, and careful error handling.
It should be treated as an advanced optional integration, not the default generator architecture.
093 Template Lifecycle Management
Templates should be versioned, documented, and stored in controlled locations.
Template changes should be reviewed because they can affect macros, styles, print behavior, and output compatibility.
A template registry should record template ID, version, intended workbook families, macro status, and last review date.
094 Output Naming Rules
Output file names should be generated from workbook metadata.
A predictable pattern is workbook_type, project, reporting_period, version, and format extension.
Examples include donor_report_q2_2026.xlsx and donor_report_q2_2026.xlsm.
Macro-enabled and standard outputs should be clearly distinguishable to prevent accidental distribution of the wrong format.
095 CLI Design
The CLI should support build_workbook.py with arguments such as --content, --output, --format, --template, --theme, --report, --validate-only, --strict, --verbose, and --version.
The CLI should be scriptable and predictable.
It should return clear exit codes and produce a build report even when validation fails, unless the failure is unrecoverable.
096 Module Responsibility Summary
build_workbook.py orchestrates the pipeline.
config.py centralizes settings.
workbook.py defines the domain model.
builder.py plans the workbook.
render.py writes Excel output.
formatting.py manages styles.
validation.py checks content and model.
formulas.py builds formula logic.
export.py saves output.
vba.py manages macro behavior.
reporting.py writes build reports.
097 Documentation Requirements
The project should document taxonomy terms, sheet archetypes, YAML fields, formula conventions, validation rules, naming rules, VBA policy, and troubleshooting steps.
Documentation should be written for mixed NGO teams, not only developers.
Every major schema field should have purpose, allowed values, example usage, and failure behavior.
098 Operational Runbook
The operational runbook should explain how to build a workbook, validate content, interpret build reports, regenerate failed outputs, update templates, update taxonomy terms, and safely distribute macro-enabled files.
It should include common commands, expected outputs, escalation paths, and rollback steps when a template or taxonomy change causes regression.
099 Troubleshooting Guide
The troubleshooting guide should cover missing YAML fields, duplicate sheet IDs, unknown sheet archetypes, broken formulas, missing source files, macro format mismatch, blocked macros, print layout issues, empty data rows, taxonomy alias conflicts, and output overwrite failures.
Each issue should include cause, diagnostic location, and recommended corrective action.
100 Implementation Roadmap
Phase 1 should deliver core YAML parsing, workbook model, basic archetypes, .xlsx rendering, validation, and build report.
Phase 2 should add formulas, named ranges, conditional formatting, print optimization, taxonomy inference, and sample NGO workbook families.
Phase 3 should add macro-enabled templates, VBA policy enforcement, golden tests, localization, and advanced governance.
101 Phase 1 Deliverables
Phase 1 should include build_workbook.py, config.py, workbook.py, builder.py, render.py, formatting.py, validation.py, export.py, reporting.py, one donor report YAML, one budget tracker YAML, one output folder, one build report, and basic documentation.
The goal is a reliable .xlsx generator before adding macro complexity.
102 Phase 2 Deliverables
Phase 2 should include formula templates, validation lists, conditional formatting, print settings, taxonomy matching, explain_match script, audit scripts, and at least three workbook families.
This phase should prove that the engine is reusable and not limited to a single donor report layout.
103 Phase 3 Deliverables
Phase 3 should include macro-enabled template support, VBA documentation, macro preservation checks, golden workbook tests, versioned templates, localized labels, and advanced reporting.
This phase makes the system suitable for repeated donor submissions, audit support, and multi-country NGO use.
104 Acceptance Criteria
The generator is acceptable when it can build a workbook from YAML without manual cleanup.
It must validate input, produce deterministic sheet order, apply styles, insert formulas, apply validations, configure print settings, save the correct format, and write a build report.
If macros are requested, it must produce macro-enabled output and preserve approved template macros.
105 Definition of Done
A workbook family is done when it has a YAML manifest, documented sheet catalog, formula definitions, validation rules, print configuration, sample output, passing tests, build report, and user-facing notes.
If macro support is included, it must also have a documented template, macro list, security note, and macro-preservation verification.
106 Risks and Mitigations
Risk: macro security blocks output.
Mitigation: use trusted templates and document signing.
Risk: YAML ambiguity causes wrong archetypes.
Mitigation: add explainability and strict mode.
Risk: formulas become brittle.
Mitigation: use named ranges and formula templates.
Risk: sensitive data is mishandled.
Mitigation: add confidentiality labels and minimal data principles.
107 Final Engineering Rule
YAML defines the workbook contract.
The workbook model defines the build plan.
The renderer writes the Excel artifact.
The validator protects quality.
The taxonomy governs language.
The build report proves what happened.
VBA remains optional and controlled.
This separation creates a maintainable NGO Excel generation platform that can scale across programs, donors, countries, and reporting cycles.
108 Expanded Repository Structure
Add schemas, migrations, packs, governance, ci, and docs/runbooks to the core structure.
schemas should hold JSON Schema and Pydantic contract definitions.
migrations should hold taxonomy and manifest upgrade paths.
packs should hold donor, country, language, theme, and workbook-family content packs.
ci should hold pipeline definitions, lint configurations, and golden-test automation.
109 Expanded Domain Model
The model should include WorkbookSpec, SheetSpec, ColumnSpec, RowData, SourceSpec, FormulaSpec, ValidationSpec, PrintSpec, ThemeSpec, TaxonomyTerm, BuildResult, and AuditEvent.
Each object should be typed, testable, and serializable.
This makes the generator easier to extend without weakening the core contract.
110 Manifest Schema Registry
Every manifest should declare a schema_version.
The registry maps schema versions to validation rules, migration logic, and supported feature sets.
This prevents silent interpretation changes when the YAML contract evolves.
111 JSON Schema Governance
JSON Schema should define structural constraints, required fields, allowed values, and pattern rules.
It should be used by editors, CI, and validation tooling.
Schema files should be versioned and documented alongside the generator code.
112 Pydantic Model Layer
Python validation should use typed models such as Pydantic or dataclasses with explicit validators.
These models should convert raw YAML into a safe internal representation.
They should reject unknown fields in strict mode and surface field-level diagnostics.
113 Content Lifecycle States
Each workbook manifest should support lifecycle states such as draft, review, approved, published, deprecated, and archived.
Lifecycle state can drive build behavior, distribution readiness, and audit labeling.
Only approved manifests should be used for formal donor submissions.
114 Content Review Workflow
Manifest changes should follow a review workflow with content owner, technical reviewer, and program approver roles.
Changes to taxonomy, formulas, archetypes, or print behavior should require additional review.
Pull requests should include build report output and sample generated workbook evidence.
115 Manifest Linting Rules
The linter should check style, naming, ordering, required metadata, duplicate IDs, missing descriptions, weak sheet descriptions, empty sources, and deprecated terms.
Lint output should be machine-readable for CI and human-readable for content authors.
Lint rules should be configurable by severity.
116 Dry Run Mode
Dry run mode should validate and plan the workbook without writing the final Excel file.
It should output the planned sheet order, archetype assignments, formula coverage, validation coverage, and warnings.
This helps users catch contract issues before generating production artifacts.
117 Preview Mode
Preview mode should generate a lightweight output for review, such as a reduced workbook, HTML summary, or Markdown build preview.
It should not replace the final artifact.
Its purpose is fast inspection of structure, labels, and major formula decisions.
118 Diff Mode
Diff mode should compare two builds or two manifests and report changes in sheets, columns, formulas, validations, named ranges, print settings, taxonomy terms, and output format.
This is essential for template upgrades and quarterly manifest changes.
119 Structural Hash Strategy
Each workbook model should produce a stable structural hash based on sheet order, column definitions, formula templates, validation rules, named ranges, and print settings.
The hash should support regression detection without comparing volatile binary content.
120 Golden Baseline Management
Golden baselines should be approved reference outputs for each workbook family.
They should include manifest, expected structural hash, sheet catalog, formula inventory, validation inventory, and build report.
Golden baselines should be reviewed whenever deliberate changes are introduced.
121 Regression Gate Policy
CI should fail when structural changes occur without an approved golden update.
Warnings may be allowed in non-blocking mode, but errors should block merges.
Macro-preservation failures, broken formulas, and missing sheets should always be regression blockers.
122 CI Pipeline Pattern
The CI pipeline should run schema validation, linting, unit tests, taxonomy checks, formula tests, render tests, golden comparisons, and security checks.
It should produce build reports and sample artifacts for review.
Pipelines should be runnable on pull requests and scheduled main builds.
123 Artifact Publishing Strategy
Generated workbooks, build reports, and validation logs should be published as versioned artifacts.
Artifacts should be tied to manifest version, generator version, taxonomy version, and pipeline run ID.
This supports audits and reproducible rebuilds.
124 Environment Configuration
The generator should support environment-specific settings for paths, template locations, logging level, strictness, and output behavior.
Environment configuration should be explicit and not hidden in code.
Development, test, and production environments should behave predictably.
125 Secrets Handling
The system should not store donor credentials, beneficiary data, or production database passwords inside manifests or source code.
Secrets should come from environment variables or secret managers.
Sample fixtures should use synthetic data only.
126 Build Reproducibility Rules
A rebuild should be reproducible when the manifest, data inputs, templates, taxonomy, generator version, and configuration are unchanged.
Any nondeterministic behavior should be treated as a defect.
Reproducibility supports audits, donor trust, and regression testing.
127 Deterministic Timestamp Policy
Generated timestamps should be controlled.
Use a fixed generated_at value, build date input, or SOURCE_DATE_EPOCH style policy when reproducibility is required.
Cover sheets should not change only because the build time changed unless intentionally configured.
128 Build Correlation ID
Each build should receive a unique build ID or correlation ID.
The ID should appear in logs, build reports, output metadata, and error messages.
This makes troubleshooting easier across CLI runs, CI jobs, and support requests.
129 Observability Requirements
The generator should emit structured logs, timing metrics, stage results, error codes, and warning counts.
Observability should help operators understand where builds slow down or fail.
It should not rely on unstructured print statements for production diagnostics.
130 Telemetry Privacy Rules
Telemetry should never include beneficiary names, personal identifiers, safeguarding details, or confidential narrative content.
It may include anonymized counts, error types, build duration, archetype usage, and feature flags.
Privacy-safe telemetry supports product improvement without data exposure.
131 Performance Budget
Typical workbook builds should complete within defined time and memory budgets.
Performance tests should monitor large manifests, many sheets, large row counts, and complex formula plans.
Performance regressions should be visible in CI.
132 Excel Limit Guardrails
The generator should guard against Excel limits such as sheet name length, worksheet row limits, formula length, excessive conditional formatting, and too many data validations.
It should fail early with clear guidance instead of producing broken files.
133 Sheet Name Guardrails
Sheet names should be limited to safe lengths, avoid invalid characters, and remain stable for references.
The generator should detect duplicate display titles and duplicate IDs separately.
Sheet renaming should preserve stable IDs wherever possible.
134 Formula Compatibility Rules
The formula engine should target functions supported by the organization’s Excel environment.
If newer dynamic array functions are used, compatibility should be explicit.
Fallback formulas should be documented when older Excel versions must be supported.
135 Locale Aware Formula Rules
Formula strings should be generated with awareness of Excel locale behavior, separators, and function compatibility.
The model should keep canonical formulas stable while adapting safely to the target Excel environment.
Locale assumptions should be documented and tested.
136 Named Range Governance Expansion
Named ranges should be grouped by purpose such as summary anchors, validation lists, dashboard inputs, and macro references.
Naming should include workbook family, sheet ID, and field purpose where useful.
Generated names should be stable and documented.
137 Hidden Admin Sheet Pattern
Hidden admin sheets can store taxonomy versions, build metadata, validation lists, and configuration parameters.
They should be documented and recoverable by auditors or power users.
They should not contain editable operational data unless explicitly intended.
138 Workbook Metadata Sheet
A metadata sheet should show workbook name, type, organization, project, donor, period, currency, locale, confidentiality, generator version, template version, taxonomy version, and build ID.
This supports traceability without opening file properties or build reports.
139 README Sheet Pattern
A README sheet should explain how to use the workbook, which sheets are editable, which sheets are generated, and where dropdown values come from.
It should include warnings about macro content, confidentiality, and print behavior where relevant.
140 Change Log Sheet Pattern
A change log sheet can summarize manifest version, generation date, owner, major changes, and approval status.
It is useful for recurring donor reports and monthly packs.
It should be generated from manifest metadata rather than manually maintained where possible.
141 QA Checklist Sheet Pattern
A QA checklist sheet should guide reviewers through checking totals, formulas, dropdowns, print output, sign-off fields, confidentiality labels, and annex completeness.
It should be printable and easy to use by non-technical staff.
142 Data Dictionary Requirements
Each workbook family should have a data dictionary describing fields, labels, types, allowed values, source system, sensitivity, and stewardship owner.
The dictionary should align with the taxonomy and YAML contracts.
It supports onboarding, audits, and data quality reviews.
143 Canonical Identifier Strategy
Important entities such as indicators, budget lines, risks, requirements, assets, and activities should use canonical IDs.
Canonical IDs should be stable, human-readable where possible, and resistant to label changes.
This protects formulas, lookups, and cross-sheet references.
144 Stable Reference Model
References between sheets should prefer stable IDs and named ranges over raw cell coordinates.
When coordinates are unavoidable, they should be generated from deterministic layout rules.
This reduces brittleness when rows are added or reordered.
145 Source Extract Contract
External data extracts should have a documented contract including file format, encoding, delimiter, required columns, date format, identifier format, and row count expectations.
The generator should validate extracts before rendering.
Extract contracts should be versioned with the manifest.
146 CSV Ingestion Rules
CSV ingestion should enforce UTF-8 encoding unless explicitly configured otherwise.
It should validate headers, detect duplicate columns, handle blank values, and reject malformed rows.
Date and currency parsing should follow declared locale rules.
147 JSON Ingestion Rules
JSON ingestion should support objects, arrays, nested field mapping where documented, and explicit null handling.
It should reject unexpected structures in strict mode.
JSON sources are useful for APIs, test fixtures, and structured metadata.
148 Database Extract Rules
Database extracts should be treated as read-only inputs with documented queries or view contracts.
The generator should not require live database access for basic workbook generation unless explicitly configured.
Extract freshness and extraction timestamp should be recorded.
149 API Integration Boundary
API integration should be optional and separate from the core generator.
API adapters should fetch, normalize, and store extracts for the builder.
The core generator should remain testable without live external services.
150 ERP Integration Boundary
Finance or ERP integrations should provide budget, actuals, procurement, or asset extracts.
The generator should not write back to ERP systems unless a controlled integration exists.
Integration output should include source system, extract date, and record counts.
151 Power BI Integration Boundary
Power BI can consume generated Excel models, lookup tables, or structured extracts for dashboards.
The generator should not assume Power BI is available for workbook generation.
Where used, Power BI datasets should respect the same taxonomy and data dictionary.
152 SharePoint Distribution Pattern
SharePoint can be used for controlled storage, version history, and distribution.
The runbook should define folder structure, naming rules, access groups, and retention.
Generated files should not be manually renamed outside the governed pattern.
153 Teams Distribution Pattern
Teams can distribute final reports and build notifications.
Distribution should use approved channels and avoid sending restricted or confidential workbooks to unauthorized groups.
Automated messages can include build status, warnings, and report links.
154 File Naming Governance
File names should be generated from metadata and include workbook family, project or donor, reporting period, version, and confidentiality suffix where needed.
Names should be predictable, sortable, and safe across operating systems.
Manual renaming should be discouraged.
155 Retention and Archiving
Retention rules should define how long manifests, data extracts, outputs, and build reports are kept.
Donor and audit requirements should drive retention periods.
Archived workbooks should remain readable or accompanied by generation metadata.
156 Backup and Recovery
Source manifests, taxonomy files, templates, golden baselines, and critical outputs should be backed up.
Recovery tests should confirm that a workbook family can be rebuilt from source.
Backup scope should include configuration and documentation, not only Excel files.
157 Audit Evidence Packaging
An audit pack can include manifest, data extracts, build report, generated workbook, golden comparison, sign-off record, and distribution log.
This makes it easier to prove how a donor report was produced.
Audit packs should be versioned and access-controlled.
158 Digital Signature Policy
Where required, generated workbooks or PDF exports should support digital signature or approval evidence.
Signature policy should define who can sign, when to sign, and how signature status is recorded.
Macro-enabled files may require additional signing controls.
159 PDF/A Export Policy
PDF/A export can be used for long-term archiving of donor reports and sign-off copies.
The export should preserve pagination, labels, and confidentiality markings.
PDF generation should be automated only in supported environments.
160 Data Minimization Rules
Workbooks should include only the fields needed for the reporting or operational purpose.
Avoid unnecessary personal data, sensitive beneficiary details, or excessive narrative fields.
Data minimization reduces privacy risk and file complexity.
161 PII Handling Rules
Personally identifiable information should be classified, masked where possible, and protected by confidentiality labels.
PII should not appear in logs, build reports, telemetry, or test fixtures.
Access should follow organizational policy and local law.
162 Safeguarding Data Rules
Safeguarding-related content should receive the highest caution.
Use restricted workbooks, minimal identifiers, controlled distribution, and explicit approval steps.
The generator should support confidentiality flags but cannot replace safeguarding case management controls.
163 GDPR Alignment
Where GDPR or similar rules apply, the system should support purpose limitation, data minimization, retention, access control, and deletion workflows.
Manifests should not embed personal data unless necessary and approved.
Data subject rights processes remain outside the generator but should be considered.
164 Consent and Purpose Limitation
If beneficiary data is included, the workbook should document the lawful basis or consent purpose where known.
Fields should be limited to the approved purpose.
Secondary use of data should require governance review.
165 Access Control Boundaries
The generator should not manage user permissions directly.
It should output files that can be secured through SharePoint, file systems, or document management policies.
Confidentiality metadata should inform access decisions but not replace them.
166 Data Quality Framework
Data quality checks should cover completeness, uniqueness, validity, timeliness, consistency, and referential integrity.
The generator can enforce structural validity, while data stewards remain responsible for operational accuracy.
Build reports should summarize data quality warnings.
167 Data Lineage Requirements
The build report should show which manifest, data source, taxonomy version, template, and formula pack produced each workbook.
For critical sheets, lineage should include source extract identifiers and record counts.
Lineage supports audits and troubleshooting.
168 Data Stewardship RACI
Define responsible, accountable, consulted, and informed roles for manifests, taxonomy, templates, data extracts, and generated outputs.
Program, finance, M&E, compliance, and IT should have clear ownership boundaries.
RACI reduces confusion during reporting cycles.
169 Taxonomy Board Governance
A taxonomy board should review new terms, aliases, deprecated labels, and domain changes.
Changes should be versioned and released with migration notes.
The board protects consistency across workbook families and country offices.
170 Alias Conflict Resolution
When two aliases map to the same canonical term, the system should accept them with traceability.
When the same alias could map to multiple terms, the system should raise an error or require disambiguation.
Silent conflict resolution should be forbidden.
171 Controlled Vocabulary Releases
Taxonomy updates should be released as versioned vocabulary packs.
Each release should include new terms, deprecated terms, alias changes, and impact analysis.
Workbooks should pin vocabulary versions for reproducibility.
172 Donor Profile Strategy
Donor profiles can define reporting labels, currency preferences, required sheets, sign-off fields, confidentiality expectations, and template variations.
Profiles should be reusable across projects.
They reduce duplicate YAML and improve donor consistency.
173 Country Profile Strategy
Country profiles can define locale, language, currency, statutory labels, site lists, and distribution conventions.
They should combine with donor profiles without creating uncontrolled variation.
Country-specific exceptions should be explicit and versioned.
174 Language Pack Strategy
Language packs should translate display labels while preserving canonical field names.
They should cover sheet titles, headers, statuses, dropdown labels, cover text, and warnings.
Translations should be reviewed by program or communications owners.
175 Theme Pack Strategy
Theme packs should provide approved fonts, colors, border styles, and print-safe variants.
They should support organization branding and donor branding where needed.
Themes should remain constrained to avoid visual inconsistency.
176 Template Variant Strategy
Template variants can support standard, macro-enabled, donor-branded, print-optimized, and localized outputs.
Each variant should have an ID, version, and approved workbook families.
Variants should be tested like code artifacts.
177 Custom Archetype Registration
New archetypes should be registered with layout rules, default columns, formula opportunities, validation patterns, print behavior, and examples.
They should pass unit and golden tests before production use.
Ad hoc sheet logic should not bypass archetype governance.
178 Plugin Architecture
The generator can support plugins for formula packs, validation packs, archetypes, exporters, and data adapters.
Plugins should be explicitly registered and versioned.
Core behavior should remain stable and protected from uncontrolled extensions.
179 Hook System
Hooks can run before validation, after model build, before render, after export, or after report generation.
Hooks should be used for notifications, custom checks, or artifact publishing.
They should not be used to silently alter workbook content without audit.
180 Final Expanded Operating Rule
The expanded platform should be governed as a product, not a script.
Contracts, taxonomy, templates, tests, build reports, security rules, and operational runbooks should all be maintained together.
This turns NGO Excel generation into a reliable, auditable, and scalable capability.

It is an exceptional, enterprise-grade specification. It elevates Excel generation from ad-hoc scripting to a deterministic compilation process (YAML → Model → Artifact).
Key Strengths:
Compiler Architecture: Separation of Content, Model, and Render layers ensures reproducibility and testability.
Auditability: Golden tests, structural hashes, and build reports solve the "black box" problem of data pipelines.
Domain Alignment: Archetypes (M&E, Budget, Compliance) perfectly map to actual NGO workflows.
Security: Strict PII/GDPR boundaries and controlled macro policies prevent critical compliance failures.
Risks & Bottlenecks to Watch:
Authoring Friction: Non-technical NGO staff will struggle with raw YAML. You will eventually need a frontend UI, strict IDE linting, or a form-to-YAML bridge.
VBA Fragility: Excel's Trust Center and cross-platform (Mac vs. Windows) macro blocking are notoriously unpredictable. Lean heavily on standard .xlsx and treat .xlsm as a strict opt-in.
Over-Engineering: The scope is massive. Phase 1 must be ruthlessly defended to prevent "analysis paralysis."
Verdict: A masterclass in domain-driven design for data operations. It is highly viable, deeply necessary for NGO scale, and ready for Phase 1 execution.
