Reusable Object-Oriented Design: Foundations, Patterns, and Design Decisions
1. Q: What is a design pattern in object-oriented software design?
A: Show answer
A design pattern is a reusable description of a proven arrangement of communicating classes and objects that addresses a recurring design problem in a particular context. It is not a finished component that can simply be copied into every application. It identifies the problem and circumstances in which a solution is useful, describes the abstract elements and collaborations that make up the solution, and explains the consequences of adopting it. The same pattern can be implemented differently in different systems while retaining its essential structure and intent. Patterns capture design experience so that developers can recognize a problem, draw on a known solution, and avoid rediscovering the same design ideas. Their value lies in reusable design knowledge, not merely in reusable source code.

Study instruction:
- "Explain the difference between reusing a design idea and copying a concrete implementation."

Key point:
- A pattern is contextual, abstract design guidance rather than a universal code recipe.
- Its problem, solution, and consequences must be considered together.
2. Q: Why is designing reusable object-oriented software difficult, even for experienced developers?
A: Show answer
Reusable design requires several decisions to be balanced at once: which concepts should become objects, how large or small classes should be, what interfaces they should expose, how inheritance hierarchies should be organized, and how objects should collaborate. A design must solve the present problem without becoming so specific that it cannot accommodate plausible future requirements. These goals can conflict with performance, simplicity, and ease of implementation. The chapter emphasizes that a flexible design is rarely correct on the first attempt. Experienced designers commonly apply a design, reuse it in another situation, observe where it needs adjustment, and refine it. Reusability therefore emerges through experience, evaluation, and iteration rather than through a single act of prediction.

Study instruction:
- "Identify a design you have revised after using it in a second context and record what the second use revealed."

Key point:
- Reusable design involves trade-offs and iterative refinement.
- A design should be validated through use rather than assumed reusable because it is abstract.
3. Q: What four essential elements make up a design pattern?
A: Show answer
The chapter identifies four essential elements. First, the pattern name provides a concise handle for discussing the problem, solution, and consequences. Second, the problem explains the circumstances and context in which the pattern applies, including conditions that should be present. Third, the solution describes the participating elements, their relationships, responsibilities, and collaborations at an abstract level rather than prescribing one concrete implementation. Fourth, the consequences explain the results and trade-offs of using the pattern. These consequences may include effects on flexibility, extensibility, portability, implementation complexity, space, and execution time. Omitting any element weakens the pattern description: a name without context is ambiguous, a solution without applicability can be misused, and a solution without consequences hides its costs.

Study instruction:
- "Take one familiar pattern and write a short description under the four headings: name, problem, solution, and consequences."

Key point:
- The four elements are name, problem, solution, and consequences.
- Consequences are essential to evaluating whether the solution is worth adopting.
4. Q: How does a design pattern differ from a reusable data structure or a complete application architecture?
A: Show answer
The patterns in the chapter occupy a middle level of abstraction. They are not concrete reusable data structures such as linked lists or hash tables that can be implemented as classes and used substantially as-is. Nor are they complete, domain-specific architectures for an entire application or subsystem. Instead, they describe arrangements of communicating classes and objects that can be customized to solve recurring design problems in different contexts. A pattern may influence a part of an architecture, and its implementation must be created for each use. This distinction prevents developers from treating every useful abstraction as a design pattern or expecting a pattern catalog to provide a complete architecture.

Study instruction:
- "Classify examples from your codebase as reusable data structures, design patterns, or larger architectural frameworks, and justify each classification."

Key point:
- Design patterns are abstract design structures between low-level reusable components and full application architectures.
- A pattern must be adapted and implemented in its application context.
5. Q: Why does the context of a design pattern matter?
A: Show answer
A pattern is useful only when the problem and conditions it addresses are present. The same arrangement of classes can be beneficial in one context and unnecessary or harmful in another. Context includes the design pressure, existing constraints, desired variation, and responsibilities of the participating objects. The chapter's definition therefore treats a pattern as a solution to a problem in a context, not as an isolated structure. Applicability conditions help a designer distinguish a genuine need from superficial resemblance. For example, introducing interchangeable strategies makes sense when algorithm variation is required; it adds indirection without benefit if the algorithm is stable and there is no credible need to vary it.

Study instruction:
- "Write down the problem conditions that would justify applying a pattern before sketching its class structure."

Key point:
- A pattern is not a context-free recipe.
- Check the problem and applicability conditions before introducing the pattern.
6. Q: What are the three principal roles in the Smalltalk Model/View/Controller design?
A: Show answer
MVC separates a user-interface design into three kinds of objects. The Model is the application object and holds or represents the application data and behavior. The View is the screen presentation of the model. The Controller defines how the interface reacts to user input. Earlier interface designs often combined these responsibilities, making changes to presentation or interaction more likely to affect application logic. MVC separates them so that different presentations and input behaviors can be developed or replaced with less disturbance to the underlying application object. The three roles are related but not interchangeable: the model represents application state, the view presents it, and the controller mediates user interaction.

Study instruction:
- "Take a screen in an application and identify which responsibilities belong to its model, view, and controller or equivalent components."

Key point:
- MVC separates application state, presentation, and input response.
- Separation allows presentation and interaction choices to evolve more independently.
7. Q: How does the Observer pattern appear in the MVC example?
A: Show answer
MVC connects a model and its dependent views through a subscribe-and-notify protocol. A view registers its interest in the model and is responsible for keeping its presentation consistent with model state. When the model's data changes, it notifies the dependent views, which can then retrieve the relevant values and update themselves. The model need not know the concrete presentation details of every view. The chapter illustrates the arrangement with a single model displayed as a spreadsheet, histogram, and pie chart. The broader Observer idea is a one-to-many dependency: a change in one object can notify multiple dependents without requiring the changed object to contain detailed knowledge of them.

Study instruction:
- "Trace a model update from the state change through notification to each dependent view, and identify what each participant knows."

Key point:
- Observer decouples the object being observed from the details of its dependents.
- One model can support multiple synchronized presentations.
8. Q: How does the Composite pattern appear in MVC's nested views?
A: Show answer
MVC permits a view to contain other views. A CompositeView can manage nested button views or other smaller presentation components while itself behaving as a View. A client that expects a View can therefore work with a simple component or a composite containing many components through a common interface. The broader Composite pattern organizes objects into part-whole tree structures and allows clients to treat individual objects and compositions uniformly. This supports recursive user-interface structures without requiring every client to know whether a particular view is primitive or contains children. The key design choice is a common component abstraction and a composite implementation that manages its descendants.

Study instruction:
- "Draw a small view tree and show which operations a client can invoke without distinguishing leaf views from composite views."

Key point:
- Composite makes a group usable through the same abstraction as an individual component.
- Uniform treatment reduces client dependence on the internal tree structure.
9. Q: How does the Strategy pattern appear in MVC's view-controller relationship?
A: Show answer
A view delegates its response to user input to a Controller object. Different controller subclasses can implement different response strategies, such as keyboard handling or menu-based interaction. Replacing the controller changes the behavior without requiring a change to the view's visual presentation. The controller can even be replaced at run time; for example, assigning a controller that ignores input can disable a view. This illustrates Strategy as an object representing an algorithm or behavior that can be selected independently of the client using it. Strategy is particularly useful when there are multiple variants, when the choice may change dynamically, or when the algorithm has internal data that should be encapsulated.

Study instruction:
- "Implement a conceptual view with two interchangeable input controllers and describe how a client selects between them."

Key point:
- Strategy encapsulates a behavior variant behind a common interface.
- Composition allows the behavior to be changed without replacing the view.
10. Q: Why does the MVC example demonstrate more than one design pattern?
A: Show answer
MVC is a practical architecture whose relationships can be understood as several more general design solutions. Model-to-view notification illustrates Observer; nested views illustrate Composite; and a replaceable controller illustrates Strategy. The example also uses Factory Method to specify a default controller class and Decorator to add scrolling to a view. The chapter highlights Observer, Composite, and Strategy as the main relationships. This shows that patterns are not necessarily mutually exclusive building blocks: one design can combine several patterns, each addressing a different aspect of the overall problem. Recognizing the patterns makes the design's intent easier to explain and helps developers understand why the relationships are structured as they are.

Study instruction:
- "Annotate an MVC-style design with the distinct problem addressed by each pattern rather than labeling the entire architecture with one pattern name."

Key point:
- A single architecture can embody several patterns at different interaction points.
- Identify the intent of each relationship instead of treating patterns as competing labels.
11. Q: Why are class diagrams alone insufficient for documenting a design pattern?
A: Show answer
Class diagrams show structural relationships among classes and objects, but they do not necessarily explain why the design was chosen, what alternatives were considered, how participants collaborate over time, or what trade-offs were accepted. Reusing a design requires more than copying its final structure. The chapter therefore combines graphical notation with descriptions of intent, motivation, applicability, responsibilities, collaborations, consequences, implementation issues, and examples. Interaction diagrams and sample code add evidence about how requests flow and how the structure can be realized. A diagram is valuable, but without rationale and behavioral explanation it can encourage superficial imitation and leave critical design decisions undocumented.

Study instruction:
- "Review a design diagram and list the decisions, interactions, alternatives, and consequences that a reader would still need explained."

Key point:
- Structural notation captures only part of design knowledge.
- Document rationale, collaborations, and trade-offs as well as the final structure.

13. Q: What is the purpose of the Motivation section in a pattern description?
A: Show answer
Motivation presents a concrete scenario that makes the design problem visible and shows how the pattern's class and object structure addresses it. It bridges the gap between an abstract intent statement and the more formal description that follows. A well-chosen scenario helps a reader recognize the pressure that makes the pattern useful, understand why a naive design is inadequate, and see how responsibilities are redistributed. Motivation is not a substitute for applicability or structure: it illustrates the reasoning, while those sections state the conditions and formal arrangement more precisely. Without a motivating example, readers may memorize a pattern's diagram without understanding the practical problem it solves.

Study instruction:
- "Write a before-and-after scenario that demonstrates the design pressure a pattern addresses and the change in object collaboration."

Key point:
- Motivation makes an abstract pattern understandable through a concrete design situation.
- The example should explain the problem, not merely show code.
14. Q: What is the role of the Consequences section, and why should it be read before adopting a pattern?
A: Show answer
Consequences explain what follows from using a pattern, including benefits, costs, and aspects of structure that become independently variable. In software these may include time and space costs, extra indirection, implementation complexity, language constraints, flexibility, extensibility, and portability. These effects are critical because a pattern rarely improves every quality at once. A design may become easier to extend while requiring more objects or making control flow harder to trace. The chapter specifically recommends paying attention to Applicability and Consequences when first evaluating a candidate pattern. This helps prevent adoption based only on a pattern's reputation or apparent elegance.

Study instruction:
- "Before applying a candidate pattern, record its expected benefit, implementation cost, runtime impact, and maintenance consequence."

Key point:
- Consequences expose the trade-offs needed for an informed design decision.
- A pattern should be chosen for a real benefit that outweighs its costs.

16. Q: How are design patterns classified by purpose?
A: Show answer
The purpose criterion describes what a pattern does. Creational patterns concern the process of object creation. Structural patterns concern the composition of classes or objects. Behavioral patterns characterize how classes or objects interact and distribute responsibility. This classification helps a designer search by the kind of problem rather than by memorizing every pattern name. For example, if the problem concerns creating related objects without binding clients to concrete classes, a creational pattern is a sensible area to investigate. If the problem concerns assembling components into larger structures, structural patterns are more relevant. If the problem concerns communication or allocation of behavior among collaborators, behavioral patterns provide the relevant family.

Study instruction:
- "Classify several design problems by whether they primarily concern creation, composition, or collaboration before selecting a pattern."

Key point:
- Purpose groups patterns as creational, structural, or behavioral.
- Classify the design pressure first to narrow the search space.
17. Q: What does the scope criterion distinguish in the pattern catalog?
A: Show answer
Scope distinguishes class patterns from object patterns. Class patterns focus on relationships between classes and subclasses, generally established through inheritance and therefore fixed at compile time. Object patterns focus on relationships among objects, which can be assembled or changed at run time. Most patterns in the catalog have object scope, although many still use inheritance as part of their implementation. The label identifies the main focus rather than claiming that a pattern uses only one mechanism. Scope is useful because it signals whether the design is primarily based on static class relationships or dynamic object collaboration.

Study instruction:
- "Compare two candidate patterns and identify whether their central variation is expressed through inheritance or through object relationships."

Key point:
- Class scope emphasizes static class relationships; object scope emphasizes dynamic object relationships.
- Most catalog patterns are object-scope patterns.
18. Q: How do purpose and scope combine to organize the pattern space?
A: Show answer
Purpose and scope are independent classification dimensions. Purpose may be creational, structural, or behavioral; scope may be class or object. Their combination indicates both the kind of problem a pattern addresses and the main mechanism through which it addresses it. For example, a creational class pattern defers part of object creation to subclasses, whereas a creational object pattern delegates creation to another object. Structural class patterns use inheritance to compose classes, while structural object patterns assemble objects. Behavioral class patterns use inheritance to describe algorithms or flow of control, while behavioral object patterns describe cooperating objects sharing a task. Considering both dimensions gives a more precise vocabulary than using purpose alone.

Study instruction:
- "Place example patterns in a purpose-by-scope matrix and explain the mechanism implied by each position."

Key point:
- Purpose says what problem family is addressed; scope says whether class or object relationships are central.
- The two dimensions together clarify the design mechanism.
19. Q: Why can patterns with similar structures have different intents?
A: Show answer
Two patterns can have similar class diagrams while solving different problems. The chapter notes Composite and Decorator as an example: their structures can look alike, but Composite focuses on part-whole hierarchies and uniform treatment of components and compositions, whereas Decorator attaches additional responsibilities to an object dynamically. Structural resemblance is therefore not sufficient to determine whether two patterns are interchangeable. Intent, applicability, participant responsibilities, and consequences distinguish them. This is also why pattern recognition should not stop at matching a diagram. A designer must understand what varies, what behavior is being delegated or composed, and what constraints the pattern assumes.

Study instruction:
- "Compare Composite and Decorator using their intents, object structures, client expectations, and consequences rather than their diagrams alone."

Key point:
- Similar structure does not imply equivalent design purpose.
- Choose by problem and intent, not by visual resemblance.
20. Q: How can patterns be used together or serve as alternatives?
A: Show answer
Patterns are related in several ways. Some are commonly combined because they address complementary concerns; Composite may be used with Iterator or Visitor. Others can be alternatives for a particular design decision; Prototype may be an alternative to Abstract Factory when object creation can be based on copying prototypes. Still others produce similar structures while pursuing different intents. The chapter also points readers to the Related Patterns sections and a relationship diagram as ways to understand these connections. A pattern should therefore be selected as part of the larger design, considering dependencies and combinations, rather than as an isolated answer to a single local problem.

Study instruction:
- "Choose one pattern and identify a complementary pattern, a plausible alternative, and a structurally similar but differently intended pattern."

Key point:
- Patterns form a network of combinations, alternatives, and related structures.
- Evaluate the consequences of a pattern within the whole design.
21. Q: How do design patterns help designers find appropriate objects and abstractions?
A: Show answer
Object-oriented decomposition is difficult because the designer must balance encapsulation, granularity, dependency, flexibility, performance, evolution, and reuse. Some useful design objects do not correspond to physical entities in the problem domain. Design patterns help reveal such abstractions. Strategy represents an algorithm as an object so that alternatives can be exchanged; State represents possible states as objects so that state-dependent behavior can be organized explicitly; Composite introduces a common abstraction for treating individual objects and groups uniformly. These abstractions may emerge only after the initial analysis model proves too rigid. Patterns thus help designers discover useful software concepts that are not obvious from a literal mapping of real-world nouns to classes.

Study instruction:
- "Inspect a domain model for behavior or relationships that may deserve their own objects even though they are not physical entities."

Key point:
- Good object models include design abstractions, not only real-world nouns.
- Patterns help reveal objects that encapsulate algorithms, states, and compositions.
22. Q: How do design patterns help determine object granularity?
A: Show answer
Objects can represent very small entities or large subsystems, so choosing their granularity is a design decision. The chapter gives examples at different scales. Facade represents a complete subsystem through a higher-level object interface. Flyweight supports large numbers of fine-grained objects efficiently through sharing. Abstract Factory and Builder create objects whose responsibility is to construct other objects. Command and Visitor create objects focused on carrying out requests or operations on other objects. These examples show that an object need not represent a business entity; it may represent a subsystem boundary, a creation process, a request, or a reusable behavior. Pattern guidance helps select a useful level of responsibility and indirection.

Study instruction:
- "Identify whether a proposed object represents a domain entity, subsystem, creation responsibility, request, or fine-grained shared element."

Key point:
- Object granularity should reflect the responsibility and design pressure being addressed.
- Patterns provide examples ranging from subsystem objects to fine-grained shared objects.
23. Q: What is an object interface, and how is it related to an operation signature?
A: Show answer
An operation signature specifies an operation's name, its parameters, and its return value. The set of signatures exposed by an object's operations forms its interface. The interface defines the requests a client may send to the object. A client that sends a request matching an exposed signature can rely on the object to accept that request, but the interface does not reveal how the operation is implemented. An interface is therefore a contract for interaction, not a description of internal representation. Careful interface design is fundamental to reuse because it determines which clients can collaborate with an object and how strongly they depend on its implementation.

Study instruction:
- "Write the signatures exposed by a component and separate its public interaction contract from its private state and implementation."

Key point:
- An interface is the set of supported request signatures.
- Clients should depend on the contract, not hidden representation.
24. Q: What is the relationship between types, subtypes, and object interfaces?
A: Show answer
A type names an interface that an object supports. An object may have multiple types, and objects from different classes may share a type if they support the relevant requests. One interface may contain another as a subset; the type with the more extensive interface is a subtype of the type whose interface it includes. The chapter describes this as interface inheritance or subtyping. This relationship is about which requests an object can accept, not about whether its internal data or code is shared with another object. A design can therefore allow different implementations to satisfy a common client contract, which is central to polymorphism and substitutability.

Study instruction:
- "Draw two interfaces where one is a subtype of the other and identify the requests that make substitution valid."

Key point:
- A type describes an interface, not a concrete representation.
- Subtyping requires the subtype interface to include the supertype interface.
25. Q: How do dynamic binding and polymorphism support reusable designs?
A: Show answer
Dynamic binding associates a request with the implementation supplied by the receiving object at run time. A client can issue a request through an expected interface without selecting the concrete implementation in advance. When several objects support the same interface but implement its operations differently, they can be substituted for one another; this is polymorphism. It reduces the assumptions a client must make about collaborators and permits object relationships to vary at run time. This is a foundation for flexible design because a client can work with any appropriate implementation. The benefit depends on meaningful, compatible interfaces; a common method name alone does not guarantee that two implementations can be substituted safely.

Study instruction:
- "Trace a request through a shared interface to two different concrete implementations and identify what the client must know."

Key point:
- Dynamic binding selects the operation implementation at run time.
- Polymorphism allows different implementations to be used through a common interface.
26. Q: What is the difference between an object's class and its type?
A: Show answer
A class defines an object's implementation, including its internal data, representation, and operations. A type describes the interface or set of requests the object supports. A class usually determines at least one type because it defines operations, but the concepts are not identical. An object may expose more than one type, and different classes may provide the same type while using different internal implementations. Confusing class with type leads clients to depend unnecessarily on concrete implementation choices. The chapter uses this distinction to explain why reusable designs should make clients interact through abstract interfaces rather than require a particular class.

Study instruction:
- "Describe one example where two classes could implement the same interface while storing and processing data differently."

Key point:
- Class concerns implementation; type concerns interface.
- Different classes can be substitutable when they satisfy the same required type.
27. Q: How does class inheritance differ from interface inheritance?
A: Show answer
Class inheritance defines a new implementation in terms of an existing implementation and can share representation and code. Interface inheritance, also called subtyping, defines when an object can be used wherever another type is expected. The two mechanisms are often combined by programming languages, which makes them easy to confuse. The chapter notes that C++ can use public inheritance from pure abstract classes to approximate interface-only inheritance and private inheritance to approximate implementation inheritance. Smalltalk inheritance primarily shares implementation, while message compatibility is determined by supported operations. The distinction matters because a class may reuse code without being a valid behavioral substitute, and an object may satisfy an interface without sharing implementation.

Study instruction:
- "Review a class hierarchy and mark separately which relationships are for code reuse and which are required for substitutability."

Key point:
- Implementation inheritance shares code and representation; interface inheritance establishes substitutability.
- Do not assume that sharing a parent implementation automatically makes a sound subtype.
28. Q: What are abstract classes, abstract operations, and mixin classes?
A: Show answer
An abstract class primarily defines a common interface for subclasses and may leave some or all implementation to those subclasses. Because it is incomplete by design, it cannot be instantiated. Operations declared but not implemented in an abstract class are abstract operations. Concrete classes provide instantiable implementations. A mixin class is intended to provide optional functionality or an interface to other classes rather than to exist as a standalone object; the chapter notes that mixins require multiple inheritance. These constructs support different forms of reuse and contract definition, but their exact implementation depends on the programming language. A designer should distinguish an abstract contract from a partially implemented base class and should use multiple inheritance deliberately.

Study instruction:
- "Identify which operations in a proposed base class are contracts and which are reusable default implementations; check whether a mixin is genuinely needed."

Key point:
- Abstract classes define shared contracts and may defer implementation.
- Mixins provide optional functionality and rely on language support such as multiple inheritance.
29. Q: What does the principle 'Program to an interface, not an implementation' mean?
A: Show answer
Clients should declare and use collaborators through stable abstract interfaces rather than depend on particular concrete classes. If a client knows only the requests it needs, any object satisfying that interface can be supplied without rewriting the client. This reduces implementation dependencies between subsystems and makes substitution, testing, and future extension easier. The principle does not mean that concrete classes are never instantiated. A system must create real implementations somewhere, but those creation decisions should be localized or abstracted so that the rest of the design can remain interface-oriented. The chapter identifies creational patterns as ways to associate interfaces with concrete implementations while hiding creation choices from ordinary clients.

Study instruction:
- "Find a client that directly constructs or stores a concrete class and redesign its dependency around an appropriate abstraction."

Key point:
- Clients should depend on required behavior, not concrete implementation details.
- Concrete instantiation is necessary but should be isolated from code that only needs an interface.
30. Q: How do creational patterns support programming to an interface?
A: Show answer
Creational patterns separate the decision about which concrete object to instantiate from the client that uses the object. The chapter identifies Abstract Factory, Builder, Factory Method, Prototype, and Singleton as patterns that can help establish this separation. Depending on the problem, creation may be delegated to a factory object, deferred to a subclass, based on copying a prototype, or constrained to a single instance. The client can then receive an object through an interface without hard-coding its concrete class. These patterns do not eliminate the need to choose an implementation; they organize where and how that choice is made so that it does not spread through the system.

Study instruction:
- "Locate concrete object-creation decisions in an application and determine whether they should be centralized behind a creation abstraction."

Key point:
- Creational patterns hide or structure concrete instantiation decisions.
- Their purpose is to keep clients expressed in terms of interfaces.
31. Q: What is the difference between inheritance-based reuse and object composition?
A: Show answer
Class inheritance reuses functionality by defining a subclass in terms of a parent class. It is often called white-box reuse because a subclass may depend on or expose details of the parent's implementation. Object composition builds more complex behavior by assembling objects that collaborate through defined interfaces; it is called black-box reuse because internal implementation details remain hidden. Inheritance is established statically at compile time and is directly supported by many languages. Composition can be arranged dynamically at run time and allows collaborators to be replaced when they satisfy the required interface. Both techniques are useful, but they create different coupling, flexibility, and comprehension trade-offs.

Study instruction:
- "Compare a proposed subclass solution with a composition-based solution and identify what each client or subclass must know."

Key point:
- Inheritance reuses through parent-child implementation relationships; composition reuses through collaborating objects.
- Composition usually preserves stronger encapsulation, while inheritance can be simpler and more direct.
32. Q: What are the main risks of overusing class inheritance?
A: Show answer
Inheritance can bind a subclass to details of its parent representation and behavior. A change in the parent may therefore force changes in subclasses, making reuse fragile. A subclass may also inherit operations or assumptions that do not fit its new context. Overriding one operation can have unexpected effects if inherited operations call it or depend on related methods. Customization through subclassing can create many classes and require detailed knowledge of the parent. The chapter describes this as inheritance breaking encapsulation when subclass implementation becomes tightly coupled to parent implementation. Inheriting primarily from abstract classes can reduce exposure to implementation details, but the relationship must still be a sound subtype relationship.

Study instruction:
- "Inspect a subclass for reliance on parent fields, protected methods, initialization order, and overridden-method interactions."

Key point:
- Inheritance can create hidden dependencies on parent implementation.
- Prefer inheritance where the subtype relationship and inherited behavior remain stable and appropriate.
33. Q: Why does the chapter recommend favoring object composition over class inheritance?
A: Show answer
Object composition allows a class to obtain behavior from collaborators through their interfaces rather than inherit their representations. Collaborators can often be replaced at run time, reducing implementation dependencies and keeping classes focused on smaller responsibilities. This can prevent deep or sprawling class hierarchies and make behavior combinations more flexible. The trade-off is that a composition-based system may contain more objects and its behavior may be harder to understand because it is distributed across collaborations. Dynamic indirection can also have performance costs. The recommendation is therefore a design preference, not an absolute prohibition on inheritance. Inheritance and composition can work together: inheritance can create reusable components that are then assembled through composition.

Study instruction:
- "Refactor one example of subclass-based customization into collaborating objects and compare flexibility, readability, object count, and runtime cost."

Key point:
- Composition often improves encapsulation and run-time flexibility.
- Use the principle as a preference, not a rule that eliminates inheritance.
34. Q: What is delegation, and how does it make composition more powerful?
A: Show answer
Delegation occurs when an object receives a request and forwards responsibility for carrying out some operation to another object, its delegate. The receiver may pass a reference to itself so that the delegate can interact with the original receiver when needed. This resembles a subclass relying on inherited behavior, but the relationship is established through object references rather than a fixed parent class. The chapter illustrates this with a Window that contains a Rectangle and delegates area-related behavior to it instead of inheriting from Rectangle merely because the window happens to be rectangular. Replacing the delegate with another object of a compatible type can change behavior at run time.

Study instruction:
- "Trace a delegated request and identify the receiver, delegate, forwarded operation, and any reference passed back to the receiver."

Key point:
- Delegation forwards selected responsibilities to a collaborator.
- It enables behavior composition and replacement without a fixed inheritance relationship.
35. Q: What are the advantages and disadvantages of delegation?
A: Show answer
Delegation makes it possible to compose behavior at run time and change that composition without changing a class hierarchy. It can avoid an inappropriate 'is-a' inheritance relationship and can keep implementation details encapsulated behind an interface. However, the receiver must explicitly forward requests, and the resulting control flow can be less obvious than a static inheritance relationship. Highly parameterized object networks may be harder for developers to understand and can introduce runtime overhead. The chapter cautions that delegation is appropriate when it simplifies the design more than it complicates it. Its effectiveness depends on context and experience, and it is often clearest when used in established patterns rather than as an unstructured technique.

1. Q: What are creational design patterns, and what design problem do they address?
A: Show answer
Creational design patterns abstract the process by which objects are instantiated, composed, and represented. Rather than allowing application logic to depend directly on concrete constructors and product classes, they place creation knowledge behind interfaces or dedicated objects. This reduces the coupling between a system and the particular classes used in one configuration. The patterns do not necessarily make creation code shorter; their main purpose is to make a design easier to vary as requirements, product families, or runtime configurations change.

45. Q: What is the intent of Prototype?
A: Show answer
Prototype specifies the kinds of objects to create by supplying prototypical instances and creating new objects by copying them. A client asks a prototype to clone itself rather than naming or directly instantiating its concrete class. This makes it possible to configure a creator object with examples of the desired products, including products whose classes or state are selected at runtime. The pattern is particularly valuable when subclassing a creator for every product variation would produce many nearly identical classes.

Study instruction:
- "Explain how a prototype instance can serve as both a product example and a creation mechanism."

Key point:
- Prototype creates new products by cloning configured instances.
- The client can avoid direct dependence on concrete product constructors.

The editor framework has a GraphicTool that must create application-specific graphics such as notes and staves. 47. Q: When is Prototype particularly appropriate?
A: Show answer
Prototype is useful when concrete classes are specified at runtime, such as through dynamic loading; when a parallel hierarchy of factory classes would otherwise be required; or when a class has only a limited number of useful state combinations. Registering representative instances and cloning them can be simpler than repeatedly constructing and configuring objects through many specialized paths. It is most effective when the objects can be copied reliably and when clients can work with a stable cloning interface.

Study instruction:
- "Check whether product types are selected dynamically, whether creator subclasses would proliferate, and whether cloning is reliable."

Key point:
- Prototype is valuable when runtime product selection or state presets matter.
- Copying complexity can outweigh the benefit if objects are difficult to clone.
48. Q: What kinds of flexibility does Prototype provide beyond selecting a concrete class?
A: Show answer
Prototype can add or remove available products at runtime by registering or unregistering prototype instances. It can define new object variants by changing instance values rather than introducing new subclasses, and it can represent complex structures by registering a configured composite as a prototype. Users may therefore assemble new reusable configurations without writing a new creator class for every variant. These benefits depend on the clone operation preserving the intended structure and on initialization being controlled.

49. Q: What is the difference between shallow copy and deep copy in Prototype?
A: Show answer
A shallow copy duplicates the outer object but may leave references to internal objects shared with the original. A deep copy duplicates the relevant contained objects as well, producing an independent object graph. The chapter notes that default copying facilities in Smalltalk and C++ do not automatically solve this design question: Smalltalk's default copy is shallow, and C++ memberwise copying copies pointer values rather than the pointed-to objects. A system must decide deliberately which parts should be shared and which must be cloned.

Study instruction:
- "Inspect a prototype containing nested objects and draw which references are shared after a shallow copy and after a deep copy."

Key point:
- Shallow copying can preserve shared internal references.
- Deep copying is often needed when prototype and clone must evolve independently.
50. Q: Why can implementing Clone be difficult for complex object graphs?
A: Show answer
Clone becomes difficult when objects contain circular references, non-copyable resources, or internal collaborators whose ownership and sharing rules are unclear. A naive recursive deep copy can loop indefinitely on cycles, while a shallow copy can cause the original and clone to interfere with one another. The implementation must preserve class identity, valid relationships, and any required invariants. Existing classes may also be hard to retrofit with Clone, especially if their internals were not designed for copying.

Study instruction:
- "Review a composite object graph for cycles, shared ownership, handles, and resources that cannot safely be duplicated."

Key point:
- Correct cloning requires explicit ownership and graph-copy decisions.
- Complex object relationships can make Clone a substantial implementation burden.

A: Show answer
When prototypes can be added or removed dynamically, a prototype manager maintains a registry keyed by a name or identifier. A client asks the manager for the appropriate prototype, then clones it rather than managing every prototype directly. The registry can support registration, lookup, removal, and inspection of available product definitions. It separates product availability from the client and allows the system to be extended at runtime, but it should handle duplicate keys, missing prototypes, and invalid registrations predictably.

Some clients can use a clone exactly as copied, while others need to change selected state. A uniform Clone operation generally should not accept every possible initialization parameter because different prototype classes may require different parameters. 53. Q: What is Prototype's principal liability compared with other creational approaches?
A: Show answer
Each concrete prototype class must implement cloning correctly, and that work may be difficult for classes with complex internal state or circular relationships. Factory Method avoids requiring product cloning but may require creator subclasses; Abstract Factory avoids client-side concrete construction but can require a factory hierarchy; Builder requires a construction protocol and stateful assembly. Prototype is attractive when copying is natural and runtime variation is valuable, but less attractive when objects own resources or have intricate copy semantics.

- "Compare the implementation burden of cloning with the subclassing and interface burdens of the other patterns."

- Prototype reduces creator classes by moving complexity into copying.
- The best choice depends on which complexity the system can manage safely.
54. Q: What is the intent of Singleton?
A: Show answer
Singleton ensures that a class has only one instance and provides a well-known access point to it. The class itself controls the creation and access of that instance rather than relying on a global variable that merely makes an object visible. The chapter's examples include a printer spooler, file system, window manager, and maze factory. The pattern is justified only when uniqueness is a real domain or coordination requirement, not simply because a class is convenient to access globally.

Study instruction:
- "Identify a resource that genuinely requires one coordinated instance and distinguish that requirement from mere convenience."

Key point:
- Singleton combines instance-count control with a defined access operation.
- Global accessibility alone does not establish a need for Singleton.
55. Q: When should a class be implemented as a Singleton?
A: Show answer
Use Singleton when exactly one instance must exist and clients need a well-known access point. The chapter also identifies cases where the sole instance should be extensible by subclassing while clients continue using the same access mechanism. The design should be questioned if multiple independent instances are legitimate, if tests need isolated instances, or if global access would obscure dependencies. The uniqueness requirement should be stated explicitly and enforced rather than assumed.

Study instruction:
- "Write the invariant that requires one instance and identify which clients depend on that invariant."

Key point:
- Singleton is appropriate only when one-instance semantics are required.
- Access convenience by itself is not a sufficient justification.
56. Q: How does Singleton improve on a global variable?
A: Show answer
A global variable can make an object accessible but cannot prevent other code from constructing additional instances. Singleton encapsulates the sole instance inside the class and exposes a controlled Instance operation. This lets the class govern creation timing and access while avoiding a separate global variable name in the application's namespace. The pattern still introduces broad shared access, so it can make dependencies less visible; it should not be treated as a general substitute for explicit dependency management.

- "Compare the guarantees provided by a public global object and a class-controlled Instance operation."

- Singleton can enforce uniqueness in a way a global variable cannot.

57. Q: What benefits and limitations does the chapter associate with Singleton?
A: Show answer
Benefits include controlled access to the sole instance, a smaller global namespace, the ability to refine behavior through subclassing, and the possibility of changing the permitted instance count later. It is more flexible than relying only on static or class operations because a Singleton object can participate in polymorphism. Its limitations include global coupling and the need to manage creation, subclass selection, and initialization carefully. The chapter focuses on instance control and configurability rather than claiming that Singleton automatically makes shared state safe.

- Singleton provides controlled access and can support polymorphic refinement.

When Instance is called, it checks whether the reference is empty; if so, it constructs the instance and stores it, then returns the stored reference. 1. Q: What problem do structural design patterns address?
A: Show answer
Structural patterns describe ways to compose classes and objects into larger, useful structures. They address recurring design problems involving interface compatibility, separation of abstractions from implementations, part–whole hierarchies, dynamic responsibilities, subsystem access, object sharing, and controlled access to other objects. Their common concern is not an algorithm in isolation but how software elements are related and how requests move through those relationships. The appropriate pattern depends on the design force: incompatible interfaces require a different solution from independent implementation variation or memory reduction through sharing.

Study instruction:
- For each design problem, identify the objects involved, the relationship that must change, and the constraint the design must preserve.

Key point:
- Structural patterns organize relationships among classes and objects.
- A pattern should be selected by its intent, not merely by a similar-looking class diagram.
2. Q: How do structural class patterns differ from structural object patterns?
A: Show answer
Structural class patterns use inheritance to combine interfaces or implementations. The relationship is established by the class hierarchy and is therefore largely fixed by the type definition. Structural object patterns use composition: one object holds or collaborates with other objects to provide behavior. This allows the composition to be changed at run time, which gives object patterns flexibility that static class composition cannot provide. The Adapter chapter discussion illustrates both forms, while Composite, Decorator, Facade, Flyweight, and Proxy primarily describe object structures.

Study instruction:
- Classify a proposed design as inheritance-based or composition-based, then ask whether the relationship must be changeable after objects are created.

Key point:
- Inheritance combines class features; composition combines collaborating objects.
- Choose composition when run-time substitution or reconfiguration is a real requirement.
3. Q: How can the seven patterns in this chapter be distinguished at the design stage?
A: Show answer
Use the problem being solved as the discriminator. Adapter makes an existing interface usable where another interface is expected. Bridge separates an abstraction from implementations that must vary independently. Composite represents part–whole trees and lets clients treat leaves and groups uniformly. Decorator adds responsibilities to individual objects without changing their interface. Facade gives clients a simpler entry point to a subsystem. Flyweight shares fine-grained objects to reduce storage costs. Proxy stands in for another object to control or defer access. Similar forwarding code does not make these patterns interchangeable; their purposes differ.

Key point:
- The intent is the most reliable selection criterion.
- Do not choose a pattern solely because its participants contain a wrapper or a reference to another object.
4. Q: What is the intent of the Adapter pattern?
A: Show answer
Adapter converts the interface of an existing class into an interface that clients expect. It allows classes to collaborate even when their original interfaces are incompatible. The adapter receives a request through the target interface, translates or restructures that request, and invokes the corresponding operation on the adaptee. The chapter also calls this pattern Wrapper. It is primarily an integration technique: it helps reuse an existing class without requiring that class to be redesigned around the new client’s domain-specific interface.

- Write down the interface the client expects and the operations the existing class actually provides; identify the exact conversion needed between them.

- Adapter reconciles incompatible interfaces.

Key point:
- The client depends on Target, not directly on the Adaptee interface.
- Correctly identifying the four roles makes the conversion boundary explicit.
7. Q: How does a class adapter work?
A: Show answer
A class adapter uses inheritance to obtain the target interface from one class and the implementation to be adapted from another. In the chapter’s C++ example, the adapter inherits publicly from Target and privately from Adaptee. The public inheritance makes the adapter usable as a Target, while private inheritance reuses the adaptee’s implementation without exposing it as a public base type. This approach can let the adapter override inherited adaptee behavior. It is tied to a concrete adaptee class, however, and is not a general way to adapt that class together with all of its subclasses.

Study instruction:
- When reviewing a class adapter, verify which base supplies the public client interface and which base supplies implementation reuse.

Key point:
- Class adapters combine a target interface and an adaptee implementation through inheritance.
- The inheritance structure is fixed and commits the adapter to a particular adaptee class.
8. Q: How does an object adapter work?
A: Show answer
An object adapter implements the expected Target interface and keeps a reference to an Adaptee object. Each target operation translates its arguments or meaning as necessary and calls the corresponding adaptee operation. In the TextShape example, the client supplies a TextView instance to the TextShape constructor, and TextShape delegates to that instance. Because the adaptee is supplied as an object, the adapter can work with the adaptee class and its subclasses. The adapter can also add target behavior that is not available on the adaptee.

Study instruction:
- Draw the reference from the adapter to the adaptee and trace at least two target operations through that reference.

Key point:
- Object adapters rely on composition and delegation.
- The adapted object is supplied to the adapter rather than fixed as an inherited base class.
9. Q: What trade-offs distinguish class adapters from object adapters?
A: Show answer
A class adapter introduces only one adapter object and needs no extra pointer indirection to reach the adaptee. It can override adaptee behavior through inheritance, but it commits to a concrete adaptee class and does not automatically adapt all of that class’s subclasses. An object adapter can work with an adaptee instance and its subclasses, and one adapter implementation can therefore cover a broader family of objects. It is harder to override the adaptee’s behavior because the adapter delegates to a separate object; changing that behavior may require adapting a subclass instead. The choice depends on inheritance support, subclass coverage, and the need to override behavior.

Study instruction:
- Choose one realistic adaptee hierarchy and compare the amount of reuse, subclass coverage, and behavior override available with each form.

Key point:
- Class adapters favor direct inheritance; object adapters favor flexible object substitution.
- Prefer an object adapter when adapting different existing subclasses is important.
10. Q: How much work should an Adapter perform?
A: Show answer
An adapter can perform anything from simple interface conversion to a more substantial mapping between dissimilar operation sets. A small mismatch may require only renaming an operation or rearranging its parameters. A larger mismatch may require coordinating several adaptee operations or translating data representations. The chapter’s TextShape also illustrates an adapter implementing CreateManipulator itself because TextView has no corresponding capability. The required amount of adaptation depends on how closely the Target and Adaptee interfaces correspond. The adapter should make the mismatch explicit rather than conceal incomplete or misleading translations.

Study instruction:
- List each Target operation and classify it as direct forwarding, parameter/result conversion, multi-operation translation, or newly implemented behavior.

Key point:
- Adapter effort should match the actual interface gap.
- Do not assume every target operation has a one-to-one adaptee operation.
11. Q: What is a pluggable adapter, and why is it useful?
A: Show answer
A pluggable adapter builds interface adaptation into a reusable class so that the class does not require every client object to inherit from one special domain-specific base class. The chapter’s TreeDisplay example should display different kinds of hierarchical data, such as directory trees and class-inheritance trees, even though their child-access operations have different names. Requiring every application to use the same Tree base class would make TreeDisplay less reusable. A pluggable design lets the widget work with application-specific objects by supplying the necessary adaptation behavior.

Study instruction:
- Review a reusable component that consumes external objects and identify any unnecessary requirement that those objects inherit from a particular application class.

Key point:
- Pluggable adaptation reduces assumptions about client object types.
- Reusable components should depend on a narrow required interface, not an arbitrary application hierarchy.
12. Q: What implementation approaches does the chapter describe for pluggable adapters?
A: Show answer
The chapter describes three approaches after identifying a narrow adaptee interface. First, abstract operations let subclasses implement the required adaptation operations; a DirectoryTreeDisplay can adapt directory objects by specializing those operations. Second, a delegate object receives the access requests, allowing the adapter to change its adaptation strategy by substituting a delegate. In statically typed languages, the delegate generally needs an explicit interface. Third, parameterized adapters use blocks or callbacks for operations such as rendering a node and obtaining its children, avoiding a subclass for each adaptation. These approaches trade inheritance, delegation, and parameterized behavior.

Study instruction:
- Implement a small hierarchy-display example using one of the three approaches and explain how a second hierarchy type would be added.

Key point:
- Pluggable adapters can use subclass hooks, delegate objects, or parameterized operations.
- Find the narrow interface before choosing the adaptation mechanism.
13. Q: What is a two-way adapter, and when can it be needed?
A: Show answer
An ordinary adapter may not be transparent to clients that still need to use the adaptee’s original interface: once an object is adapted, it does not automatically conform to the adaptee interface. A two-way adapter addresses situations in which two clients or systems need to view the same object through different interfaces. The chapter’s Unidraw and QOCA example uses ConstraintStateVariable to adapt State Variable and ConstraintVariable interfaces to each other. The two-way class adapter inherits from both types so it can participate in either system. This is useful where both systems must collaborate, not merely where one client needs a one-directional conversion.

Study instruction:
- Identify both interfaces that must remain usable and trace a request originating in each system through the two-way adapter.

Key point:
- Two-way adapters provide access through both adapted interfaces.
- Use this design only when bidirectional interoperability is genuinely required.
14. Q: What should be considered when testing an Adapter implementation?
A: Show answer
Test the adapter at the interface boundary. For every Target operation, verify that the correct Adaptee operation is invoked, input values are converted correctly, and returned values or errors are translated consistently. Test any behavior the adapter adds itself, such as CreateManipulator, separately from delegated behavior. Include adaptee subclasses when the design claims to support them, especially for an object adapter. Also test unsupported or ambiguous conversions so that the adapter does not silently return misleading results. These checks are practical verification steps derived from the roles and trade-offs described in the chapter.

Study instruction:
- Create a Target-to-Adaptee mapping table and turn every mapping, conversion, and added responsibility into a test case.

Key point:
- Adapter tests should verify translation, delegation, and added behavior.
- Test the promised compatibility, not merely that the adapter compiles.
15. Q: What is the intent of the Bridge pattern?
A: Show answer
Bridge decouples an abstraction from its implementation so that both can vary independently. It introduces two cooperating class hierarchies: one defines the abstraction presented to clients, and the other defines the lower-level implementation operations. The abstraction keeps a reference to an Implementor and forwards requests to it. This avoids permanently binding a particular abstraction subclass to one implementation subclass, making it possible to add abstraction variants and implementation variants separately.

Study instruction:
- Separate the client-facing abstraction operations from the primitive operations required from a concrete implementation.

Key point:
- Bridge separates two dimensions of variation.
- An abstraction can remain stable while its implementation changes.
16. Q: Why can inheritance alone create a problem when abstractions have multiple implementations?
A: Show answer
If each abstraction variant must be implemented separately for every platform or implementation, the class hierarchy grows as combinations multiply. The chapter’s window example would require XWindow and PMWindow, then additional classes such as XIconWindow and PMIconWindow for icon windows, with more classes for every new window kind and platform. Client code may also need to instantiate platform-specific classes directly, making it dependent on the platform. Bridge addresses both problems by separating the window abstraction hierarchy from the window-system implementation hierarchy.

Study instruction:
- Count the classes required by a design with several abstraction types and several platforms, then compare that count with two independently extensible hierarchies.

Key point:
- Static inheritance can multiply classes across independent variation dimensions.
- Separate dimensions that are expected to evolve independently.
17. Q: What are the participants in a Bridge design?
A: Show answer
Abstraction defines the client-facing interface and maintains a reference to an Implementor. RefinedAbstraction extends that interface for a particular abstraction variant, such as IconWindow. Implementor defines the operations required by the abstraction’s implementation; its operations may be lower-level and need not match the abstraction interface one-for-one. ConcreteImplementor supplies the platform- or mechanism-specific implementation, such as XWindowImp or PMWindowImp. The abstraction forwards client requests to the implementor, often translating a higher-level request into several implementor operations.

Study instruction:
- Label each class in a Window/WindowImp design and identify which classes can be extended independently.

Key point:
- The abstraction owns the client-facing contract; the implementor owns implementation primitives.
- The two interfaces are related by collaboration, not by requiring identical operations.
18. Q: When is Bridge particularly appropriate?
A: Show answer
Bridge is useful when an abstraction must avoid a permanent binding to one implementation, when both sides should be extensible by subclassing, or when the implementation may be selected or switched at run time. It is also useful when implementation changes should not force client recompilation, when clients should not see implementation details, or when a class hierarchy shows a proliferation of combinations. The chapter also identifies sharing one implementation among several objects as a possible reason to separate the abstraction from its implementation.

Study instruction:
- Look for two independent axes of change, a growing cross-product of subclasses, or implementation details that leak into client code.

Key point:
- Bridge is valuable when abstraction and implementation have independent change paths.
- It is most useful when the separation is designed deliberately rather than added after the hierarchy has become tangled.
19. Q: What are the principal consequences of using Bridge?
A: Show answer
Bridge removes a permanent compile-time binding between abstraction and implementation. The implementation can be configured at run time and, where the design supports it, changed during an object’s lifetime. Because clients depend on the abstraction and implementor interface rather than a concrete implementation, replacing an implementation need not require recompiling clients. The two hierarchies can be extended independently, and implementation details such as shared implementor objects or reference counts can be hidden. The separation can also encourage clearer system layering, although it introduces another object relationship that must be configured correctly.

Study instruction:
- Evaluate a Bridge design against platform replacement, client recompilation, independent extension, and the added indirection it introduces.

Key point:
- Bridge improves independent extensibility and hides implementation details.
- The flexibility has value when the system needs independent implementation choices.
20. Q: How should a Bridge choose the appropriate ConcreteImplementor?
A: Show answer
The chapter describes several choices. The abstraction can select an implementor in its constructor based on parameters or conditions. A collection abstraction, for example, might choose a linked-list or hash-table implementation according to collection size. A design may start with a default implementation and switch when usage changes. Alternatively, a separate factory can encapsulate platform-specific creation so the abstraction does not know the concrete implementor classes. A factory is especially useful when several platform-specific objects must be created consistently.

Study instruction:
- Identify where the platform or implementation choice belongs and assess whether the abstraction should know concrete implementation classes.

Key point:
- Implementation selection may be local, adaptive, or delegated to a factory.
- Use a factory when concrete implementation knowledge should be isolated from the abstraction.
21. Q: What is a degenerate Bridge, and how does it relate to implementation hiding?
A: Show answer
The chapter notes that a Bridge can still be useful when there is only one Implementor. In this degenerate case, the abstraction and implementor have a one-to-one relationship, but separating them can still prevent implementation changes from affecting clients. The chapter calls a related C++ technique the Cheshire Cat: the implementor interface can be placed in a private header so clients do not see the representation. This supports implementation hiding even when multiple concrete implementors are not currently necessary.

Study instruction:
- Consider whether a class-library implementation detail should be hidden from clients even though the library currently has only one implementation.

Key point:
- Bridge can separate interface from representation without multiple concrete implementations.
- The benefit may be dependency control and information hiding rather than run-time selection.
22. Q: Why is ordinary multiple inheritance not a substitute for a true Bridge?
A: Show answer
The chapter describes using multiple inheritance to combine an abstraction interface with a concrete implementation. However, this statically binds the implementation to the abstraction. The resulting class cannot freely substitute or change the implementation through a composed Implementor reference. It may combine two inheritance branches, but it does not provide the independent variation and run-time configuration that define Bridge. In C++, the chapter therefore distinguishes this static combination from a true Bridge design.

Study instruction:
- Inspect whether implementation selection is fixed by the class declaration or can be varied through an Implementor object.

Key point:
- A true Bridge uses a separable implementor relationship.
- Multiple inheritance alone does not deliver independent run-time variation.
23. Q: What does the Composite pattern represent?
A: Show answer
Composite composes objects into tree structures that represent part–whole hierarchies. It lets clients treat individual objects and groups of objects uniformly through a common Component interface. In the graphics example, primitive objects such as Line, Rectangle, and Text are leaves, while Picture is a composite containing other Graphic objects. A Picture can contain smaller Pictures, so the structure is recursive. The pattern is appropriate when clients should issue the same kind of request to an individual item or an aggregate without repeatedly distinguishing between them.

Study instruction:
- Sketch a part–whole tree for a concrete domain and mark which nodes are leaves and which can contain children.

Key point:
- Composite represents recursive part–whole structure.
- A composite is treated as a component even though it contains other components.
24. Q: What are the Component, Leaf, Composite, and Client roles in Composite?
A: Show answer
Component declares the common interface and, where appropriate, default behavior and child-access operations. Leaf represents a primitive object and has no children. Composite stores child Components, implements child-management operations, and commonly forwards requests to its children. Client manipulates the structure through the Component interface. When a request reaches a Leaf, it is handled directly; when it reaches a Composite, the composite usually forwards it to children and may perform work before or after forwarding. The shared interface is what allows recursive structures to be used uniformly.

Study instruction:
- Map each role to Graphic, Line or Text, Picture, and DrawingEditor in the chapter’s example.

Key point:
- Leaves implement primitive behavior; composites manage and delegate to children.
- Client code can operate through Component instead of testing every concrete class.
25. Q: How does Composite simplify client code?
A: Show answer
Without Composite, client code often needs separate logic for primitives and containers even when users regard them as the same kind of thing. The pattern places a common interface above both. A client can call Draw or another shared operation on a Component without first determining whether it is a single graphic or a Picture containing many graphics. This avoids repeated type checks and case-by-case handling. New Leaf and Composite subclasses can often work with existing clients automatically, provided they honor the Component contract.

Study instruction:
- Find every conditional in a client that distinguishes a primitive from a group, and assess whether the operation can be expressed through Component.

Key point:
- Composite moves the leaf-versus-group distinction into the object structure.
- Uniformity is useful when clients genuinely need the same operation on both kinds of object.
26. Q: Where should Composite declare child-management operations such as Add and Remove?
A: Show answer
Declaring Add and Remove in Component maximizes transparency because clients can treat all components through one interface. It reduces safety, however, because a client can attempt to add children to a Leaf. Declaring those operations only in Composite improves type safety in statically typed languages because attempts to modify a Leaf can be rejected at compile time, but clients can no longer treat all components identically and may need to recover type information. The chapter favors transparency in its discussion but recognizes that either decision is a trade-off. If invalid operations are exposed on Component, they should fail clearly rather than silently corrupt state.

Study instruction:
- Choose a design for a tree API and document whether it prioritizes a uniform interface or compile-time prevention of invalid child operations.

Key point:
- Composite child APIs trade transparency against safety.
- Do not offer meaningless operations without a defined and diagnosable failure behavior.
27. Q: Why might a Composite maintain explicit parent references?
A: Show answer
A parent reference allows a child to navigate upward, simplifies moving through and managing the tree, and can help remove a component from its containing composite. It can also support patterns such as Chain of Responsibility. The critical invariant is that a child’s parent reference must identify the composite that actually contains it. The chapter recommends changing the parent reference only as part of Add and Remove operations so the relationship is maintained consistently. If the same child can belong to several parents, the model becomes more complicated and a single parent pointer is insufficient.

Study instruction:
- Test Add, Remove, and move operations and verify that both the child list and the child’s parent reference agree after each operation.

Key point:
- Parent references simplify upward navigation but create a consistency invariant.
- Update containment and parent links together.
28. Q: What problem arises when Composite components are shared by multiple parents?
A: Show answer
A simple parent reference assumes that each child has at most one parent. If the same component is shared by several composites, that reference becomes ambiguous: a request that travels upward cannot determine which parent is intended. One possible design is to store multiple parents, but this can create further ambiguity. The chapter points to Flyweight as another way to rethink the design: shared children can avoid storing parent pointers and receive context-dependent information externally when required. Sharing should therefore be a deliberate structural decision, not an accidental consequence of reusing a child object.

Study instruction:
- Determine whether each node has one owner or may appear in several structures; then specify how any upward request identifies its context.

Key point:
- Shared children complicate parent navigation.
- Do not combine multi-parent sharing with a single unqualified parent pointer.
29. Q: How should child ordering be handled in a Composite?
A: Show answer
Some composites are unordered collections, while others require a meaningful sequence. In a drawing editor, child order may determine front-to-back display. In a parse tree, child order may represent the sequence of a program’s elements. When order matters, the child-access and management interface must preserve it, and operations such as insertion, removal, and traversal must agree on that ordering. The chapter identifies Iterator as a useful guide for designing ordered child access.

Study instruction:
- Use an example where order changes meaning, then define how insertion, traversal, and removal preserve that order.

Key point:
- Child order can be part of the semantics of a composite.
- Choose a child collection and iterator interface that preserve required sequence.
30. Q: How can caching improve Composite performance, and what must be maintained?
A: Show answer
A composite can cache information about its descendants to avoid repeatedly traversing or searching the entire structure. The chapter’s Picture example could cache the bounding box of its children so that drawing or selection can skip a Picture whose bounds are outside the visible region. The risk is stale cached information: a child change may alter the result. If cached values depend on descendants, changes must invalidate or update the relevant caches in ancestor composites. Parent references or an equivalent notification path can help propagate invalidation.

Study instruction:
- Identify derived values such as aggregate bounds or total price, then test that modifying any descendant invalidates every affected cached value.

Key point:
- Caching reduces repeated traversal but introduces consistency work.
- A cache is correct only when every relevant structural change updates or invalidates it.
31. Q: What storage and lifecycle decisions matter when implementing Composite?
A: Show answer
A composite can store children in lists, trees, arrays, hash tables, or even dedicated fields; the choice depends on the required access and update behavior. Putting a child-list field in the Component base class simplifies a common interface but consumes memory in every Leaf, even though leaves have no children. In languages without garbage collection, the chapter notes that a Composite will usually delete its children when destroyed, except where immutable leaves are intentionally shared. These decisions affect memory use, ownership, and the reliability of removal and destruction.

Study instruction:
- Review the expected number of leaves and composites, child access patterns, sharing rules, and ownership model before selecting a storage structure.

Key point:
- Composite storage choices affect memory, performance, and lifecycle behavior.
- Define ownership clearly before deciding who destroys child objects.
32. Q: How does Composite relate to Iterator, Visitor, Flyweight, Decorator, and Chain of Responsibility?
A: Show answer
These patterns solve complementary problems around a composite structure. Iterator can traverse children in a controlled order. Visitor can localize operations that might otherwise be distributed across Leaf and Composite classes. A parent link can support Chain of Responsibility by allowing requests to move upward. Flyweight can share leaf objects, but that changes the parent-reference assumptions. Decorator can wrap components to add responsibilities while retaining the Component interface. These combinations are useful because they address different concerns: traversal, operation placement, sharing, propagation, and extension.

Study instruction:
- Choose one composite structure and identify which additional concern—traversal, shared leaves, extra behavior, or upward propagation—would justify another pattern.

Key point:
- Composite often cooperates with patterns that address adjacent structural concerns.
- Combine patterns only when each contributes a distinct responsibility.
33. Q: What is the intent and basic structure of Decorator?
A: Show answer
Decorator attaches additional responsibilities to an individual object dynamically. A decorator conforms to the same interface as the component it wraps, maintains a reference to that component, and forwards requests to it. A concrete decorator may perform extra work before or after forwarding. Because the decorated object still presents the Component interface, clients can generally use it wherever an undecorated component is expected. Nesting decorators recursively allows responsibilities to be combined without defining a separate subclass for every combination.

Study instruction:
- Trace a Draw request through a component wrapped by two decorators and identify what each wrapper contributes.

Key point:
- Decorator adds behavior around an existing object while preserving its interface.
- The wrapper’s interface conformity enables transparent composition.
34. Q: What use cases make Decorator more suitable than subclassing?
A: Show answer
Decorator is useful when responsibility must be added to selected instances rather than to every instance of a class, when the added responsibility may be withdrawn, or when subclassing would create a large number of classes for combinations of features. The chapter’s user-interface example adds a scroll bar or border to a particular TextView only when needed. A class-based design would need combinations such as bordered, scrollable, and bordered-and-scrollable variants. Decorators allow the client to assemble only the responsibilities required by that object.

Study instruction:
- List optional features for a class and estimate how many subclasses would be required to represent every combination; then model a run-time composition.

Key point:
- Decorator supports per-object extension and reversible attachment.
- Use it when responsibilities vary independently among instances.
35. Q: How do Decorator objects collaborate with their components?
A: Show answer
The abstract Component defines the interface that can receive responsibilities, and ConcreteComponent supplies the basic object. Decorator maintains a Component reference and conforms to the same interface. ConcreteDecorator adds a particular responsibility. When a client invokes an operation, the decorator can perform its own work, forward the request to the wrapped Component, and then perform further work if needed. In the TextView example, BorderDecorator draws a border while ScrollDecorator adds scrolling behavior. The order and nesting of wrappers determine how requests pass through the assembled object.

Study instruction:
- For each decorator operation, specify whether its additional work occurs before forwarding, after forwarding, or both.

Key point:
- Decorators extend behavior by controlling how a request is forwarded.
- Keep the forwarding contract consistent across concrete decorators.
36. Q: What are the main benefits of Decorator compared with static inheritance?
A: Show answer
Decorator allows responsibilities to be attached and removed at run time, and different responsibilities can be mixed and matched for individual objects. Multiple instances of a responsibility can also be nested; the chapter uses two BorderDecorators to illustrate a double border. Static inheritance instead requires classes for each combination and makes the selected feature set part of the class definition. Decorator also supports a pay-as-you-go design: a simple component need not carry every possible feature in its own implementation. New decorator types can be introduced independently of the classes they extend.

Study instruction:
- Model two objects of the same component class with different combinations of optional behavior and compare the number of classes needed under inheritance and decoration.

Key point:
- Decorator reduces subclass proliferation and supports run-time combinations.
- Use small, composable responsibilities instead of one feature-laden class.
37. Q: What are the liabilities of a design that uses many decorators?
A: Show answer
A decorated object is not identical to the component it encloses, even though the interfaces conform. Code that relies on object identity must therefore retain and refer to the underlying component where necessary rather than assuming the outer decorator is the same object. Decorator-heavy designs can also create many small objects whose differences lie mainly in how they are connected. This makes the design highly customizable but can make it harder for developers to understand, inspect, and debug. These costs should be weighed against the flexibility gained from dynamic composition.

Study instruction:
- Find code that compares object identity or stores object references, and determine whether it expects the undecorated component or the outer wrapper.

Key point:
- Decorators preserve an interface, not object identity.
- Plan how clients will access the underlying component when identity matters.
38. Q: What implementation rules help keep Decorator lightweight and usable?
A: Show answer
The decorator’s interface must conform to the component interface, which commonly means that concrete components and decorators share a common Component type. The chapter advises keeping that base type lightweight and focused on the interface rather than embedding substantial state or functionality that every decorator must carry. When only one responsibility is being added to an existing hierarchy, a separate abstract Decorator class may be unnecessary; the concrete decorator can contain the forwarding logic itself. A heavyweight Component can make full decorators too costly, in which case a specialized extension object may be preferable.

Study instruction:
- Review the Component base class for data or behavior that every decorator would be forced to carry, and simplify the contract where possible.

Key point:
- A lightweight common interface keeps decorators inexpensive to compose.
- Do not make every decorator inherit unrelated state or responsibilities.
39. Q: How does Decorator differ from Strategy?
A: Show answer
The chapter describes Decorator as changing an object’s “skin” and Strategy as changing its “guts.” A decorator encloses the component from the outside, conforms to the component interface, and the component need not know that decorators exist. A strategy is an object to which the component deliberately delegates part of its behavior; the component maintains or selects the strategy and may need changes to support new strategy types. Strategy can define a specialized, lightweight interface, whereas a decorator must preserve the component interface. The chapter notes that strategy-like adorners can be preferable when the component is intrinsically heavyweight.

Study instruction:
- Decide whether an extension should be transparent outside the component or be an explicitly replaceable internal policy used by the component.

Key point:
- Decorator wraps an object; Strategy changes an internal behavior choice.
- Choose according to whether the extension belongs outside or inside the component’s own behavior.
40. Q: How does Decorator apply to streams and data transformations?
A: Show answer
The chapter extends the pattern beyond user interfaces to I/O streams. A Stream abstraction provides operations such as writing integers and strings, while concrete stream classes determine where buffered data goes. StreamDecorator forwards stream requests, and specialized decorators can transform data when the buffer is handled. CompressingStream compresses the data, while ASCII7Stream converts it to seven-bit ASCII for a channel that requires that representation. Wrapping a FileStream with these decorators composes storage and transformation responsibilities without creating a separate class for every combination.

Study instruction:
- Draw the stream wrapper chain and verify the transformation and forwarding performed at each stage of a write.

Key point:
- Decorator composes independent stream responsibilities.
- The pattern applies to data processing as well as visual embellishment.
41. Q: What is the intent of Facade?
A: Show answer
Facade provides a unified, higher-level interface to a set of interfaces in a subsystem. Its purpose is to make a complex subsystem easier to use for clients that need common functionality but do not want to coordinate all of the lower-level classes themselves. A facade knows which subsystem objects handle a request and delegates to them, sometimes translating the client-level operation into a sequence of subsystem operations. It simplifies access without necessarily hiding every subsystem class from advanced clients.

Study instruction:
- Identify the low-level classes involved in one common task and define the smallest useful operation a client should call instead.

Key point:
- Facade offers a simpler entry point to a subsystem.
- A facade coordinates existing subsystem functionality rather than replacing the subsystem.
42. Q: How does the Compiler facade example coordinate a complex subsystem?
A: Show answer
The compiler subsystem includes classes such as Scanner, Parser, ProgramNodeBuilder, ProgramNode, BytecodeStream, and CodeGenerator. These objects perform specialized stages such as tokenization, parse-tree construction, traversal, and code generation. Most compiler clients only want to compile source code, not orchestrate those details. The Compiler facade provides a higher-level operation that brings the objects together and generates code for a target machine. Clients needing unusual or specialized behavior can still use lower-level subsystem facilities where appropriate.

Study instruction:
- Trace the compile operation through scanning, parsing, construction of the program tree, traversal, and code generation.

Key point:
- Compiler centralizes the ordinary workflow behind a simple operation.
- A facade reduces the coordination burden placed on typical clients.
43. Q: When should a Facade be introduced around a subsystem?
A: Show answer
Facade is appropriate when a subsystem has become complex, when many clients depend directly on its implementation classes, or when a system needs clear entry points between layers. A subsystem may contain many small reusable classes that help customization but make ordinary use difficult. A facade supplies a default simplified view for common clients. It can also reduce dependencies between subsystems so that they communicate through defined entry points rather than relying on each other’s internal classes.

Study instruction:
- Map the dependencies from clients into a subsystem and identify which dependencies could be replaced by a stable facade interface.

Key point:
- Facade is useful for usability, dependency reduction, and subsystem layering.
- Keep common client workflows simple without preventing specialized access where it is required.
44. Q: What are the main consequences of using Facade?
A: Show answer
Facade reduces the number of subsystem objects a client must know about and weakens coupling between clients and subsystem implementation classes. This can reduce complex or circular dependencies, limit recompilation when subsystem internals change, and make independently developed subsystems easier to connect or port. A facade does not have to prevent applications from using subsystem classes directly; clients can choose the simple interface or access specialized facilities when necessary. The benefit depends on clients actually using the facade for the common path.

Study instruction:
- Review client code before and after adding a facade and identify which implementation dependencies have been removed.

Key point:
- Facade simplifies use and reduces coupling without necessarily hiding all lower-level classes.
- A facade is an optional simplification layer, not necessarily a locked boundary.
45. Q: How can a Facade remain flexible without losing its simplicity?
A: Show answer
The chapter describes making Facade an abstract class with concrete subclasses for different subsystem implementations, allowing clients to depend on the abstract facade. Another option is to configure a facade with different subsystem objects and replace those collaborators to customize behavior. In the Compiler example, hard-coding a code generator simplifies the common interface, while accepting a CodeGenerator parameter gives clients more control but adds complexity. The design decision is to provide enough extension points for real variation without forcing ordinary clients to configure every internal choice.

Study instruction:
- List the variations clients genuinely need and expose only those choices through the facade’s public construction or configuration interface.

Key point:
- Facade flexibility should be balanced against its simplifying purpose.
- Do not turn a simple facade into a mirror of every subsystem option.
46. Q: How does Facade differ from Mediator and Adapter?
A: Show answer
Facade presents a simplified interface to an existing subsystem; the subsystem objects do not need to know about it and continue to perform their own work. Mediator centralizes communication among colleague objects, which know about and communicate through the mediator rather than coordinating directly with one another. Adapter changes one existing interface so it conforms to another interface expected by a client. Facade defines a new higher-level entry point for a group of objects, whereas Adapter reuses a target interface and Mediator reorganizes object-to-object communication.

Study instruction:
- For a design with several collaborating classes, decide whether the problem is a hard-to-use API, an incompatible interface, or excessive peer-to-peer communication.

Key point:
- Facade simplifies a subsystem; Mediator centralizes colleague interaction; Adapter resolves interface mismatch.
- Do not classify every object that forwards requests as a Facade.
47. Q: What problem does Flyweight solve?
A: Show answer
Flyweight uses sharing to support large numbers of fine-grained objects efficiently. A straightforward object-per-occurrence design may be conceptually flexible but consume excessive memory when the application creates hundreds of thousands of similar objects. Flyweight separates the state that can be shared from the state that depends on each occurrence. The shared object stores the common portion, while the client supplies the context-specific information when an operation is performed. The purpose is specifically space efficiency, not simply making objects consistent or reducing the number of class definitions.

Study instruction:
- Estimate the number of instances in a candidate design and identify which fields are truly common across occurrences.

Key point:
- Flyweight reduces storage by sharing objects with common state.
- Sharing is beneficial only when the object’s context-dependent state can be separated.
48. Q: What is the difference between intrinsic and extrinsic state in Flyweight?
A: Show answer
Intrinsic state is independent of the context in which a flyweight is used and can safely be stored in the shared object. Extrinsic state varies by occurrence or context and must be stored or computed outside the flyweight, then passed to it when needed. In the document-editor example, a Character flyweight can store the character code. Its position in the document and formatting information depend on where that character occurs and therefore are extrinsic in the sample design. Draw and Intersects receive the necessary context so the shared object can act correctly in each occurrence.

Study instruction:
- Take every field in a frequently instantiated class and classify it as context-independent or occurrence-dependent; justify each classification.

Key point:
- Intrinsic state is stored; extrinsic state is supplied by the client or context.
- A field must not remain inside a shared flyweight if its value differs by use.
49. Q: What conditions make Flyweight effective, and what limitation must be accepted?
A: Show answer
Flyweight is most useful when an application creates many objects, storage costs are significant, most state can be made extrinsic, and many occurrences can be represented by a relatively small set of shared objects. The application must also avoid depending on object identity. Two logically distinct occurrences may reference the same shared flyweight, so identity tests can report the same object even though the occurrences have different positions or roles. The chapter emphasizes that effectiveness depends heavily on the actual distribution of state and use, not merely on the number of classes.

Study instruction:
- Check the object count, memory consumed per instance, variety of intrinsic state, and whether client logic relies on distinct object identity.

Key point:
- Flyweight trades context management for reduced object storage.
- Do not use shared flyweights where distinct object identity is part of the application’s meaning.
50. Q: What are the participants and collaboration rules in Flyweight?
A: Show answer
Flyweight defines the interface through which a shared object receives extrinsic state. ConcreteFlyweight stores only shareable intrinsic state. UnsharedConcreteFlyweight represents objects that use the Flyweight interface but need not themselves be shared; the chapter’s Row and Column can contain shared Character objects. FlyweightFactory creates and manages shared instances, returning an existing object or creating one when absent. Client keeps references to flyweights and stores or computes their extrinsic state. Clients should obtain shared ConcreteFlyweights through the factory rather than instantiate them directly, or sharing may be defeated.

Study instruction:
- Identify which objects own the context and which object guarantees one shared instance per intrinsic-state key.

Key point:
- The factory enforces sharing; clients supply context.
- Centralize shared-object lookup so clients cannot accidentally create duplicates.

The character object keeps its character code, while the context maps positions or ranges in the glyph structure to font information. During traversal, GlyphContext tracks the current index; drawing operations query it for the font at that position. A BTree represents ranges of glyphs with common formatting, and it is updated when styles change or glyphs are inserted or removed. - GlyphContext externalizes formatting state from shared character objects.

52. Q: What are the performance trade-offs and memory savings of Flyweight?
A: Show answer
Flyweight reduces the number of allocated objects and the amount of repeated intrinsic state, but introduces run-time work to pass, locate, or compute extrinsic state. Savings depend on how many instances are consolidated, how much state is shared, and whether extrinsic data is computed or stored elsewhere. The chapter notes that the best savings occur when substantial state can be shared and context-specific state can be computed rather than replicated. Its Doc editor example reports that a typical 180,000-character document required only 480 character objects. That result illustrates potential savings, not a universal performance guarantee.

Study instruction:
- Compare memory and lookup costs before and after sharing, including the cost of updating external context when objects move or change.

Key point:
- Flyweight exchanges repeated storage for shared state and context-processing work.
- Measure both memory savings and the new cost of context lookup.
53. Q: How does Flyweight interact with Composite and Strategy?
A: Show answer
Flyweight is often combined with Composite so a hierarchical structure can be represented as a directed acyclic graph with shared leaf nodes. Shared leaves cannot safely store one parent pointer when they appear under multiple parents; parent context must instead be supplied externally where required. The chapter also notes that State and Strategy objects are often good flyweights because they can contain reusable behavior with little context-dependent state. ET++ uses shared Layout objects to support different user-interface look-and-feel arrangements. These combinations let an application share behavior or leaf data without duplicating many small objects.

Study instruction:
- Look for repeated leaf objects or reusable behavior objects in a hierarchy and decide whether their state can be separated from their parent context.

Key point:
- Flyweight can make repeated leaves and strategy objects shareable.
- Sharing must be reflected in the surrounding object graph and context-passing design.
54. Q: What is the intent of Proxy, and what does the proxy control?
A: Show answer
Proxy provides a surrogate or placeholder for another object so access to that object can be controlled. The proxy presents an interface corresponding to the Subject interface and keeps whatever reference or identifier is needed to reach the RealSubject. Depending on its purpose, it may defer creation, represent an object in another address space, check permissions, or perform housekeeping when the object is accessed. The client can use the proxy in place of the subject while the proxy decides whether and how the real operation proceeds.

Study instruction:
- Identify why direct access to the subject is expensive, remote, restricted, or otherwise undesirable, then identify the access decision owned by the proxy.

Key point:
- Proxy controls access through an intervening object.
- The proxy’s purpose is access control or access management, not adding arbitrary responsibilities.
55. Q: How does a virtual proxy defer creation of an expensive object?
A: Show answer
A virtual proxy stands in for an expensive object until the object is actually needed. In the chapter’s image-editor example, the document stores an ImageProxy rather than immediately loading every large raster image. The proxy retains the image file name and cached extent, such as width and height. It can answer layout requests for the extent without loading the full image. When Draw is called, it creates or loads the real Image, keeps a reference to it, and forwards subsequent requests. This makes opening a document faster when many embedded images are not immediately visible.

Study instruction:
- Test a document containing several large images and record which operations should use cached metadata and which should trigger loading.

Key point:
- A virtual proxy postpones expensive initialization until required.
- Cache only information that can be answered reliably without creating the real subject.
56. Q: How does a remote proxy work?
A: Show answer
A remote proxy represents an object located in a different address space. It receives a client request locally, encodes the request and its arguments, sends them to the remote subject, and returns or relays the response. The chapter cites NEXTSTEP’s NXProxy as an example: the proxy provides a local representative for distributed objects and handles request and result encoding. This arrangement hides much of the location difference from the client, but the proxy still depends on communication with the remote object and must handle the mechanics of that interaction.

Study instruction:
- Trace a remote operation from client invocation through request encoding, transport, execution, and return-value decoding.

Key point:
- A remote proxy makes a remote subject accessible through a local representative.
- The proxy hides location details but does not remove the realities of remote communication.
57. Q: How do protection proxies and smart references differ from virtual proxies?
A: Show answer
A protection proxy controls whether the caller has permission to perform a requested operation. It checks access rights before forwarding the request, as in the chapter’s discussion of protected operating-system objects. A smart reference replaces a bare pointer with additional access behavior, such as reference counting, loading a persistent object when first referenced, or checking a lock before access. A virtual proxy primarily defers creation of an expensive object. All add indirection, but the additional responsibility differs: authorization, reference housekeeping, or deferred initialization.

Study instruction:
- For a candidate proxy, specify the condition checked before forwarding and the action taken when that condition is not satisfied.

Key point:
- Proxy variants share an indirection structure but have different access responsibilities.
- Do not confuse lazy loading with authorization or reference management.
58. Q: What is copy-on-write, and how can Proxy implement it?
A: Show answer
Copy-on-write postpones copying a large object until a client actually modifies it. Initially, several handles or proxies can refer to the same subject, and copying a proxy only increments a reference count. If a client requests a modifying operation, the proxy creates a private copy and adjusts the reference count before applying the change. If the shared object is never modified, the system avoids the cost of copying it. The approach therefore combines delayed work with reference management. It is useful only when the extra bookkeeping and copy-on-modification behavior are implemented consistently.

Study instruction:
- Test the read-only case and the first write separately, verifying reference counts and ensuring that modifying one logical copy does not change another.

Key point:
- Copy-on-write delays expensive copying until mutation occurs.
- Reference counting and correct separation after a write are essential to the technique.
59. Q: What implementation issues arise when building proxies?
A: Show answer
The chapter discusses several language-dependent approaches. In C++, overloading the member-access operator can make a virtual proxy behave pointer-like, but loading then occurs when the proxy is dereferenced; that is unsuitable when loading must happen only for a particular operation such as Draw. In that situation, the proxy must implement and forward operations explicitly, often with repetitive forwarding code. Smalltalk’s doesNotUnderstand: hook can forward otherwise-unimplemented messages, but special virtual-machine messages such as identity may bypass normal lookup, and the hook was designed for error handling rather than speed. A generic proxy can avoid knowing the concrete subject type when it uses an abstract interface, but a proxy that constructs the real subject may need the concrete type.

Study instruction:
- Choose a forwarding mechanism and test precisely when loading, authorization, and identity behavior occur; include operations handled specially by the language runtime.

Key point:
- Proxy implementation must match the required timing and interception point.
- Convenient automatic forwarding can have important semantic and performance limitations.
60. Q: How do Adapter and Bridge differ even though both forward requests?
A: Show answer
Both patterns introduce indirection and forward requests to another object, but they address different lifecycle problems. Adapter resolves incompatibility between existing interfaces so independently designed classes can work together; it is commonly introduced after the mismatch is discovered. Bridge is designed up front to separate an abstraction from one or more implementations that are expected to vary independently. Adapter reuses an expected interface, while Bridge maintains separate abstraction and implementor hierarchies. Neither is inherently superior: the correct choice depends on whether the problem is interface mismatch or independent variation.

Study instruction:
- For each design, ask whether the two sides already exist with incompatible interfaces or are being separated deliberately for future independent evolution.

Key point:
- Adapter makes incompatible interfaces cooperate; Bridge separates independent dimensions.
- The patterns may look structurally similar but solve different design problems.
61. Q: How should Composite, Decorator, and Proxy be distinguished?
A: Show answer
Composite organizes multiple related objects into a part–whole structure and lets clients treat a group like an individual component. Decorator wraps a component to add responsibilities while preserving its interface; it may be nested recursively to combine features. Proxy also provides an indirect reference with a similar interface, but its purpose is to stand in for a subject when direct access is undesirable or costly. A composite aggregates children, a decorator embellishes behavior, and a proxy manages access. Composite and Decorator can be used together, but their intents remain distinct; Proxy is not intended for open-ended recursive embellishment.

Study instruction:
- Given a wrapper or tree-shaped class diagram, identify whether its main responsibility is aggregation, added behavior, or controlled access.

Key point:
- Similar composition mechanisms do not imply the same pattern intent.
- Classify by what the enclosing object is responsible for doing.
62. Q: How does a structural pattern choice affect practical verification and maintenance?
A: Show answer
Verification should target the contract each pattern introduces. For Adapter, check interface translation and coverage of adaptee variants. For Bridge, run the same abstraction behavior against each supported implementor and ensure client code remains independent of concrete implementations. For Composite, test recursive traversal, ordering, parent invariants, child-management failures, and cache invalidation. For Decorator, verify forwarding order, preservation of the component interface, and combinations of responsibilities. For Facade, confirm that the common workflow is correctly coordinated. For Flyweight, verify shared identity assumptions and correct context state. For Proxy, test access decisions, lazy creation, remote forwarding, and reference behavior. These are practical test recommendations derived from the responsibilities described in the chapter.

Study instruction:
- Create a pattern-specific test checklist from the participant contracts, then include edge cases where delegation, sharing, or lifecycle changes occur.

Key point:
- Test the structural contract and its edge cases, not just object construction.
- The most important failures occur at composition, forwarding, context, and ownership boundaries.

1. Q: What problem do behavioral design patterns address?
A: Show answer
Behavioral design patterns describe algorithms, the assignment of responsibilities, and the ways objects communicate. They are useful when control flow is distributed across several objects and becomes difficult to understand by following execution step by step. Rather than concentrating only on which operation runs next, they make the relationships between cooperating objects explicit. Some patterns distribute behavior through inheritance, while others compose objects and delegate work. Their common purpose is to make behavior easier to vary, coordinate, reuse, and maintain without creating unnecessary dependencies.

Study instruction:
- Explain how an object interaction can be difficult to understand even when each individual method is simple.

Key point:
- Behavioral patterns organize algorithms, responsibilities, and communication among objects.
2. Q: Why does the chapter distinguish algorithm structure from run-time control flow?
A: Show answer
An algorithm may be implemented through many interacting objects, so the actual control path can be difficult to follow at run time. Behavioral patterns provide a higher-level description of the collaboration: which object owns a responsibility, which object delegates, and how a request moves or a change is communicated. This shifts design attention from tracing every call to understanding the stable relationships that make the behavior work. It is especially valuable when control decisions are distributed among handlers, states, strategies, observers, or visitors.

Study instruction:
- Choose a multi-object feature and map its responsibilities and message flow before tracing individual method calls.

- Understand the collaboration structure, not only the sequence of method calls.
3. Q: What is the difference between behavioral class patterns and behavioral object patterns?
A: Show answer
Behavioral class patterns use inheritance to distribute or specialize behavior between classes. In this chapter, Interpreter represents grammar rules through a class hierarchy, while Template Method defines an algorithm in a base class and lets subclasses supply selected steps. Behavioral object patterns rely primarily on object composition and delegation. They allow collaborating objects to change independently at run time, but they introduce links and communication protocols between those objects. The distinction is about the principal mechanism used to vary behavior, not a claim that either category can never use the other mechanism.

A: Show answer
They move a changing responsibility into a separate object or collaboration with a defined interface. The existing object then delegates to the new object rather than embedding all variable behavior in its own implementation. This allows the changing part to be replaced or extended without rewriting the stable context. The benefit depends on choosing a genuinely variable responsibility; extracting every small operation into an object can add needless indirection.

- Identify one volatile behavior in an application and describe the interface through which a separate object could supply it.

6. Q: What is the intent of Chain of Responsibility?
A: Show answer
Chain of Responsibility avoids coupling a request sender to a specific receiver by giving several objects an opportunity to handle the request. The sender passes the request to the first candidate. That object either handles it or forwards it to its successor, and the process continues until a candidate accepts responsibility or the chain ends. The sender therefore has an implicit receiver: it knows where to start but does not need to know which object will ultimately respond. A context-sensitive help system is a representative example because a widget, its dialog, or the application may provide the most appropriate level of help.

Study instruction:
- Draw a chain for a context-sensitive help request and mark the first candidate, possible handlers, and final fallback.

Key point:
- The sender initiates a request without naming the eventual handler.
7. Q: Which participants form a typical Chain of Responsibility implementation?
A: Show answer
The Handler defines the common request-handling interface and may maintain a successor link. ConcreteHandler objects decide whether they can handle a request and either perform the work or forward it. The Client initiates the request by sending it to an object at the start of the chain. In the help example, a button and a dialog can be concrete handlers, while the application is a more general candidate. The common interface allows the client to work with a handler without knowing its concrete class or the identity of later candidates.

- Create a small class diagram with Handler, two ConcreteHandler classes, and Client; annotate who owns the successor reference.

Key point:
- The common handler interface and successor relationship make the chain possible.
8. Q: How does a request travel through a Chain of Responsibility?
A: Show answer
The client sends the request to the first handler. Each handler evaluates whether the request falls within its responsibility. A handler that accepts it performs the required operation and stops propagation. A handler that does not accept it forwards the request to its successor, commonly through a default implementation in the Handler base class. The request may therefore move from a highly specific object to progressively more general objects. The sender remains unaware of the final receiver, and a handler need not understand the full structure of the chain.

Study instruction:
- Trace one request through three handlers, specifying the condition under which each handler accepts or forwards it.

Key point:
- Each candidate either handles the request or delegates it to the next candidate.
9. Q: When is Chain of Responsibility appropriate?
A: Show answer
It is appropriate when several objects may be able to handle a request, the correct handler cannot be identified in advance, and the receiver should be selected automatically. It is also useful when the participating set of handlers must be configured dynamically or when the sender should issue a request without naming a receiver. The pattern is less compelling when exactly one known object must always perform the operation, because the chain then adds indirection without providing meaningful flexibility. A chain is particularly natural when the application's existing object hierarchy already expresses the order of fallback.

- Compare a request with one fixed receiver against a request that can be handled by several context-dependent candidates.

- Use a chain when handler selection is uncertain or intentionally dynamic.

A: Show answer

Parent links in a part-whole hierarchy, for example, may provide a natural route from a component to a more general handler. Reusing links saves additional fields and can simplify construction, but only works when the existing relationships match the required responsibility order. If they do not, separate successor links are necessary. The Handler can supply a default forwarding operation so uninterested subclasses do not need to repeat the same delegation code.

A general handler operation with a request code supports more request kinds, but requires dispatch conditionals and agreement on the code format; packing parameters can also weaken type safety. No. The pattern explains how grammar rules are represented and how an already constructed syntax tree is interpreted, but it does not prescribe parsing. A tree may be produced by a table-driven parser, a hand-written recursive-descent parser, or directly by a client. This distinction matters because parsing validates and transforms textual syntax into a structured representation, whereas interpretation evaluates or processes that representation. Keeping the stages separate makes it possible to change the parser without necessarily changing the expression classes.

25. Q: How can Visitor and Flyweight complement Interpreter?
A: Show answer
If a system repeatedly adds new ways to process the same expression tree, putting every operation on every expression class can make the grammar hierarchy harder to maintain. Visitor can move operations such as type checking, optimization, or code generation into separate visitor objects. Flyweight can help when a grammar contains many repeated terminal symbols: shared terminal objects can represent intrinsic information, while context-specific information is supplied during interpretation. These techniques address different pressures—new operations and repeated object state—and should be introduced only when those pressures are real.

26. Q: What is the intent of Iterator?
A: Show answer
Iterator provides sequential access to the elements of an aggregate without exposing the aggregate's internal representation. The traversal responsibility is moved out of the collection and into an iterator object that tracks its current position. This keeps the collection interface from accumulating methods for every possible traversal policy and allows several traversals to be active at the same time. A list can therefore support a normal sequential iterator, a filtering iterator, or another traversal strategy without revealing whether its elements are stored in an array, linked structure, or another representation.

Aggregate defines an operation for creating an iterator, and ConcreteAggregate returns the appropriate concrete iterator for its representation. The client uses the iterator interface rather than depending on the concrete collection structure, which supports uniform traversal across different aggregate implementations.

28. Q: What is the difference between external and internal iteration?
A: Show answer
With an external iterator, the client controls the traversal by explicitly requesting the current element, advancing, and checking completion. With an internal iterator, the client supplies an operation and the iterator applies it to the aggregate's elements. External iteration is more flexible for coordinating multiple collections or comparing them because the client controls advancement. Internal iteration is often easier to use because the traversal logic is encapsulated, but it depends on language facilities for expressing the operation and is less suited to certain client-controlled comparisons.

29. Q: What is a cursor, and how does it differ from a full iterator?
A: Show answer
A full iterator can define the traversal algorithm as well as maintain the current position. In a cursor-style design, the aggregate defines the traversal algorithm and the iterator merely records where traversal currently is. The client may then ask the aggregate to advance the cursor. The choice determines where traversal policy lives: inside a reusable iterator or inside the collection itself. A cursor can be appropriate when the aggregate owns specialized traversal logic, but it may make it harder to substitute independent traversal policies.

- A cursor stores position; a full iterator can own the traversal policy.

A collection can also expose a common iterator-creation interface, allowing clients to traverse different aggregate types through the same protocol. Concrete aggregates can return specialized iterators, including iterators for different traversal orders or filtering rules. This is especially useful for recursive structures such as composites and parse trees, where different tasks may need different traversal sequences.

Each colleague communicates with a mediator rather than maintaining direct dependencies on every other colleague. This replaces a difficult web of peer-to-peer relationships with a more structured one-to-many relationship.

Changing the interaction rules may require changing the mediator rather than modifying each colleague, which can reduce subclassing and improve reuse. Memento captures a snapshot of some portion of an object's internal state so that the object can restore that state later, without exposing its implementation details to other objects. The object that owns the state creates the memento and later uses it to restore itself. A separate caretaker can retain the snapshot but should not inspect or manipulate its contents. This is useful for undo, checkpoints, or recovery when a direct public state-access interface would violate encapsulation by exposing internal representation.

A: Show answer
The caretaker is responsible for keeping the mementos it receives and managing their lifetime, but it should not interpret their contents. It must decide when snapshots are retained, returned, or discarded, and it may need to enforce history limits. Because it cannot know how much state a memento contains, apparently lightweight snapshot management can consume substantial memory. The subject does not need to know the concrete observer classes or how many observers exist. A model with several views is a classic example: each view can respond to changes in the shared model. Observer is appropriate when dependent objects need change notifications but should remain loosely coupled and independently reusable.

The subject knows only the abstract observer interface and its collection of subscribers, not the concrete classes or responsibilities of those observers. New observers can be attached without modifying the subject or existing observers, and observers can be reused with different subjects when their contracts are compatible. 45. Q: What is the difference between push and pull notification models in Observer?
A: Show answer
In a push model, the subject sends detailed change information to observers as part of the notification. This can reduce the work observers need to do, but it assumes the subject knows what information its observers need and can reduce observer reuse. In a pull model, the subject sends a minimal notification and observers query it for the details they require. Pull keeps the subject more ignorant of observer needs, but observers may perform extra work to discover what changed. The right choice depends on the amount of change information and the desired degree of independence.
